## 一、背景与问题

### 切块的时候，上下文被切掉了

要让 AI 模型在特定场景里有用，它常常需要背景知识：客服聊天机器人需要了解所服务的具体业务，法律分析机器人需要知道大量的过往案例。开发者通常用检索增强生成（RAG）来补这块知识：从知识库里检索相关信息，追加到用户提示词里，再让模型回答。

传统 RAG 的做法是先把知识库切成小块（通常几百个 token），用嵌入模型把每块变成向量，存进向量数据库；运行时按语义相似度找出最相关的块，追加到提示词里。嵌入模型擅长捕捉语义关系，但容易错过精确匹配；于是人们再叠加一个老技术 BM25——按词面精确匹配排序，对包含唯一标识符或技术术语的查询特别有效。两者用排序融合（rank fusion）合并去重，就是传统混合检索的完整流程。

问题出在切块这一步。切块会把上下文切掉。文章给了一个例子：知识库里有一堆美国 SEC 财报，问题是“ACME Corp 在 2023 年第二季度的收入增长是多少？”相关的一块可能只写着“公司收入比上季度增长了 3%”，单独看这块，既不知道是哪家公司，也不知道是哪个季度。这样的块既难被检索到，即使被检索到，模型也很难用好。

### 这篇要问什么

问题可以说成一句话：能不能在嵌入与建立 BM25 索引之前，先给每个块补上一段说明它在整篇文档中位置的上下文，让检索不再因为切块而丢失信息——而且补上下文这件事本身能不能便宜到可以大规模部署？

如果答案是肯定的，RAG 的检索步骤就能在不换嵌入模型、不换向量库的前提下直接变好。这是一篇工程方法公告，它要回答的不是一个科学假说，而是一个做法问题：这个做法管不管用、好多少、贵不贵。

## 二、方法与设计

### 上下文检索：给每个块贴一张说明条

上下文检索（Contextual Retrieval）由两个子技术组成。

第一是上下文嵌入（Contextual Embeddings）：在嵌入每个块之前，先在块前面加上一段针对该块的解释性上下文，说明这个块在整篇文档中的位置与含义。

第二是上下文 BM25（Contextual BM25）：用同样加了上下文的文本来建立 BM25 索引，让词面匹配也能利用这些上下文信息。

回到 SEC 财报的例子：原来的块只说“公司收入比上季度增长了 3%”，加上上下文之后，块前面会多一段说明，指出这是哪家公司、哪份文件、哪个季度。文章在正文里展示了这样一个转换示例，但示例的具体文字只存在于图中，抓取文本中没有。

### 用 Claude 生成上下文

手动给成千上万甚至上百万个块写上下文是不现实的。文章的做法是交给 Claude：写一个提示词，让模型结合整篇文档，为每个块提供一段简洁的、针对该块的上下文。生成上下文用的是 Claude 3 Haiku，提示词本身在正文里以图片形式给出，抓取文本中没有（见未核实清单）。

生成的上下文通常是 50–100 个 token， prepend 到块前面，再拿去嵌入和建立 BM25 索引。预处理流程图同样只存在于图中。

### 用提示词缓存把成本压下来

上下文检索之所以能低成本部署，文章说，关键在于 Claude 的提示词缓存（prompt caching）功能。生成上下文时不需要为每个块都重复传入整篇参考文档：把文档加载进缓存一次，之后引用缓存内容即可。

在 800 token 的块、8k token 的文档、50 token 的上下文指令、每个块 100 token 上下文这些假设下，生成上下文检索块的一次性成本是每百万文档 token 1.02 美元。这是一个成本估算，不是实测账单：它依赖上面那组假设条件，换一组假设，数字就变。

### 先说清楚：知识库小的时候，根本不需要 RAG

文章开头特意先讲了一个更简单的答案：如果知识库小于 200,000 个 token（大约 500 页材料），直接把整个知识库放进提示词里就行，不需要 RAG 或类似方法。几周前发布的提示词缓存让这种做法更快、更便宜：延迟降低 2 倍以上，成本降低最高 90%。只有当知识库大到放不进上下文窗口时，才需要上下文检索这样的可扩展方案。

## 三、主要发现

### 评估设计

实验覆盖多个知识领域（代码库、小说、arXiv 论文、科学论文）、多个嵌入模型、多种检索策略与评估指标。评估指标是 1 减去 recall@20，即在前 20 个块里没能检索到的相关文档所占的百分比，也就是 top-20 检索失败率。正文的图展示的是所有知识领域的平均表现，用的是表现最好的嵌入配置（Gemini Text 004），取前 20 个块。

附录 II 给出了每个领域的部分示例问题与答案，例如代码库领域问 BasicConfigurator 的默认布局、小说领域问与 Lestrade 会面的神秘人的姓名首字母、arXiv 领域问 Penn Treebank 聚类实验中每个噪声水平用了多少个模型。完整的评估集没有公开，各领域各有多少个问题也没有报告。

### 三个数字：35%、49%、67%

正文给出的核心结果只有三个，都是平均值，都是相对降幅。

只用上下文嵌入，top-20 检索失败率从 5.7% 降到 3.7%，相对减少 35%。再叠加上下文 BM25，失败率降到 2.9%，相对减少 49%。再加一个重排序（reranking）步骤，失败率降到 1.9%，相对减少 67%。

文章说，上下文检索在评估过的每一个“嵌入模型 × 数据源”组合上都提升了性能。分项的数字在附录 I 与附录 II 的表和图里，无法从文本提取。

### 其他做法的比较

文章顺带报告了几个它试过、效果不好的做法：给块加上通用的文档摘要，收益非常有限；假设文档嵌入（hypothetical document embedding）与基于摘要的索引，评估下来表现较差。这些说法只有定性描述，没有数字。

### 重排序：再筛一遍，取前 20

重排序是最后一步：先做初始检索拿到一批候选块（实验中取前 150 个），把这些块连同用户查询一起交给重排序模型打分，选出最相关的前 K 个（实验中取前 20 个），再交给生成模型。重排序能让回答更好，同时降低成本与延迟，因为模型处理的信息更少了。

实验用的是 Cohere 的重排序模型。Voyage 也有重排序模型，但文章说没来得及测试。重排序会增加一点运行时延迟，哪怕重排序模型是并行打分的；多重排一些块能换更好的效果，少排一些则延迟与成本更低，文章建议开发者在自己的场景里试验。

### 实现时的四个注意事项

文章列了四点实现建议。第一是切块边界：块大小、切块边界与重叠的选择会影响检索性能，脚注 1 可能有补充说明，但脚注内容未在抓取文本中给出。

第二是嵌入模型：上下文检索在测试过的所有嵌入模型上都有提升，但不同模型受益程度不同；Gemini 与 Voyage 的嵌入效果特别好。

第三是自定义上下文提示词：通用提示词已经不错，但针对具体领域定制的提示词可能更好，例如加入只在知识库其他文档里定义的关键术语表。

第四是块的数量：往上下文窗口里多放几个块，能提高包含相关信息的概率，但信息太多也会干扰模型；实验试了 5、10、20 个块，20 个表现最好（附录里有比较，但数字只在图里）。

文章还提醒：生成回答时，可以把上下文检索的块传给模型，并区分哪些是上下文、哪些是块本身。以及一条贯穿全文的建议：永远要跑自己的评估（always run evals）。

### 作者的六条总结

结论部分把发现总结为六条：嵌入加 BM25 好于只用嵌入；Voyage 与 Gemini 是测试过的嵌入模型中最好的；传 20 个块比只传 10 个或 5 个更有效；给块加上下文能大幅提升检索准确率；重排序好于不重排序；所有好处可以叠加——要最大化提升，就把上下文嵌入（Voyage 或 Gemini）、上下文 BM25、重排序步骤与 20 个块组合起来用。

## 四、作者的结论与局限

### 作者自己得出的结论

作者的中心结论是：上下文检索大幅提升 RAG 的检索步骤。两个子技术——上下文嵌入与上下文 BM25——把 top-20 检索失败率降低了 49%（5.7% → 2.9%），再加上重排序，降低 67%（5.7% → 1.9%）。而且所有好处可以叠加，组合起来用效果最好。

他们还认为，这个做法部署起来很便宜：借助提示词缓存，生成上下文的一次性成本是每百万文档 token 1.02 美元。文章最后鼓励所有做知识库的开发者都去试试 cookbook 里的实现。

### 作者承认的局限

这篇东西几乎没有以“局限”名义写出的自我批评。它是一篇工程公告，不是研究论文，所以没有局限一节、没有威胁效度讨论、没有失败分析。能从正文里找到的、作者自己划出的边界有这么几处。

第一，知识库小的时候不需要这个方法：小于 200,000 token 的知识库，直接放进提示词就行。第二，重排序要付出延迟与成本代价，两者之间需要权衡，文章没有给出具体的延迟或成本数字，只建议开发者自己试验。第三，块的数量、切块边界、提示词定制这些实现选择都会影响效果，文章只给了方向性建议，没有给出普适的最优配置。第四，Voyage 的重排序模型没有测试，Cohere 的重排序模型是唯一实测过的。

关于评估本身，文章没有报告评估集的规模、各领域的问题数量、误差棒、统计检验，也没有说明问题与答案是如何构造的（附录 II 只给了每类几个例子）。这些缺失不是作者“承认”的局限，是文章根本没有讨论的部分。

## 五、精读点评

以下这一节是分析者的判断，与上面按文章原意呈现的内容分开。上面的部分讲的是这篇东西做了什么、发现了什么、自己怎么说；这一节讲的是分析者认为它在科学上到底回答了什么问题，价值在哪里，最弱的地方在哪里。

这篇东西要回答的问题，可以用五个问题讲清楚。反常是：RAG 系统明明存着答案，却因为切块把“哪家公司、哪个季度”这类标识信息切掉了，检索不到——知识在库里，系统却找不到。它重要，是因为这个问题堵在所有大知识库 RAG 系统的入口处：检索失败了，下游生成再强也没用；而且它是一个纯工程问题，不需要新模型，只需要改预处理。之前没解决，不是因为没人想到“给块加上下文”——文章自己就列了三种先行做法（通用文档摘要、假设文档嵌入、基于摘要的索引），说它们收益有限或表现较差——而是因为没人把“让模型给每个块写一段定位说明”这件事做到便宜：逐块调模型写上下文，在没有提示词缓存的时候成本太高。这篇文章的办法恰好绕过了这个 blocker：提示词缓存让整篇文档只加载一次，逐块生成上下文的边际成本就只剩每个块那 50–100 token。答案改变的是实践：RAG 的预处理流程里多了一个便宜的步骤，检索失败率在自家基准上大约减半。

这篇东西的价值可以分四句话说。认知上，它没有推翻或确认任何科学信念——它本来就不是一个科学主张，而是一个工程配方；它确认的只是一个直觉：块缺了上下文，补上就有用。方法上，它留下了一个可以直接拿走的配方：Claude 3 Haiku 写 50–100 token 的定位上下文，prepend 到块前，同时进嵌入索引与 BM25 索引，再用排序融合与重排序收尾；这个配方后来被广泛复用，这是它真正的持久价值。边界上，它明确不证明这个做法在任何知识库、任何嵌入模型、任何查询类型上都有效——数字只来自四个自家领域、一个自家构造的评估集、最好的那个嵌入配置的平均值；读者最容易误读的推论是把“失败率降低 49%”读成“RAG 准确率提高 49%”，两者不是一回事。启示上，它指向了一个最便宜的决定性实验：在公开基准上重跑同一套配方，看 49% 的降幅还剩多少。

最弱的地方是评估本身。四个数字里只有一个是绝对值（5.7% 的基线失败率），三个降幅全是相对数，而基线本身就很低：5.7% 降到 2.9%，绝对降幅只有 2.8 个百分点。更重要的是，评估集是 Anthropic 自己构造的，问题与答案的构造方式没有说明，样本量没有报告，误差棒没有，分项数字只在图里。读者无法判断 5.7% 这个基线在别的评估集上是不是 15% 还是 2%，也无法判断 35%、49%、67% 这三个降幅里有多少来自“上下文”本身、有多少来自评估集恰好对上下文敏感。文章还说“在每一个嵌入模型与数据源组合上都有提升”，但这个全称判断的证据只在附录的图里，正文没有给任何一个分项数字。

如果用效度来打分，内部效度在它自己的设置内说不清楚：没有对照实验的细节，没有随机化与重复的概念，没有统计检验，三个降幅的计算方式（平均值的相对变化）本身没问题，但没有不确定性估计。外部效度低：四个领域都是 Anthropic 自己选的，问题是自家构造的，嵌入配置只报告了最好的那一个，生成上下文的模型只有一个（Claude 3 Haiku），重排序模型只有一个实测过的（Cohere）。构念效度处在中间：指标定义很干净——1 减去 recall@20，就是“前 20 个块里没找到相关文档的比例”——但这个指标量的是检索步骤，不是最终回答的质量；文章没有报告下游生成质量有没有跟着变好，“检索失败率降低”与“回答变好”之间隔了一步，没有数据。标题里“dramatically improves”这个说法，量的是检索失败率的相对降幅，不是回答质量。

可复现性比较低：方法描述确实简单到可以照着做，cookbook 也公开了；但评估集没有公开，问题构造方式没有说明，各领域样本量没有报告，附录的分项数字只在图里。一个能干的读者可以复现这个方法的思路，但复现不出 5.7% → 2.9% 这组数字。

什么能加强这篇东西，什么能打破它，答案是同一个实验：在公开的检索基准上重跑上下文检索。具体做法是，取一个公开的 RAG 评估集（例如有标准问题与标准答案的集合），按文章的配方生成上下文，用同样的 recall@20 指标报告基线与上下文检索的失败率，并给出样本量与置信区间。如果降幅仍然接近 49%，“给块加上下文大幅降低检索失败”这个主张就大幅加强；如果降幅缩到几个百分点甚至消失，那就说明标题数字主要是自家评估集的人工产物，教训就从“上下文检索很有效”变成“自家基准上的数字不能外推”。在那之前，一个更便宜的中间步骤是：把附录里的分项数字写成文字表——这些数字已经跑出来了，只是现在只存在于图里。

## I. 结论、结果与价值总览

**一句话结论：**给每个文本块加一段模型生成的定位上下文，能把自家基准上的 top-20 检索失败率从 5.7% 降到 2.9%（再加 BM25 与重排序后到 1.9%），但这是一篇没有同行评审、没有公开评估集的工程博客，数字能不能外推完全没有证据。

**核心结论。**第一，上下文嵌入降低检索失败率，置信度中。证据是标题数字：在最好的嵌入配置（Gemini Text 004）下，所有领域平均的 top-20 失败率从 5.7% 降到 3.7%，相对减少 35%。但评估集是自家构造的，样本量与误差棒均未报告，所以置信度只能给中。

第二，上下文嵌入加上下文 BM25 再降一档，置信度中。证据是失败率进一步降到 2.9%，相对减少 49%。同样的评估集限制适用，置信度给中。

第三，再加 Cohere 重排序，失败率降到 1.9%，相对减少 67%，置信度中。证据是正文明确给出的数字；限制是重排序模型只实测了 Cohere 一家，Voyage 的未测。

第四，这个做法部署成本低，置信度低。证据是每百万文档 token 1.02 美元的一次性成本估算，但这是一个依赖一组假设条件的算术结果，不是实测账单，而且只覆盖生成上下文的一步，不包括嵌入、索引与重排序的成本。

第五，知识库小于 200,000 token 时不需要 RAG，置信度中。这是文章明确给出的设计建议，有提示词缓存的延迟与成本数字作支撑，但那两个数字（延迟降低 2 倍以上、成本降低最高 90%）没有给出测量条件。

**关键结果。**基线 top-20 检索失败率 5.7%（Gemini Text 004，取前 20 个块，所有领域平均）。上下文嵌入：3.7%，相对减少 35%。上下文嵌入加上下文 BM25：2.9%，相对减少 49%。再加 Cohere 重排序（前 150 个重排取前 20 个）：1.9%，相对减少 67%。成本估算：每百万文档 token 1.02 美元（800 token 块、8k token 文档、50 token 指令、每块 100 token 上下文、提示词缓存）。直接放进提示词的阈值：200,000 token（约 500 页）。分项数字（各领域、各嵌入模型、@10 与 @5、NDCG）只在附录图与表图片里，未核实，不在此列。

**科学价值总评。**这篇东西值得被记住为一个工程配方：“切块丢上下文，就让模型给每个块写一段 50–100 token 的定位说明，再同时进嵌入与 BM25 索引。”它不值得被记住为一个科学发现：它没有提出可证伪的假说，没有对照实验，没有不确定性估计，也没有公开的评估集。它的持久贡献是方法论与产品性的：一个简单、便宜、可直接部署的预处理步骤，以及一个被广泛复用的做法。即使 49% 这个数字将来被证明夸大了，配方本身作为工程实践仍然有用。

**适用边界。**不要引用这篇论证“上下文检索在一般 RAG 任务上把失败率降低一半”或“RAG 准确率提高 49%”——数字只来自四个自家领域、一个自家构造的评估集、最好的那个嵌入配置的平均值，而且量的是检索失败率的相对降幅，不是回答质量。不要把附录图与表图片里的分项数字、NDCG 结果当作已确立的数字，它们只存在于图中。不要把每百万 token 1.02 美元当作实测成本，它是一组假设下的估算。不要把“Gemini 与 Voyage 最好”当作逐项已确立的排名，各模型的数字没有以文字形式给出。
