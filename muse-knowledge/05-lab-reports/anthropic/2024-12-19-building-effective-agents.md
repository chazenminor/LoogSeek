## 一、背景与问题

### 这篇东西从哪里来

过去一年里，Anthropic 与几十个不同行业的团队合作，帮他们搭建基于大语言模型的智能体。作者观察到一个反复出现的现象：最成功的实现，用的不是复杂的框架或专门的库，而是简单、可组合的模式。

这个观察就是全文的出发点。作者要做的事很直接：把这些年从客户合作与自己搭建中学到的东西写下来，给开发者一份关于如何搭建高效智能体的实用建议。

### 它要回答的问题

问题可以说成一句话：搭建智能体系统时，什么时候该用什么结构，以及怎样才算“高效”？

文章先把问题拆开。第一，“智能体”（agent）这个词本身就含糊：有的客户用它指完全自主、长期独立运行的系统，有的客户用它指按预定流程走的工作流。作者把这两类都归为“agentic systems”（智能体系统），但坚持要区分两种架构：工作流（workflows）与智能体（agents）。

第二，复杂不是免费的。智能体系统常常拿延迟和成本换任务表现，所以要先想清楚这笔交易划不划算。很多时候，根本不需要智能体系统。

第三，即使决定要建，框架也可能帮倒忙。框架简化了调用模型、定义工具、串联调用这些底层工作，但多出来的抽象层会遮住底层的提示词与响应，让调试变难，还会诱使人加上本不需要的复杂性。

## 二、方法与设计

### 这篇东西没有实验

先说清楚一点：这不是一篇有方法与设计的研究。它没有研究问题、没有对照、没有指标、没有样本。它的“方法”就是作者的经验总结：与几十个团队合作的观察，加上 Anthropic 自己搭建智能体的经验。

所以这一节只能按文章自己的顺序，把它给出的分类与建议如实讲出来，而不是按实验论文的套路去套它。

### 定义：工作流与智能体

作者给出的区分很简单。工作流是“大语言模型与工具通过预定义的代码路径编排起来的系统”。智能体是“大语言模型动态地指挥自己的流程与工具使用、自己掌控如何完成任务的系统”。

这个区分是全文的骨架。后面所有的模式，都是沿着“预定义”与“动态决定”这条线排开的。

### 什么时候用、什么时候不用

作者的建议是：先找最简单的解法，只在必要时才增加复杂性。这可能意味着根本不建智能体系统。

智能体系统拿延迟和成本换更好的任务表现，要先判断这笔交易是否值得。复杂性有道理的时候，工作流适合定义清晰的任务，因为它可预测、一致；智能体适合需要在规模上灵活决策的场合。但对很多应用来说，只优化单次大语言模型调用，加上检索与上下文示例，就已经够了。

### 框架：先直接用 API

作者列了几个框架，但紧接着就泼了冷水。框架让上手变容易，却也容易遮住底层、诱使人加复杂。作者的建议是：先直接用大语言模型 API，很多模式几行代码就能实现；如果确实要用框架，一定要理解它底层的代码，因为对底层机制的错误假设，是客户常犯的错误来源。

### 从简单到复杂的模式谱

文章的主体部分按复杂度递增，介绍了一个基础构件与五种工作流，最后讲到自主智能体。

基础构件是“增强型大语言模型”（augmented LLM）：一个配上了检索、工具、记忆等能力的模型。现在的模型能主动用这些能力，自己生成搜索查询、选择合适的工具、决定保留什么信息。作者建议把精力放在两件事上：按具体用例定制这些能力，并且给模型一个简单、文档齐全的接口。文中提到的一个实现方式是模型上下文协议（Model Context Protocol，MCP），它让开发者能用简单的客户端实现接入第三方工具的生态。文章其余部分默认每次大语言模型调用都能用到这些增强能力。

五种工作流依次是：提示词链（prompt chaining）、路由（routing）、并行化（parallelization）、编排器-工作器（orchestrator-workers）、评估器-优化器（evaluator-optimizer）。自主智能体（agents）放在最后，作为复杂度最高的一端。

## 三、主要发现

### 五种工作流

提示词链把任务拆成一串步骤，每次大语言模型调用处理上一次调用的输出。中间步骤可以加程序化的检查（文中的图里标为“gate”，关卡），确保过程还在正轨上。它适合任务能干净地拆成固定子任务的场合，主要目的就是拿延迟换更高的准确率，让每一次调用都变成更容易的任务。例子是先生成营销文案、再翻译成另一种语言；或者先写文档大纲、检查大纲是否符合标准，再按大纲写文档。

路由先对输入分类，再把它导向专门的后续任务。这样可以把关注点分开，给不同类别写更专门的提示词。不用路由的话，为一类输入优化提示词，可能会损害其他输入的表现。它适合任务有明确的不同类别、且分类能被准确处理的情况，分类可以由大语言模型做，也可以用传统的分类模型或算法。例子是把客服查询按类型分流——一般问题、退款请求、技术支持——各自走不同的下游流程与工具；或者把简单常见的问题交给更小、更便宜的模型，把难的、不常见的问题交给更强的模型，以兼顾性能与成本。

并行化让大语言模型同时处理一个任务，再用程序把输出聚合起来。它有两种变体。分段（sectioning）是把任务拆成相互独立的子任务并行跑；投票（voting）是把同一个任务跑多次，得到多样化的输出。它适合子任务能并行提速、或者需要多个视角以提高置信度的场合。对复杂的任务，把每个考虑因素交给一次单独的调用来处理，通常比让一次调用同时处理所有因素效果更好，因为每次调用的注意力更集中。分段的例子是：一个模型实例处理用户查询，另一个同时筛查不当内容或请求，这比让同一次调用既做防护又做核心回答效果更好；另一个例子是自动化评估，每次调用评估模型在某个提示上表现的不同方面。投票的例子是：用几个不同的提示审查一段代码的漏洞，只要有提示发现问题就标记；或者用多个提示评估一段内容是否不当，用不同的投票阈值来平衡误报与漏报。

编排器-工作器是中心大语言模型动态拆解任务、分派给工作器大语言模型、再综合结果。它适合无法预先知道需要哪些子任务的复杂任务，比如写代码时，要改哪些文件、每个文件怎么改，都取决于具体任务。它与并行化在形状上相似，关键区别是灵活性：子任务不是预先定好的，而是编排器根据具体输入决定的。例子是每次都要对多个文件做复杂改动的代码产品，以及需要从多个来源收集、分析相关信息的搜索任务。

评估器-优化器是一个大语言模型调用生成回答，另一个提供评估与反馈，循环往复。它特别适合有明确评估标准、且迭代改进能带来可衡量价值的场合。作者给出两个判断是否合适的信号：第一，当人把反馈说清楚时，大语言模型的回答能被证明有所改进；第二，大语言模型本身能提供这种反馈。这与人类作者反复修改、打磨文章的过程类似。例子是文学翻译，翻译模型一开始可能抓不住细微差别，但评估模型能给出有用的批评；以及需要多轮搜索与分析才能收集足够信息的复杂搜索任务，由评估器决定是否还需要继续搜索。

### 自主智能体

随着大语言模型在理解复杂输入、推理与规划、可靠使用工具、从错误中恢复这些关键能力上的成熟，智能体开始在生产中出现。智能体从人类的指令或与人类的互动讨论开始工作。任务明确后，它独立规划与执行，过程中可能回来向人类索取更多信息或判断。执行中，智能体要在每一步从环境中获取“地面实况”（ground truth），比如工具调用结果或代码执行结果，以评估自己的进展。智能体可以在检查点暂停，等待人类反馈，或者在遇到阻碍时停下来。任务常常在完成时终止，但也常见设置停止条件，比如最大迭代次数，以保持控制。

作者强调，智能体能处理复杂的任务，但实现往往很直接：通常就是大语言模型根据环境反馈循环使用工具。因此，工具集的设计与文档必须清晰、深思熟虑，附录二专门讲这一点。

什么时候用智能体：适合开放式问题，无法预测需要多少步骤、也无法把路径写死；大语言模型可能要跑很多轮，开发者必须对它的决策有一定信任。智能体的自主性让它适合在可信环境中规模化执行任务。

代价也很明确：自主性意味着更高的成本，以及错误可能层层累积的风险。作者建议在沙盒环境里做大量测试，并加上适当的防护措施。

作者给的例子来自 Anthropic 自己的实现：一个解决 SWE-bench 任务的编码智能体，根据任务描述对多个文件做编辑；以及“computer use”（计算机使用）的参考实现，让 Claude 操作计算机完成任务。

### 组合与定制

这些构件不是规定动作，而是开发者可以塑造、组合的常见模式。成功的关键与任何大语言模型功能一样：衡量性能，不断迭代实现。作者再次强调：只有在能证明复杂性确实改善结果时，才加上复杂性。

### 总结：三条核心原则

文章结尾收成三条原则。第一，设计保持简单。第二，优先保证透明度，明确展示智能体的规划步骤。第三，认真打磨智能体与计算机的接口（agent-computer interface，ACI），通过完备的工具文档与测试来实现。

框架能帮人快速上手，但进入生产时，不要犹豫减少抽象层、用基本组件搭建。按这三条原则做，就能做出不仅强大、而且可靠、可维护、值得信任的智能体。

### 附录一：实践中的智能体

附录一讲了客户合作中发现的两个特别有前景的应用。两者都说明，智能体在那些既需要对话、又需要行动，有明确成功标准、能形成反馈循环、并且有意义的人类监督的任务上，价值最大。

客服支持结合了熟悉的聊天机器人界面与工具集成能力。它天然适合更开放的智能体，因为支持对话本来就是对话流，又需要访问外部信息与执行操作；工具可以拉取客户数据、订单历史与知识库文章；退款、更新工单这类操作可以程序化处理；成功与否可以用用户定义的解决结果来衡量。已经有公司用按成功解决次数收费的定价模式，显示出对自家智能体的信心。

编码智能体是另一个。软件开发领域的大语言模型能力已经从代码补全发展到自主解决问题。智能体特别有效，因为代码方案可以通过自动化测试验证；智能体能用测试结果作为反馈来迭代；问题空间定义清晰、结构良好；输出质量可以客观衡量。Anthropic 自己的实现现在能仅凭 pull request（拉取请求）的描述，解决 SWE-bench Verified 基准里的真实 GitHub 问题。不过作者也提醒，自动化测试能验证功能，但人类评审对确保方案符合更广泛的系统需求仍然至关重要。

### 附录二：给工具做提示词工程

无论建什么样的智能体系统，工具都很可能是重要组成部分。工具让 Claude 通过在 API 里指定工具的确切结构与定义，来与外部服务和 API 交互；当 Claude 计划调用工具时，会在 API 响应里包含一个工具使用块（tool use block）。工具的定义与规格，值得与整体提示词同等的提示词工程关注。

同一个动作常常有几种表达方式。比如文件编辑可以写 diff（差异），也可以重写整个文件；结构化输出可以把代码放在 markdown 里，也可以放在 JSON 里。在软件工程里，这些差别只是表面形式，可以无损转换。但对大语言模型来说，有些格式写起来要难得多：写 diff 需要在写新代码之前，就在块头里算好有多少行在变化；把代码写进 JSON 里（相比 markdown）需要对换行与引号做额外的转义。

作者给出三条选择工具格式的建议：给模型足够的 token 去“思考”，别让它还没想清楚就把自己写进死角；格式尽量接近模型在互联网文本里自然见过的样子；确保没有格式上的额外负担，比如不用准确数几千行代码，也不用对代码做字符串转义。

经验法则是：想想人们在人机界面（human-computer interface，HCI）上花了多少精力，就在智能体-计算机界面（ACI）上投入同样的精力。具体做法有：站在模型的角度想问题——只看工具描述与参数，这个工具的用法是否一目了然，还是需要仔细琢磨？如果需要仔细琢磨，模型大概率也一样。一个好的工具定义通常包括示例用法、边界情况、输入格式要求，以及与其他工具的明确界限。能不能改参数名或描述，让用法更明显？这相当于给团队里的初级开发者写一份出色的 docstring（文档字符串），在工具有很多相似项时尤其重要。测试模型怎么用工具：在工作台（workbench）里跑很多示例输入，看模型犯什么错，再迭代。用防错（poka-yoke）设计工具：改参数，让犯错变得更难。

作者还给了一个自己的例子。在搭建 SWE-bench 智能体时，他们花在优化工具上的时间，比花在优化整体提示词上的时间还多。比如他们发现，模型在用相对文件路径的工具时，智能体一旦离开根目录就会出错。修复办法是把工具改成始终要求绝对文件路径——改完之后，模型使用这个方法再也没有出过错。

## 四、作者的结论与局限

### 作者自己得出的结论

作者的结论就是那三条原则加上“先简单”的总纲：成功不在于建最复杂的系统，而在于为需求建“合适的”系统。从简单的提示词开始，用全面的评估去优化，只在更简单的方案不够用时才加上多步智能体系统。设计保持简单，规划步骤透明，工具接口要像人机界面一样认真打磨。

作者没有声称这些模式经过了实验验证。全文的语气是“我们学到了什么、我们建议你怎么做”，而不是“我们证明了什么”。这一点要如实记下来：它的结论是建议，不是发现。

### 作者承认的局限

这篇东西没有“局限”一节，作者也没有系统地列出自己方法的不足。但有几处保留意见是作者自己写明的。

第一，智能体拿延迟与成本换任务表现，这个交易不是在所有场合都划算。作者把这一点放在开头，作为要不要建智能体系统的前提。

第二，智能体的自主性带来错误累积的风险，作者明确建议在沙盒环境里大量测试、加上防护措施。这等于承认：按他的方法建出来的系统，在没有这些防护时是不可靠的。

第三，自动化测试能验证代码功能，但人类评审对确保方案符合更广泛的系统需求仍然至关重要。这是对编码智能体那一节的直接保留：测试通过不等于方案是对的。

第四，框架会遮住底层、诱使人加复杂。这是对“用框架上手”这个建议本身的保留，作者的补救办法是“理解底层代码”，但他没有给出怎么验证自己理解得对不对。

除此之外，作者没有承认更多。比如他没有讨论自己的经验样本可能有什么偏差，也没有讨论这些模式在不同模型、不同任务上的适用边界。

## 五、精读点评

以下这一节是分析者的判断，与上面按论文原意呈现的内容分开。上面的部分讲的是这篇东西说了什么、建议了什么；这一节讲的是分析者认为它在科学上到底回答了什么问题，价值在哪里，最弱的地方在哪里。

这篇东西要回答的科学问题，可以用五个问题讲清楚。反常是：2024 年前后，智能体框架与自主智能体概念爆发式增长，开发者面对一堆新名词与新框架，不知道该怎么选；与此同时，Anthropic 在客户合作里反复看到，复杂框架搭出来的系统反而不如简单模式好用。这个反差逼出了问题：到底什么结构才真正管用？它重要，是因为选错结构要付真金白银的代价——延迟、成本、调试时间，以及错误在自主循环里累积；对领域来说，它关系到“智能体”这个词会不会被框架营销掏空；对实践来说，它直接决定开发者第一行代码该怎么写。之前做不了，是因为没有人系统地把生产中的做法收拢成一份分类：学术界研究的是单个模型的能力，工业界的经验散落在各个团队的内部复盘里，没有公开的、可对照的模式语言；blocker 是“经验没有被整理成可复用的分类”，而不是缺数据或缺算力。这篇工作的办法是凭作者自己的合作经验，把做法按复杂度排成一条谱：从增强型大语言模型，到五种工作流，再到自主智能体。这个办法能回答“该怎么选”的问题，是因为它给了开发者一个决策顺序：先单次调用，再工作流，最后才是智能体，每一步都有明确的适用条件。答案改变的是：它给了行业一套共享词汇——提示词链、路由、并行化、编排器-工作器、评估器-优化器、工作流与智能体的区分——这套词后来成了讨论智能体设计的默认语言。至于“哪种结构在哪种任务上真的更好”，它没有回答，那需要对照实验，而这篇东西一篇实验也没做。

这篇东西的价值可以分四句话说。认知上，它没有确立任何新的事实性主张——它确认的只是一个分类：预定义路径与动态决策这条区分线，以及五种工作流的划分。证据就是文章本身的文字，没有数字可以复核；反事实是，如果这篇不存在，行业迟早也会从别的渠道长出类似的词汇，但 Anthropic 这篇的版本成了最广为引用的那一个。方法上，它留下的可复用东西就是这套模式语言与三条原则，外加附录二里关于工具格式的几条具体建议（给足思考 token、格式贴近自然文本、去掉计数与转义负担、用防错设计）。这些建议不需要新实验就能拿走用，这是全文最实在的产出。边界上，它明确不证明任何一种模式在效果上优于另一种，也不证明“简单总是更好”——作者自己的话是“只有在能证明复杂性确实改善结果时，才加上复杂性”，这句话本身就把举证责任推给了读者，而不是由这篇文章来承担。启示上，它指向了一个最便宜的决定性实验：在同一个任务、同一套评估上，把单次调用、提示词链与自主智能体三者并排跑一遍，看成功率、延迟与成本各是多少；如果简单方案赢了，“先简单”就得到了它一直缺的那份证据，如果智能体明显赢了，这篇建议的适用边界就被画出来了。

最弱的地方是，全部建议都建立在没有公开的经验上。作者说“与几十个团队合作”，但没有说这些团队是谁、任务是什么、成功与失败各占多少、简单模式赢过复杂模式的具体案例是哪几个。没有这些信息，读者无法判断这套建议是来自几十次成功，还是一两次印象深刻的成功加上很多没提的失败。更具体地说，文章里每一条“什么时候用”的判断——比如“提示词链适合能干净拆分的任务”“并行化比单次调用效果更好”——都没有给出任何比较数据。它们读起来像真理，实际上是未经检验的断言。还有一个薄弱点：文章把“简单”同时当作手段与目的在用。一方面说简单是好的设计原则，另一方面又说只有证明复杂性改善结果时才加复杂——这两句话合起来其实没有给出可操作的判据：改善多少才算“证明”？成本与延迟的权重怎么算？文章没有回答。

如果用效度来打分，内部效度不适用：没有实验、没有对照、没有度量，就没有内部效度可言；硬要打分的话，只能给最低档，因为任何一条因果主张（比如“并行化效果更好”）在文章里都没有对照支撑。外部效度同样无法评估：经验来自 Anthropic 自己的客户群，文章没有描述这个样本的构成，也就不知道它能推广到哪些任务、哪些模型、哪些组织。构念效度处在中间：低层面的定义很干净，工作流与智能体的区分、五种工作流的划分，定义清晰、互相不重叠；但高层面的构念——“高效”（effective）——从来没有被操作化：高效是指成功率高、延迟低、成本低，还是可维护？文章在不同地方用的是不同的意思。统计结论效度不适用：全文没有一个数字，没有统计可言。

可复现性是低的：这不是一篇可以重跑的东西。读者可以照着模式自己搭系统，但无法复现作者的结论，因为作者的结论来自没有公开的客户合作经验。唯一可复核的部分是附录二的工具格式建议——相对路径改绝对路径这个例子，读者可以在自己的智能体上试一试，看是不是真的不再出错；但原文连样本量与出错定义都没给，所以连这个小例子也无法严格复核。

## 六、证伪器、替代解释与接下来看什么（§H）

### 证伪器

这篇东西的主要主张大多是规范性的建议，不是可证伪的事实主张。能写出证伪器的有以下几条。

主张“先用最简单的解法，只在必要时加复杂”：在同一任务、同一评估集上，比较单次调用、提示词链与自主智能体三者的成功率、延迟与成本。如果自主智能体在成功率上明显高于单次调用，且多花的延迟与成本在可接受范围内，那么“先简单”作为默认策略就是错的——至少在这个任务类别上是错的。

主张“并行化比让一次调用同时处理所有因素效果更好”：在同一个复杂任务上，比较一次调用处理全部因素与多次调用各处理一个因素的输出质量。如果单次调用的质量等于或高于并行化，这个主张即被证伪。

主张“框架会遮住底层、诱使人加复杂”：找一组用框架搭建的智能体与一组直接用 API 搭建的、任务相同的智能体，比较两组的调试时间与不必要的复杂性（比如多余的调用次数）。如果框架组并不更难调试、也不更多余，这个主张即被证伪。

主张“工具格式越贴近自然文本，模型用起来越不容易错”：在同一个工具上比较两种格式（比如 diff 与重写整个文件）的调用成功率。如果更贴近自然文本的格式反而错误更多，这个主张即被证伪。

其余主张，比如“设计保持简单”“规划步骤要透明”，是设计价值观，不是事实主张，写不出证伪器，记为不可证伪。

### 替代解释

第一个替代解释是选择偏差。Anthropic 合作的团队，是那些已经选择用 Claude、并且愿意与 Anthropic 合作的团队；他们遇到的问题、他们的任务类型，可能本来就更适合简单模式。那些需要复杂框架才能解决的问题，可能根本不在作者的视野里——不是因为简单模式赢了，而是因为复杂问题没来找 Anthropic。区分办法：看这套建议在 Anthropic 客户群之外的任务上是否同样成立，比如开源社区里用其他模型搭建的智能体项目。

第二个替代解释是模型能力，而不是模式本身。2024 年底的 Claude 模型在工具使用与按指令行事上已经很强，简单模式能跑通，可能只是因为模型够强，而不是因为模式本身好。换一个工具使用能力弱的模型，同样的简单模式可能处处碰壁，反而需要框架提供的结构来兜底。区分办法：在不同能力的模型上跑同一套模式，看“简单模式够用”这个结论是否随模型能力变化。

第三个替代解释是，文章的流行程度来自它的清晰与时机，而不是它的正确性。2024 年底正是智能体概念最混乱的时候，一篇把概念收拾干净、给出清晰词汇的文章，天然容易被引用与传播。它的影响力可能反映的是行业对一套共享语言的需求，而不是这些建议本身经过了验证。区分办法：看后续的对照实验是否支持它的具体主张，而不是看它被引用了多少次。

### 作者自述局限 vs 分析者发现的局限

作者自己承认的局限只有四处，都是散落在正文里的保留意见：智能体拿延迟与成本换表现，不总是划算；自主性带来错误累积，需要沙盒测试与防护；自动化测试能验证功能，但人类评审仍然至关重要；框架会遮住底层、诱使人加复杂。

分析者发现的、作者没说的局限更根本。第一，全部建议建立在没有公开的经验样本上：团队是谁、任务是什么、成功与失败的比例，全部未报告。第二，没有一条主张有对照证据：所有的“什么时候用”判断都是断言，不是比较的结果。第三，“高效”这个核心词没有被定义，成功率、延迟、成本、可维护性在不同地方被混着用。第四，页面是更新过的版本，框架与模型名已被改写，读者无法确定 2024 年原文的建议在今天是否还适用——而文章顶部那条更新说明，恰恰承认了工具格局已经变了。第五，文章没有讨论它的建议在什么条件下会失效，比如模型能力变化、任务类型变化、组织规模变化。

### 接下来看什么

排第一的是最便宜的决定性实验：选一个有明确成功标准的真实任务——比如附录一里的客服支持，用“用户定义的解决结果”作指标——搭三个版本：单次调用加检索、提示词链工作流、自主智能体。在同一套评估集上跑，记录成功率、延迟与成本。判据是：如果自主智能体在成功率上没有比单次调用高出一个值得付延迟与成本代价的幅度，“先简单”就得到了它一直缺的证据；如果它明显赢了，这篇建议的适用边界就被画出来了。这个实验便宜，因为它不需要新模型、新数据，只需要把文章自己的建议当作待检验的假设去跑一遍。

其次值得看的是附录二的工具格式建议能不能复现：拿相对路径与绝对路径那个例子，在自己的编码智能体上重跑，记录两种格式下的工具调用错误率与样本量。原文没有给数字，补上这个数字不需要新实验，只需要把已经跑过的结果写清楚。

再往后看的是 Anthropic 后来关于 Managed Agents 的新文章（页面顶部已经指向了它），看作者自己在两年后有没有修正这篇的建议——特别是框架一节，原文说“先直接用 API”，新文章是否还这么说，是判断这篇建议有没有过期的最直接办法。

### 未解问题

这篇东西没有回答、也无法从文中确定的有：简单模式在哪些任务类别上真的优于复杂模式，边界在哪里；五种工作流各自的适用条件有没有可量化的判据，还是只能凭经验判断；“高效”到底指什么，成功率、延迟、成本三者出现冲突时怎么取舍；附录一里 SWE-bench Verified 的实际解决率是多少；附录二里绝对路径改动前后的工具调用错误率各是多少；2024 年原文与现在页面上的版本之间，除了框架与模型名之外，还改过哪些句子。回答这些问题需要的材料，分别是：对照实验结果、明确的评估指标与权重、原文的存档版本，以及作者公开的客户合作案例细节。

## I. 结论、结果与价值总览

**一句话结论：**这是一篇没有实验、没有数字的工程经验帖，它凭与几十个团队合作的观察，给出了“先简单、再按需加复杂”的决策顺序与五种工作流加一种自主智能体的模式语言；作为实践建议它清晰有用，作为研究结论它没有任何证据支撑——读者应当把它当作经验之谈，而不是经过验证的发现。

**核心结论。**第一，这篇东西确立了一套模式语言，置信度高。证据是文章本身：工作流与智能体的区分、五种工作流的划分、三条原则，定义清晰、文字完整；但这只是“文章写了什么”，不是“世界是什么样”。

第二，这篇东西没有确立任何一条关于效果的事实主张，置信度高。证据是数字台账：全文没有一个可核查的数字，SWE-bench 的解决率、工具改动的错误率、合作团队的数量，全部没有报告或只有模糊说法。

第三，这篇东西的建议在实践上仍然有用，置信度中。证据是附录二的工具格式建议具体、可操作，而且与“站在模型的角度想问题”这个思路是一致的；但“有用”这个判断来自分析者的阅读，不是来自对照实验，所以只能给中。

第四，这篇东西读到的版本不是 2024 年的原文，置信度高。证据是页面顶部的更新说明与 2026-10-09 的最后更新时间，以及框架与模型名明显是后来改过的。

**关键结果。**全文没有关键结果，因为没有数字。唯一能写进来的，是四条“无可用数字”的记录：合作团队的数量只说了“几十个”，没有确切数字；SWE-bench Verified 的解决率没有给；工具改绝对路径前后的错误率没有给；工具优化与提示词优化的时间分配没有给。附录二的定性观察是：模型在用相对路径的工具时，智能体离开根目录后会出错，改成绝对路径后不再出错——但这句话没有样本量与错误定义，不能当作数字。
