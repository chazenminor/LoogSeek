## 一、背景与问题

### 这篇东西要解决什么问题

Claude Code 是 Anthropic 发布的命令行智能体编码工具。它有意设计得低层级、不带倾向性（low-level and unopinionated），给用户接近原始模型的访问能力，而不强制特定的工作流。这种设计让它灵活、可定制、可脚本化，但对刚接触智能体编码工具的工程师来说，学习曲线是存在的——至少在他们形成自己的最佳实践之前是这样。

这篇博客的定位就是把“已经证明有效”的通用模式写下来：既包括 Anthropic 内部团队的经验，也包括外部工程师在各种代码库、语言与环境里的经验。博客开篇就声明：清单里的内容没有一条是定规，也没有一条普遍适用，都只是起点，鼓励读者自己试验、找到最适合自己的做法。

### 这篇要回答的问题

这篇东西没有科学问题，它要回答的是一个实践问题：怎么用好 Claude Code？它给出的答案是六组做法：定制设置、多给工具、试几种常见工作流、优化工作流、用 headless 模式做自动化、用多 Claude 实例并行。

## 二、方法与设计

这篇博客没有实验设计。它的方法是经验总结：把内部团队与外部用户已经在用的做法整理出来。没有任何对照、没有任何测量、没有任何评估指标。以下按博客自己的六节结构呈现。

### 1. 定制设置（Customize your setup）

- 写 `CLAUDE.md` 文件：Claude 启动会话时会自动把它拉进上下文，适合写常用 bash 命令、核心文件与工具函数、代码风格、测试指令、仓库规矩（例如分支命名、merge 还是 rebase）、开发环境配置、项目特有的意外行为与警告。`CLAUDE.md` 可以放在仓库根目录（建议用 `CLAUDE.md` 入 git 共享，或 `CLAUDE.local.md` 加进 `.gitignore`）、运行目录的任何父目录（monorepo 有用）、任何子目录（按需拉取），或 home 目录（`~/.claude/CLAUDE.md`，对所有会话生效）。运行 `/init` 命令可以让 Claude 自动生成一份。
- 调优 `CLAUDE.md`：它会成为提示的一部分，应该像常用提示一样迭代优化。常见错误是加了大量内容却不验证效果。按 `#` 键可以给 Claude 一条指令，让它自动写进相关的 `CLAUDE.md`。Anthropic 内部有时会把 `CLAUDE.md` 过一遍提示改进器（prompt improver），并通过加 emphasis（例如 "IMPORTANT" 或 "YOU MUST"）来提高指令遵循度。
- 管理工具白名单：默认情况下，Claude Code 对可能修改系统的操作（写文件、很多 bash 命令、MCP 工具）都会请求许可。可以通过四种方式管理：会话里选 "Always allow"、用 `/permissions` 命令、手动编辑 `.claude/settings.json` 或 `~/.claude.json`、用 `--allowedTools` 命令行参数。
- 如果用 GitHub，装 `gh` CLI：Claude 懂得用它来创建 issue、开 PR、读评论。不装也能用 GitHub API 或 MCP 服务器。

### 2. 多给 Claude 工具（Give Claude more tools）

- 用 bash 工具：Claude Code 继承用户的 shell 环境，可以用自定义的 bash 工具——告诉它工具名与用法示例、让它跑 `--help` 看文档、把常用工具写进 `CLAUDE.md`。
- 用 MCP：Claude Code 既是 MCP 服务器也是客户端。作为客户端，它可以通过项目配置、全局配置或签入的 `.mcp.json` 文件连接任意数量的 MCP 服务器。`--mcp-debug` 参数可以帮助排查配置问题。
- 用自定义斜杠命令：把重复工作流（调试循环、日志分析）的提示模板存成 `.claude/commands` 文件夹里的 Markdown 文件，输入 `/` 时就能从菜单里调用，可以用 `$ARGUMENTS` 传参；也可以放进 `~/.claude/commands` 作为个人命令。

### 3. 常见工作流（Try common workflows）

- 探索、计划、写代码、提交：先让 Claude 读相关文件、图片或 URL（明确告诉它先别写代码），再让它做计划（建议用 "think" 这个词触发扩展思考模式；"think" < "think hard" < "think harder" < "ultrathink" 对应递增的思考预算），然后实现，最后提交并开 PR。博客强调，前两步很关键——不先研究与计划，Claude 倾向于直接跳去写代码。
- 先写测试、提交；再写代码、迭代、提交：测试驱动开发（TDD）与智能体编码结合。让 Claude 按预期输入输出写测试、跑测试并确认失败、提交测试，再写代码直到测试通过（不要改测试），最后提交代码。给它一个明确的迭代目标（视觉 mock、测试用例或其他输出）效果最好。
- 写代码、截图、迭代：给 Claude 截浏览器图的能力（例如 Puppeteer MCP 服务器、iOS 模拟器 MCP 服务器，或手动粘贴截图），给它视觉 mock，让它实现设计、截图、迭代到与 mock 相符，再提交。通常迭代 2–3 次后结果会明显更好。
- 安全 YOLO 模式（Safe YOLO mode）：用 `claude --dangerously-skip-permissions` 跳过所有权限检查，让 Claude 不间断工作到完成。博客警告说，让 Claude 跑任意命令有风险，可能导致数据丢失、系统损坏甚至数据外泄（例如通过提示注入攻击），建议在没有联网的容器里使用，并给出了一个 Docker Dev Containers 的参考实现。
- 代码库问答：向 Claude 提问，就像问项目里的另一位工程师一样（例如“日志是怎么工作的？”“怎么新增一个 API 端点？”）。在 Anthropic，这已经成为核心的新人 onboarding 工作流。
- 与 git 交互：很多 Anthropic 工程师用 Claude 处理 90% 以上的 git 交互——查 git 历史、写提交信息、处理复杂的 git 操作（回退文件、解决 rebase 冲突、比较与嫁接补丁）。
- 与 GitHub 交互：开 PR（一句 "pr" 它就懂）、一键修复简单的代码评审意见、修失败的构建或 linter 警告、分类与分流 open issues。
- 与 Jupyter notebook 交互：Anthropic 的研究员与数据科学家用 Claude Code 读写 notebook，Claude 能解读输出（包括图片）。建议把 Claude Code 与 `.ipynb` 文件并排开在 VS Code 里。

### 4. 优化工作流（Optimize your workflow）

- 指令要具体：越具体的指令，首次尝试的成功率越高，事后纠正越少。
- 给 Claude 图片：粘贴截图、拖放图片、给图片文件路径；对 UI 设计稿、视觉图表特别有用。
- 指明要看的文件：用 tab 补全快速引用仓库里的文件或文件夹。
- 给 Claude URL：把具体的 URL 和提示一起贴进去；对常用域名可以用 `/permissions` 加进白名单，避免重复问许可。
- 尽早并经常纠正方向：自动接受模式（shift+tab 切换）可以让 Claude 自主工作，但主动协作、引导 Claude 的做法通常效果更好。纠正工具有四种：开始前先让 Claude 做计划、按 Escape 中断、双击 Escape 回到历史记录里改写之前的提示、让 Claude 撤销改动。
- 用 `/clear` 保持上下文聚焦：长会话里上下文会被无关对话、文件内容与命令填满，降低性能甚至分散注意力，任务之间多用 `/clear`。
- 复杂工作流用检查清单与草稿本：让 Claude 用一个 Markdown 文件（甚至 GitHub issue）做检查清单与工作草稿本，例如修大量 lint 错误时，先让它把 lint 命令的全部错误写进清单，再逐条修复、验证、打勾。
- 把数据传给 Claude：直接复制粘贴、管道输入（例如 `cat foo.txt | claude`，适合日志、CSV 与大文件）、让 Claude 用 bash 命令、MCP 工具或自定义斜杠命令拉数据、让 Claude 读文件或抓 URL。

### 5. 用 headless 模式做基础设施自动化（Use headless mode to automate your infra）

Claude Code 有 headless 模式，用于 CI、pre-commit hooks、构建脚本等非交互场景：用 `-p` 参数加提示启用，`--output-format stream-json` 可以输出流式 JSON。注意 headless 模式不在会话之间持久化，每次会话都要重新触发。

博客举了两个例子：用 headless 模式做 issue 分流（GitHub 事件触发时，让 Claude 检查新 issue 并打标签；Claude Code 自己的公开仓库就是这么做的），以及用 Claude 做 linter（发现传统 lint 发现不了的主观代码评审问题，例如拼写错误、过时注释、误导性的函数名或变量名）。

### 6. 多 Claude 工作流（Uplevel with multi-Claude workflows）

- 一个 Claude 写代码，另一个验证：一个写代码，`/clear` 或另开一个终端启动第二个 Claude 来评审或测试，再开一个读代码与评审意见、按意见改代码。写测试与写代码也可以分开。分开上下文往往比单个 Claude 全包效果更好。
- 多个仓库 checkout：开 3–4 个 git checkout，分别放在不同的文件夹与终端标签页里，各跑一个 Claude 做不同的任务，轮流检查进度、批准或拒绝权限请求。
- 用 git worktrees：更轻量的多任务并行方式。每个 worktree 有自己的工作目录、共享同一份 git 历史与 reflog。用 `git worktree add ../project-feature-a feature-a` 创建，`cd` 进去启动 Claude，完成后 `git worktree remove` 清理。
- 用 headless 模式加自定义 harness：`claude -p` 可以编程式地接入更大的工作流。两种主要模式：扇出（fan out，把大迁移或大分析拆成任务列表，循环调用 Claude 处理每个任务）与流水线（pipelining，把 `claude -p "<提示>" --json` 的输出接到流水线的下一步）。`--verbose` 有助于调试，生产环境建议关掉。

## 三、主要发现

这篇博客没有“发现”，只有做法。按它自己的说法，最值得记住的几条是：

- 先探索、再计划、再写代码——跳过前两步是性能下降的主要原因。
- 给 Claude 一个明确的迭代目标（测试、视觉 mock），它才能自我纠正、越改越好。
- 上下文管理是性能的一部分：`/clear`、检查清单、多实例分开上下文，都是为了不让无关内容挤占注意力。
- 权限与安全是显式设计：默认保守，`--dangerously-skip-permissions` 是有意的危险选项，只应在隔离容器里用。

博客没有给出任何一条做法的效果数字。唯一接近数字的说法是“很多 Anthropic 工程师用 Claude 处理 90% 以上的 git 交互”——这是一个内部轶事，没有分母、没有测量方法、没有时间范围，不能当作实证结果引用。
