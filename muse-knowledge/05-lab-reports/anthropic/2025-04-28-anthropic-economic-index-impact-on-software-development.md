## 一、背景与问题

### 为什么要研究软件开发

编程工作在现代经济里只占一小部分，但影响力很大。过去几年里，能协助并自动化大量编码工作的 AI 系统，让这些工作发生了巨大变化。Anthropic 之前的经济指数研究发现，计算机相关职业的美国工人在 Claude 上的使用极不成比例——也就是说，与相关职业的从业人数相比，关于计算机相关任务的对话多得多。教育场景里也一样：涉及大量编码的计算机科学学位，AI 使用高度不成比例。

为了更详细地理解这些变化，团队分析了 50 万次编码相关的对话，覆盖 Claude.ai（大多数人交互 Claude 的“默认”方式）与 Claude Code（新的专业编码 agent，能用多种数字工具独立完成复杂任务链）。

### 这份报告要回答的问题

报告要讲的问题可以说成三句话。第一，开发者是怎么与 Claude 互动的——在多大程度上是让 AI 直接干活（自动化），在多大程度上是与 AI 协作（增强）？第二，开发者在用 Claude 造什么——哪些语言、哪些任务最常见？第三，是哪些人在用 Claude 写代码——初创公司、企业、学生、个人项目，各占多少？

## 二、方法与设计

### 数据与分析工具

团队分析了总共 50 万次 Claude 对话（在 Claude Code 与 Claude.ai 之间分配），用的是隐私保护分析工具 Clio（博客链接到 Clio 的介绍）。这个工具把用户对话提炼成更高层次的、匿名的洞见。在这里，它被用来识别对话的主题（例如“UI/UX 组件开发”），以及把对话归类为“增强”还是“自动化”。

博客没有说明 50 万次对话在两个平台之间是怎么分配的，也没有说明数据覆盖的时间窗口（只在局限一节说，出于隐私考虑，只分析了特定保留窗口内的数据）。

### 分类框架：自动化与增强

报告沿用了之前经济指数报告的区分：自动化（automation）是 AI 直接执行任务；增强（augmentation）是 AI 与用户协作完成任务。自动化与增强又各自分成几个子类型。博客提到了其中几个：反馈循环（Feedback Loop）——Claude 自主完成任务，但需要人类验证（例如用户把报错信息发回给 Claude）；指令型（Directive）——Claude 在最少用户互动下完成任务；学习型（Learning）——用户从 AI 模型那里获得知识。博客没有列出全部子类型，也没有给出每个子类型的精确定义。

### “谁在用”的分类

团队还用分析系统识别了最能描述用户编码互动的项目类型（例如个人项目与初创公司项目）。博客明确说，因为不知道 Claude 的回应在真实世界里是在什么背景下被使用的，这些分析依赖于从不完整数据里做出的不确定推断，因此这些发现比前面那些更初步。

## 三、主要发现

### 发现一：编码 agent 的自动化程度远高于通用聊天界面

Claude Code 上 79% 的对话被识别为自动化，21% 为增强；相比之下，Claude.ai 上只有 49% 的对话被归类为自动化。博客说，这可能意味着，随着 AI agent 变得更常见、更多 agentic AI 产品被造出来，我们应该预期任务的自动化会更多。

细分来看，反馈循环模式在 Claude Code 上几乎是 Claude.ai 的两倍（35.8% 对 21.3%）；指令型对话在 Claude Code 上也更高（43.8% 对 27.5%）。所有增强模式——包括学习型（用户从 AI 模型那里获得知识）——在 Claude Code 上都明显低于 Claude.ai。

博客指出，这些结果说明了专业编码 agent 与人们与大语言模型交互的“标准”方式（通过 Claude.ai 这样的聊天界面）之间的差异。随着更多 agentic 产品发布，AI 融入人们工作的方式可能会发生变化——至少在编码这个案例里，可能涉及更多的任务自动化。

但博客也提醒，即使在自动化里，人类仍然经常参与：反馈循环互动仍然需要用户输入（哪怕输入只是把报错信息粘贴回给 Claude）。不过，博客说，无法确定这种模式是否会持续下去——随着更有能力的 agentic 系统出现，可能需要越来越少的用户输入。

### 发现二：开发者常用 AI 造面向用户的应用

总体上，开发者常用 Claude 构建网站与移动应用的用户界面与互动元素。虽然没有哪一种语言占主导，但以 Web 开发为主的 JavaScript 与 TypeScript 合计占全部查询的 31%，HTML 与 CSS（其他面向用户的代码语言）合计又占了 28%。后端开发语言也有代表：Python 占查询的 14%，但 Python 有双重用途——既用于后端开发，也用于数据分析；加上 SQL（另一种数据导向语言，占查询的 6%），这些语言可能还包括许多数据科学与分析应用，而不只是传统后端开发。

从任务类型看，最常见的五项任务里有两项聚焦于面向用户的应用开发：“UI/UX 组件开发”与“Web 与移动应用开发”各占对话的 12% 与 8%。这类任务越来越适合一种被称为“氛围编程”（vibe coding）的现象——不同经验水平的开发者用自然语言描述想要的结果，让 AI 接手实现细节。

更通用的用途，例如“软件架构与代码设计”与“调试与性能优化”，在 Claude.ai 与 Claude Code 上也都高度 represented。

博客推测，这些发现提示，以制作简单应用与用户界面为中心的工作，可能比纯后端工作更早受到 AI 系统的冲击——如果能力不断提升让“氛围编程”进入主流工作流程。随着 AI 越来越多地处理组件创建与样式任务，这些开发者可能会转向更高层次的设计与用户体验工作。

### 发现三：初创公司是 Claude Code 的主要早期采用者，企业落后

初创公司的工作占 Claude Code 对话的 32.9%（比它们在 Claude.ai 上的使用高出近 20%），而企业工作只占 Claude Code 对话的 23.8%（略低于它们在 Claude.ai 上 25.9% 的占比）。

此外，学生、学术界、个人项目建造者与教程/学习用户加起来，占两个平台全部互动的一半。换句话说，采用编码辅助工具的不只是企业，个人也是重要的采用者。

博客说，这些采用模式与过去的技术变迁相似：初创公司用新工具获得竞争优势，而老牌组织行动更谨慎，往往在全公司推广之前先做详细的安全检查。AI 的通用性可能加速这个动态：如果 AI agent 带来显著的生产力提升，早期与晚期采用者之间的差距可能转化为可观的竞争优势。

**注意：摘要与正文的数字对不上。** 博客开头的三点摘要里写的是“33% 的 Claude Code 对话服务于初创公司相关的工作，相比之下只有 13% 被识别为企业相关应用”。但正文里写的是企业工作占 Claude Code 对话的 23.8%，不是 13%。这两个数字对不上。一种可能的解释是，摘要里的 13% 实际上是初创公司工作在 Claude.ai 上的占比（32.9% 比它“高出近 20%”，32.9 减 20 约等于 13），被错误地标成了“企业相关”。但这只是分析者的推测，博客本身没有解释这个不一致。读者引用企业占比时，应该用正文的 23.8%，并注明摘要里的 13% 与正文冲突。

### 附录：编码任务比非编码任务更“自动化”

作为补充分析，团队还把软件相关的自动化与增强模式，与不涉及软件的互动模式做了比较。这个分析只在 Claude.ai 上做，因为 Claude Code 专注于软件应用。

与不涉及软件的使用场景相比，软件开发更自动化。反馈循环的大幅增加（+18.3%）推动了这一点，并显著抵消了指令型行为的明确下降（-11.2%）。换句话说，AI 辅助编码目前需要大量的人类审阅与迭代，哪怕 Claude 做了大部分工作。

## 四、作者的结论与局限

博客的结论是：AI 正在从根本上改变开发者工作的方式。在使用专业 agentic 系统（如 Claude Code）的地方，这种变化尤其强烈，在面向用户的应用开发上尤其明显，并且可能让初创公司比更成熟的企业更有优势。

报告提出了一串后续问题：人类仍然参与其中的反馈循环模式会随着 AI 能力提升而持续，还是会转向更完整的自动化？随着 AI 系统能够构建更大规模的软件，开发者会不会转向主要管理和指导这些系统，而不是写代码？哪些软件开发角色变化最大，哪些可能完全消失？

编码 AI 技能的提升对 AI 开发本身也可能有重要后果：由于大量 AI 研究与开发依赖软件，AI 辅助编码的进步可能有助于加速突破，形成正反馈循环，进一步加速 AI 进展。

作者自述的局限列在“Limitations”一节，有六条：只分析了 Claude.ai 与 Claude Code 的数据，排除了 Team、Enterprise 与 API 使用（这些在职业场景里可能显示不同模式）；自动化与增强之间的界限随着 Claude Code 这样的 agentic 工具变得越来越模糊（例如反馈循环在质量上不同于传统自动化，因为它仍然需要人类监督与输入，未来可能需要扩展这个框架）；“谁在用”的分类依赖于有限背景下的推断，有些分类可能是错的，并且有一个“无法分类”选项（Claude.ai 对话里占 5%，Claude Code 对话里占 2%），这个类别被排除在分析之外、结果被重新归一化；数据集可能只捕捉了早期采用者，这些用户可能不代表更广泛的开发者群体，自我选择可能让使用模式偏向更有经验或技术上更大胆的用户；出于隐私考虑，只分析了特定保留窗口内的数据，可能错过软件开发里的周期性模式（例如冲刺周期或发布计划）；Claude 使用的代表性相对于整体 AI 编码辅助采用情况是不清楚的，许多开发者除了 Claude 还用多种 AI 工具，报告只呈现了他们 AI 参与的部分视图；最后，报告只研究了开发者把什么委托给 AI，没有研究他们最终怎么在代码库里使用 AI 输出、生成代码的质量如何、或这些互动是否有效提高了生产力或代码质量。

## 六、精读点评

### 这篇东西是什么，不是什么

这是一份描述性分析报告，不是实验、不是因果研究。它用 50 万次真实对话回答了“开发者怎么用 Claude 写代码”这个问题，有明确的样本量、分类方法与局限声明。按精读模板来套，它有可核查的数字与方法，但没有假设检验、没有对照实验、没有因果推断——它的结论都是“观察到了什么”，不是“什么导致了什么”。

### 最值得注意的一点：自动化与增强的界限正在模糊

报告最有价值的一点不是 79% 对 49% 这个对比，而是它自己承认的局限：反馈循环在质量上不同于传统自动化，因为它仍然需要人类监督与输入。Claude Code 上 79% 的“自动化”里，有 35.8% 是反馈循环——也就是人类还在回路里贴报错、做验证。如果把反馈循环算成“半自动化”，那 Claude Code 的“纯自动化”（指令型）其实是 43.8%，与 Claude.ai 的 27.5% 相比，差距就没有 79% 对 49% 看起来那么大。报告没有做这个拆分，但它给出了拆分所需的数字。读者引用 79% 时，应该同时说明其中将近一半是需要人类参与的反馈循环。

### 摘要与正文对不上的 13%

报告里有一处内部不一致，值得单独指出：摘要说企业相关应用只占 Claude Code 对话的 13%，正文说占 23.8%。这两个数字差了将近一倍。最可能的解释是摘要把初创公司在 Claude.ai 上的占比（约 13%）错标成了企业占比——因为正文说初创公司占比“比 Claude.ai 高出近 20%”，32.9% 减去 20 个百分点正好约等于 13%。但这只是分析者的推测，博客本身没有解释。无论原因是什么，这个不一致说明报告的编辑校对有疏漏，读者引用企业占比时应该用正文的 23.8%，并注明摘要里的数字与正文冲突。

### 它没有回答的问题：生产力与质量

报告的局限一节很诚实：它只研究了开发者把什么委托给 AI，没有研究他们最终怎么在代码库里使用 AI 输出、生成代码的质量如何、或这些互动是否有效提高了生产力或代码质量。这意味着，报告能证明的是“开发者在用 AI 做更多事”，不能证明“开发者因为 AI 变得更高效”或“代码变得更好”。“氛围编程”这个观察很有意思，但报告没有数据说明氛围编程产出的代码质量如何——这是它留给后续研究的最大缺口。

### “谁在用”的分类最不可靠

报告自己把“谁在用”的发现标为“更初步”：分类依赖于从不完整数据里做出的不确定推断，有些分类可能是错的，还有 5%（Claude.ai）与 2%（Claude Code）的对话无法分类、被排除后重新归一化。初创公司 32.9% 对企业 23.8% 这个对比，是建立在这种推断之上的。读者引用它时，应该同时注明它的初步性质——报告自己就是这么标的。

### 科学价值

认知价值：中等。它给出了编码 agent 与通用聊天界面在使用模式上的第一个大规模对比，并记录了“氛围编程”与初创公司早期采用这两个值得跟进的观察。方法价值：低到中等。Clio 这个工具是可复用的，但本篇报告本身没有留下新的方法——它的分类框架（自动化/增强）是沿用之前报告的。边界价值：高。局限一节写得非常完整，六条局限把“这篇报告不能证明什么”说得很清楚。启示价值：中等。它提出了一串后续问题（反馈循环会不会持续、开发者会不会转向管理 AI、哪些角色会消失），但没有给出可检验的下一步实验设计。

### 总体判断

作为一份描述性报告，它是扎实的：样本量大、分类方法透明、局限声明完整、数字大多可以从正文核对。它的主要毛病是摘要与正文的一处数字冲突，以及“自动化”这个标签把需要人类参与的反馈循环也算了进去——79% 这个 headline 数字比实际情况显得更自动化。置信度：高，针对“报告写了什么与数字是多少”（除摘要的 13% 外）；中，针对“谁在用”的发现——报告自己标为初步；不适用，针对生产力或代码质量——报告没有测量。

## 七、证伪器、替代解释、接下来看什么

### 证伪器

这份报告没有可证伪的科学主张——它是一份描述性报告，不是假设检验。如果把它的核心主张（“编码 agent 比通用聊天界面更自动化”）当作主张来检验，检验方式是：在另一个时间窗口、另一个开发者样本里重复这个分析，看 Claude Code 的自动化占比是否仍然显著高于 Claude.ai。如果重复分析里两者没有差异，这个主张就站不住。但报告没有提供可复现的数据集（对话数据是隐私保护的），独立复现无从做起。

### 替代解释

- 替代解释一：Claude Code 的自动化占比更高，不是因为 agent 本身更自动化，而是因为用 Claude Code 的人本身就是更愿意把任务完全交给 AI 的早期采用者（自我选择）。如果这个解释是对的，那么同一批用户在 Claude.ai 上也应该表现出更高的自动化占比；而报告没有按用户分组，无法排除这个解释。报告自己在局限里承认了早期采用者偏差。
- 替代解释二：前端开发占比高，不是因为 AI 更擅长前端，而是因为 Claude 的用户群体本身就偏向 Web 开发（例如大量独立开发者与初创公司）。如果这个解释是对的，那么换一个用户群体（例如嵌入式系统开发者），语言分布应该完全不同；报告没有给出用户群体的基线分布，无法排除这个解释。

### 作者自述的局限与分析者发现的局限

作者自述的局限：只分析了 Claude.ai 与 Claude Code 的数据；自动化/增强界限正在模糊；“谁在用”的分类依赖不完整数据的推断、部分可能错误，无法分类的对话被排除后重新归一化；数据集可能只捕捉了早期采用者；只分析了特定保留窗口内的数据；Claude 使用的代表性不清楚；没有测量生产力或代码质量。

分析者发现的局限：摘要与正文的企业占比数字冲突（13% 对 23.8%）；79% 的“自动化”里有 35.8% 是需要人类参与的反馈循环，headline 数字比实际情况显得更自动化；50 万次对话在两平台之间的分配没有给出；数据覆盖的时间窗口没有给出；自动化/增强的全部子类型没有列出；没有作者署名行；没有 arXiv 版本。

### 接下来看什么

最便宜的决定性下一步，是修正摘要里的 13% 并说明它的来源。判据是一句话：修正后的数字是否与正文的 23.8% 一致、或给出 13% 的正确归属。如果摘要的数字被悄悄改掉而不留说明，读者就无法知道哪个版本是对的。

其次值得看的是：报告没有测量的东西——生产力与代码质量。下一步研究应该跟踪同一批开发者，看用了 Claude Code 之后，他们的产出速度、代码缺陷率、返工率有没有变化。判据是一句话：自动化占比的提升是否伴随着可测量的生产力提升，还是只伴随着更多的审阅与返工。

## §I 收尾综合

**一句话结论：** 这是一份扎实的描述性报告——它用 50 万次真实编码对话说明，专门的编码 agent（Claude Code）比通用聊天界面自动化得多（79% 对 49%），而且前端开发与初创公司是早期采用的主力；但它只描述“人们怎么用”，不测量生产力或代码质量，而且摘要与正文有一处数字对不上（企业占比 13% 对 23.8%），读者引用时要留神。

**核心结论：**

1. Claude Code 上 79% 的对话是自动化，Claude.ai 上只有 49%；其中反馈循环（35.8% 对 21.3%）与指令型（43.8% 对 27.5%）都更高。置信度：高。证据：数字台账 E2、E3、E4。
2. 开发者常用 Claude 造面向用户的应用：JavaScript 与 TypeScript 合计占查询的 31%，HTML 与 CSS 合计占 28%；“UI/UX 组件开发”与“Web 与移动应用开发”各占对话的 12% 与 8%。置信度：高。证据：数字台账 E5、E6、E9。
3. 初创公司工作占 Claude Code 对话的 32.9%，企业工作占 23.8%；但“谁在用”的分类依赖不完整数据的推断，报告自己标为初步。置信度：中。证据：数字台账 E10、E13。
4. 摘要里的企业占比 13% 与正文的 23.8% 冲突，原因未解释。置信度：高（就“冲突存在”）。证据：数字台账 E11。
5. 报告没有测量生产力提升、代码质量或错误率。置信度：高。证据：数字台账 E15。

**关键结果表：**

| 结果 | 数字 | 条件 |
|---|---|---|
| 自动化对话占比 | Claude Code 79%，Claude.ai 49% | 50 万次编码对话；反馈循环占其中 35.8% 对 21.3% |
| JavaScript 与 TypeScript 占比 | 31% | 全部查询 |
| HTML 与 CSS 占比 | 28% | 全部查询 |
| UI/UX 组件开发占比 | 12% | 全部对话 |
| 初创公司工作占比 | 32.9% | Claude Code 对话；分类为初步推断 |
| 企业工作占比 | 23.8%（摘要写 13%，冲突） | Claude Code 对话；Claude.ai 上为 25.9% |
| 生产力或代码质量 | 无可用数字 | 报告没有测量 |

**科学价值总评：** 认知上有中等价值——编码 agent 与通用界面的第一个大规模使用对比，加上“氛围编程”与初创公司早期采用这两个观察；方法上价值有限——分类框架是沿用的，没有留下新方法；边界上价值很高——局限一节把“不能证明什么”说得很完整；启示上它提出了一串后续问题，但没有给出可检验的下一步设计。总体上，这篇工作值得因为“它用真实数据记录了编码 agent 如何改变开发者的工作方式”被记住，不值得因为任何生产力或代码质量的结论被记住——它本来就没有测量这些。

**适用边界：** 不要拿 79% 去主张“编码工作已经被 AI 自动化了”——其中 35.8% 是需要人类参与的反馈循环；不要拿摘要的 13% 去主张企业采用率低——正文说是 23.8%，两者冲突；不要拿这份报告去主张“AI 提高了开发者生产力”——报告没有测量生产力；不要拿“谁在用”的发现当作定论——报告自己标为初步推断。
