## 一、背景与问题

### 为什么长时运行的智能体是个问题

文章开头说，随着智能体能力变强，开发者越来越多地让它们承担需要数小时、甚至数天工作的复杂任务。但让智能体跨多个上下文窗口持续取得进展，仍然是一个开放问题。

核心困难在于：长时运行的智能体只能以离散的会话（session）工作，每个新会话开始时对之前发生过的事一无所知。文章打了一个比方：就像一个软件项目由轮班的工程师接力，每个新来的工程师都不知道上一班发生了什么。因为上下文窗口有限，而大多数复杂项目又不可能在一个窗口内完成，智能体需要一种办法，在编码会话之间架起桥梁。

### 光有上下文压缩还不够

Claude Agent SDK 本身已经是一个强大的通用智能体脚手架，擅长编码，也擅长其他需要调用工具来收集上下文、规划与执行的任务。它有上下文管理能力，例如压缩（compaction），让智能体在不耗尽上下文窗口的情况下持续工作。理论上，有了这套设置，智能体应该可以无限期地持续做有用的工作。

但作者说，压缩是不够的。即使是最前沿的编码模型 Opus 4.5 在 Claude Agent SDK 上以多上下文窗口循环运行，只给一个高层提示——比如“仿造一个 claude.ai 克隆版”——也建不出一个生产质量的网络应用。

失败表现为两种模式。第一种，智能体倾向于一次做太多——本质上想一口气把整个应用做出来。这常常导致模型在实现中途耗尽上下文，留下一个做到一半、又没有文档记录的功能给下一个会话。下一个会话只好先猜之前发生了什么，再花大量时间把基本功能修好。即使有压缩也会这样，因为压缩并不总能把完全清晰的指令传给下一个智能体。

第二种失败模式往往出现在项目后期。一些功能已经建好之后，后来的某个智能体实例环顾四周，看到已经取得了进展，就宣布工作完成了。

### 问题拆成两部分

作者把问题拆成两部分。第一，需要搭建一个初始环境，为提示所要求的所有功能打下基础，让智能体可以一步一步、一个功能一个功能地工作。第二，应该提示每个智能体朝着目标取得增量进展，同时在会话结束时把环境留在干净的状态。

所谓“干净的状态”，意思是那种可以直接合并到主分支的代码：没有重大 bug，代码整齐、文档齐全，一个开发者可以不用先清理一堆无关的烂摊子就直接开始做新功能。

## 二、方法与设计

### 两部分的解法

作者在内部试验中用两部分的解法应对上述问题。

**初始化智能体（initializer agent）。** 第一次会话使用一个专门的提示，让模型搭建初始环境：一份 `init.sh` 脚本、一个记录智能体做过什么的 `claude-progress.txt` 文件，以及一个展示已添加文件的初始 git 提交。

**编码智能体（coding agent）。** 之后每一次会话都要求模型取得增量进展，然后留下结构化的更新。

这里的关键洞见，作者的说法是：找到一种办法，让智能体在以全新的上下文窗口开始时快速理解工作状态——办法就是 `claude-progress.txt` 文件加上 git 历史。这些做法的灵感来自作者对有效软件工程师日常工作的了解。

### 环境管理的具体做法

文章在 Anthropic 更新过的 Claude 4 提示指南（prompting guide）里已经分享过多上下文窗口工作流的最佳实践，包括一种使用“第一个上下文窗口用不同的提示”的脚手架结构。这个“不同的提示”要求初始化智能体搭建好环境，带上未来编码智能体有效工作所需的一切上下文。这里则对其中几个关键组件做更深入的讲解。

**功能清单（feature list）。** 为了解决智能体一口气做完整个应用、或过早宣布项目完成的问题，作者提示初始化智能体写一份全面的功能需求文件，把用户的初始提示展开。在仿造 claude.ai 的例子里，这意味着 200 多项功能，例如“用户可以打开一个新聊天、输入查询、按回车、看到 AI 的回答”。这些功能最初都标为“未通过”（failing），这样后来的编码智能体就对完整功能长什么样有一个清晰的轮廓。

作者提示编码智能体只能通过改动一个 `passes` 字段的状态来编辑这个文件，并用措辞强烈的指令，例如“删除或编辑测试是不可接受的，因为这可能导致功能缺失或有 bug”。经过一些试验，他们最终决定用 JSON 格式来写这个文件，因为与 Markdown 文件相比，模型不太可能不恰当地改动或覆盖 JSON 文件。

**增量进展（incremental progress）。** 有了初始环境脚手架之后，下一轮编码智能体被要求一次只做一个功能。这种增量做法对解决智能体一次做太多的倾向至关重要。

一旦开始增量工作，模型在改完代码之后把环境留在干净状态仍然至关重要。在作者的试验里，引出这种行为的最好办法是：要求模型把进展提交到 git，写描述性的提交信息，并在进度文件里写进展总结。这样模型也可以用 git 回滚糟糕的代码改动、恢复代码库的工作状态。

这些做法还提高了效率：智能体不再需要猜之前发生了什么，也不再需要花时间把基本应用修好。

**测试（testing）。** 作者观察到的最后一个主要失败模式是，Claude 倾向于不经充分测试就把一个功能标为完成。没有明确提示时，Claude 会改代码，甚至会用单元测试、或对开发服务器发 `curl` 命令做测试，但却不能认识到这个功能端到端并不工作。

在构建网络应用的例子里，一旦明确提示 Claude 使用浏览器自动化工具、像人类用户那样做全部测试，它在端到端验证功能方面大多做得很好。

给 Claude 提供这类测试工具大幅改善了表现：智能体能够发现并修复那些只看代码看不出来的 bug。

但仍有一些问题残留，例如 Claude 的视觉能力与浏览器自动化工具的局限，让它难以发现每一种 bug。举例说，Claude 通过 Puppeteer MCP 看不到浏览器原生的 alert 弹窗，依赖这类弹窗的功能因此往往 bug 更多。

### 每个会话如何上手

有了上述一切之后，每个编码智能体都会被提示先走一遍上手步骤，其中有些很基础，但仍然有帮助：

1. 运行 `pwd` 看自己在哪个目录里——只能编辑这个目录里的文件。
2. 读 git 日志和进度文件，了解最近做了什么。
3. 读功能清单文件，选优先级最高、尚未完成的功能来做。

这种做法每个会话都为 Claude 省下一些 token，因为它不必自己琢磨怎么测试代码。要求初始化智能体写一份能启动开发服务器的 `init.sh` 脚本、并在实现新功能之前先跑一遍基本的端到端测试，也很有帮助。

在仿造 claude.ai 的例子里，这意味着智能体总是先启动本地开发服务器，再用 Puppeteer MCP 开一个新聊天、发一条消息、收到回答。这样 Claude 就能快速发现应用是否被留在了损坏状态，并立刻修复已有的 bug。如果智能体反倒先开始实现新功能，很可能会让问题更糟。

文章在“上手”一节末尾说，“一个典型的会话以以下助手消息开始”，但抓取到的正文里这句话之后没有列出任何消息内容——这部分似乎缺失或未被抓取，见未核实清单。

## 三、主要发现

这篇帖子没有实验、没有对照、没有统计，也没有可核查的性能数字。它的“发现”全部是定性的做法总结，来自作者在内部试验中的观察。

可以归纳为四条做法。第一，第一个会话专门用来搭建环境：功能清单、进度文件、初始化脚本、初始 git 提交。第二，之后每个会话一次只做一个功能，功能清单用 JSON 写、只改状态字段，并用强措辞禁止删除或编辑测试。第三，每轮结束时提交到 git、写进度总结，保持环境干净可交接；上手时先读日志、进度文件与功能清单。第四，明确提示模型像人类用户一样用浏览器自动化工具做端到端测试——作者说这大幅改善了表现，但没有给出任何数字。

全文唯一一个具体数字是：仿造 claude.ai 的例子里，功能清单有 200 多项功能。这个数字只说明那个例子的规模，不是对方法效果的度量。

## 四、作者的结论与局限

### 作者的结论

作者的结论很克制：这篇研究展示了一套长时运行智能体脚手架中可能的一组解法，让模型能够跨多个上下文窗口取得增量进展。但仍有开放问题。

### 作者自述的局限与未来工作

作者在未来工作一节里点了两个方向。

最值得注意的是，目前仍不清楚：是单个通用编码智能体在各上下文中表现最好，还是多智能体架构能取得更好表现。作者认为，测试智能体、质量保证智能体、代码清理智能体这类专门化的智能体，在软件开发生命周期的各子任务上可能做得更好，这是合理的。

另外，这个演示是针对全栈网络应用开发优化的。未来的方向是把这些发现推广到其他领域。作者认为，这些经验教训中的一部分或全部，很可能可以应用到其他类型的长时运行智能体任务上，例如科学研究或金融建模。

除此之外，作者没有列出其他局限，也没有讨论这套做法在哪些条件下会失效、成本是多少、或者与不做这些做法的基线相比好多少。

## 五、精读点评

> 本节是分析者的判断，只放在这里，不织进上面对论文的呈现里。

### 这不是一篇论文，是一篇做法帖

首先要说清楚这篇东西的分量：它没有研究问题、没有实验设计、没有对照、没有数字。它是一篇工程实践帖，讲的是 Anthropic 内部摸索出来的一套脚手架做法。按精读工具的模板套，它的大部分格子都是空的——不是没读懂，是原文就没有。

这并不意味着它没有价值。它的价值在于把一套做法写得具体、可照着做：初始化智能体该产出哪几样东西、功能清单为什么用 JSON、为什么禁止改测试、每轮结束为什么要提交 git、每个会话开头先做哪三件事。这些都是能直接拿走的东西。只是读者要清楚，这些做法的证据只是“我们在内部试验中发现”，没有可核查的对照数据。

### 最承重的一点：所有效果宣称都没有数字

全文里“大幅改善了表现”“至关重要”“最好办法”这类判断，没有一个配了数字。没有基线对比：不做这些做法时，Opus 4.5 在同一个任务上能走多远、失败几次；做了之后又能走多远。没有任务成功的定义，也没有成本数据：每个会话多花多少 token 在读日志、写进度文件上。200 多项功能这个数字只是例子的规模，不是效果。

所以这篇帖子的主张应当读成“我们试下来觉得这样管用”，而不是“这样被证明管用”。任何人拿它去为“长时运行智能体问题已经解决”背书，都是误读。

### 做法本身合理，但有几处值得追问

功能清单用 JSON 而不是 Markdown，理由是模型不太可能不恰当地改动 JSON——这个理由是经验性的，没有数据支撑，而且它依赖模型对格式的行为特性，换一个模型未必成立。同样，“一次只做一个功能”与“每轮留下干净状态”这两条，听起来像良好的软件工程习惯被翻译成了提示词；它们有效，很可能不是因为提示词有什么魔力，而是因为它们把一个大任务切成了小任务、并强制留下了可恢复的状态。文章没有区分这两件事。

还有一个没有回答的问题：这套做法的适用范围。演示只针对全栈网络应用开发，作者自己也承认推广到科学研究或金融建模只是“很可能”。功能清单、浏览器端到端测试这些具体做法，在那些领域里未必有直接对应的东西。

### 总体判断

这是一篇诚实但很薄的工程帖：它没有夸大——没有宣称数字、没有宣称解决了长时运行问题，只说“这是可能的一组解法，还有开放问题”。它的优点是做法具体、可直接复用；它的弱点是没有任何可核查的证据，效果宣称全凭作者的内部观察。

可信度上，做法描述本身可信（它们就是作者实际在用的提示与流程），但效果判断的置信度只能给低：没有对照、没有数字、没有复现路径。最值得记住的不是任何结论，而是那套做法清单本身——以及它提醒的一件事：长时运行智能体的问题，至少有一部分是工程脚手架问题，不只是模型能力问题。

## §I 收尾综合

**一句话结论：**这是一篇没有实验与数字的工程实践帖，只给出一套让 Claude Agent SDK 跨多上下文窗口持续写代码的具体做法（首会话搭环境、每轮只做一个功能、留干净可交接的状态），做法来自内部试错、未经验证。

**核心结论：**

1. 长时运行智能体的核心困难是会话之间没有记忆，上下文压缩不足以解决它；失败模式是一次做太多导致中途耗尽上下文，以及过早宣布完成。（置信度：中。证据：正文问题描述；但这是作者的观察陈述，没有对照数据。）
2. 两部分解法——初始化智能体搭环境、编码智能体增量推进并留下结构化更新——是作者内部试验的产物，做法具体可复用。（置信度：中。证据：正文方法描述与 GitHub quickstart 链接；效果未经验证。）
3. 功能清单（JSON、只改状态字段、禁止删改测试）、git 提交与进度文件、浏览器自动化端到端测试，是这套做法的三个具体要点。（置信度：高。证据：正文逐项描述。）
4. 是否单智能体最好、还是多智能体架构更好，仍不清楚；这套做法目前只针对全栈网络应用开发优化。（置信度：高。证据：作者在未来工作一节里自己说的。）
