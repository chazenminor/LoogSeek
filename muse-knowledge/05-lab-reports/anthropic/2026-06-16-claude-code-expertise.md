## 一、背景与问题

### 智能体编程火了，但没人知道它在实践中长什么样

这篇报告的出发点是一个落差：基准测试上的能力上限已经很高、还在上升——前沿模型在 METR 的时间跨度（time-horizon）评估上，已经能自主完成需要人花几小时的软件任务。但能力上限不等于实际用法。人们真的把决定交给智能体了吗？没有正式编程经验的人，能不能指挥智能体完成复杂的技术工作？这些工具的快速普及与改进，对知识工作整体意味着什么？

报告要回答的不是“模型能做什么”，而是“人们实际在用它做什么、怎么做、做得成不成”。数据是 Claude Code 的真实使用记录：2025 年 10 月到 2026 年 4 月之间约 40 万次交互式会话，来自约 23.5 万人。

### 是什么逼出了这个问题

有两个具体的关切。第一是劳动市场的走向。如果智能体编程工具正在吸收大量实现性的工作，那么什么样的人会从中受益、什么样的人会被落下，就成了一个需要数据回答的问题，而不是凭直觉争论的问题。第二是“领域专业知识 vs 编程技能”这个悬而未决的判断：一种常见的假设是，会写代码的人才能用好编程智能体；另一种可能是，真正起作用的是对问题本身的理解——知道要解决什么、知道怎么验证答案对不对。这篇报告要在这两者之间做一个初步的裁决。

不解决这个问题会怎样？对实践来说，雇主、教育者和政策制定者会在没有证据的情况下押注：要么以为“人人都能靠智能体写代码了”，要么以为“只有程序员能用好它”。两种押注错了，代价都很大。对领域来说，关于“智能体时代什么技能还值钱”的讨论，会继续停留在轶事与基准分数上，而不是建立在真实使用数据上。

为什么这个问题现在能问？因为 Anthropic 有了两样东西：一是足够大规模的真实使用数据（约 40 万次会话），二是隐私保护分析的基础设施——研究者不直接读任何一份会话记录，所有数字都是对会话单元的聚合。这两样东西加起来，让“描述真实用法”这件事第一次有了可操作的办法。没有这个基础设施，同样的问题只能靠小样本访谈或自我报告来回答。

读完之后应该改变的认知是：**决定会话成败的不是会不会写代码，而是对任务领域的理解有多深**。以及一个与之配套的分工图景：人做“做什么”的决定，智能体做“怎么做”的决定。这两个判断加起来，指向一个劳动市场的初步图景——智能体正在替代实现性的工作，但同时在奖励那些对问题有扎实理解的人。

## 二、方法与设计

### 样本：约 40 万次会话，来自约 23.5 万人

分析覆盖 2025 年 10 月到 2026 年 4 月（含首尾月）的交互式 Claude Code 会话，均匀随机抽样得到 398,198 次会话，来自 234,751 名用户。其中 73,066 名用户在样本中出现不止一次，6,382 人出现 5 次以上，1,413 人出现 10 次以上。样本排除了 Anthropic 内部的使用。

覆盖的入口是 Claude Code 命令行界面（CLI）、Claude Code 桌面应用和 claude.ai。明确排除的有三类：第三方集成开发环境里的使用、软件开发工具包（SDK）调用、以及零次人工轮次的会话——也就是无头（headless）模式的非交互调用，例如 `claude -p "<prompt>"`。博客在结尾承认，非交互式使用占了相当大的一块活动，本报告不覆盖它，未来要为它开发度量框架。

所有分类都跑在隐私保护分析基础设施上。研究者从不直接读任何一份会话或记录；报告里的每个数字，都是对包含足够多不同用户的会话单元的聚合，达不到最低用户数的单元会被压制不报告。

### 分类器：一个模型读记录、打标签

几乎每个分类器都是一次 Claude Sonnet 4.6 调用，温度 0.2，必须从给定选项里恰好选一个。给模型的记录是会话全文（人工、助手、系统轮次），每轮中间截断到 5,000 字符，整份记录截断到 25,000 字符。例外是任务价值估计器：先用 Claude Haiku 4.5 把会话改写成自由职业招聘帖，再用 Opus 4.7 对照真实招聘帖定价。

 alongside 分类器，报告还用了每场会话自动记录的遥测数据：人工提示数（轮次）、模型调用数（API 请求）、成功的工具调用数、输出 token 数、增删代码行数，以及用户账号的年龄（注册 Anthropic 多少天，不是注册 Claude Code 多少天）。

### 九种工作模式

每场会话被归入九种工作模式之一——最能描述这场会话想完成什么的单一活动。四种直接涉及写代码或维护代码：新建（building）、修复（fixing）、测试（testing）、编排其他智能体或自动化流水线（orchestrating）。一种是操作软件：部署、配置、跑流水线、监控系统（operating）。两种是先搞清楚再动手：理解现有系统怎么工作（understanding）、动手前规划一次改动（planning）。两种与代码无关、或代码只是顺带：分析数据（analyzing）、通过演示文稿与其他散文体文档沟通（communicating）。

分类按主导活动定，而不是按用户第一轮说了什么。如果一场会话开头在规划、但大部分轮次在写代码，就归为新建，而不是规划。这个规则写进了分类器的提示词里。

### 决策归属：谁在做规划决定，谁在做执行决定

报告从两个角度看人机分工。第一个角度是决定：建了一个隐私保护的决策归属分类器，让它列出会话里所有有意义的决定，再把决定分成规划类（做什么、采取什么方法、什么算完成）与执行类（改哪些文件、写什么代码、用什么语言、跑哪些命令），然后把每个决定归属到 Claude 或用户名下。每场会话由此得到两个数字：用户在规划决定中的占比、用户在执行决定中的占比。

第二个角度是行动：看会话的结构。一场 Claude Code 会话是用户与 Claude 来回交替——用户写一个提示，Claude 去做一串工作，用户再写一个提示，如此往复。报告数的是每轮里 Claude 做了多少动作。

### 专业知识：五级量表，评的是任务本身

每场会话里，模型按五级量表给用户在该任务上的表面专业知识打分：1 新手（Novice）、2 初学者（Beginner）、3 中级（Intermediate）、4 高级（Advanced）、5 专家（Expert），证据太薄时标“不清楚”。分类器看三个同等权重的信号：表述的具体程度（用户是不是用只有懂行的人才用得上的命名实体与约束来框定问题）、要求验证的类型（泛泛的“请再检查一下”不算专业知识，针对性的“你真的调用 commit() 了吗”才算）、以及纠正的方向（Claude 纠正用户的领域概念，往下拉；用户抓住 Claude 的领域错误，往上推）。

关键的一点是，专业知识是任务特定的，不是职业头衔的同义词。一个资深工程师第一次问 Rust 问题，在 Rust 这件事上就是初学者；一个从没写过 Python 的会计，如果能准确说出 Python 脚本必须执行哪些对账规则、并在月末结账的边界情况上抓住 Claude 的错误，在这个任务上就是专家。

### 职业：按美国劳工统计局的分类推断

报告从会话记录推断每位用户的职业，映射到美国劳工统计局标准职业分类（SOC）的 23 个大类之一。分类器只被允许用项目上下文、文件名与结构、引用的制品（法律文件、临床数据、财务报告、课程表等）与用词等信号，并且被明确指示不得把“写代码”本身当作从事编码职业的证据。只有在有明确信号表明软件或数据工作就是用户的本职时，会话才会被归入计算机与数学职业（Computer and Mathematical Occupations）。例如一位律师写脚本自动标记一叠合同里缺失的条款，会被归入法律职业，哪怕这场会话的工作主要是软件。没有职业信号的会话留为未分类。

约 70% 的会话能推断出职业；其余约 30% 在职业分析中被排除。报告另外还设了一个“工作所属职业”分类器——按会话里做的工作本身通常属于哪个职业来分类，与“用户本人职业”分开，但正文的主要结论用的是用户本人职业。

### 成功：两层度量，一层判断、一层验证

报告不观察用户的真实世界结果，也不能直接问用户有没有得到想要的东西。成功靠两套互补的、基于记录的度量。

第一是**判断成功**（judged success）：一个分类器读完整份记录，判断这个人是否做成了他一开始想做的事，选项是成功、部分成功、失败、没有明确目标。

第二是**核实成功**（verified success）：两个配套的分类器分别给成功证据与失败证据打分。成功信号分类器找可验证的成功证据，特别是与工作匹配的 git 活动（提交、拉取请求）、测试套件通过、以及用户明确肯定，分数从“没有信号”到 1（弱信号）到 5（多个硬信号）。失败信号分类器找出错的证据：错误、测试失败、反复尝试同一件事、用户对产出表示不满。核实成功要求同时满足两条：被判断为成功，并且成功信号至少达到 4 分——也就是记录里至少有一个硬的可验证信号。

在下面关于成功程度的分析里，没有明确目标的会话被排除，这类会话约占全部样本的 7.7%。

报告还定义了两个派生概念。**遇到麻烦**（hits trouble）：失败信号达到 3 分及以上，也就是有具体证据表明会话中途出了问题。**放弃**（abandoned）：一场遇到麻烦的会话同时被判断为失败、并且遥测记录里一行代码都没写。

### 任务价值：把会话改写成自由职业招聘帖再定价

每场会话的经济价值，用一个两步的模型调用来估计。第一步，Claude Haiku 4.5 把会话改写成一条 Upwork 风格的自由职业招聘帖——假装客户在雇人做 Claude 实际做的那份工作，只写范围与交付物，不提 Claude 或 AI。第二步，Opus 4.7 把这条帖子对照一个由 200 条真实自由职业招聘帖组成的校准语料定价。校准语料来自 2024–2026 年的公开招聘帖数据集，限定为固定价格、价格在 10 到 50,000 美元之间、描述至少 50 个字符；约 23,000 条帖子通过了筛选。

报告自己说，这些价格估计很粗糙，主要用来在不同任务之间、随时间作比较，不应按美元面值去读。附录里有更坦率的验证数字，见下一节。

## 三、主要发现

### 发现一：人做规划决定，智能体做执行决定

平均来看，人做出约 70% 的规划决定，但只做出约 20% 的执行决定。报告的表述是：实际分工很清楚——人决定建什么，智能体决定怎么建。

行动层面的数字与这个分工一致。一场典型会话大约有四轮；每条用户提示平均引发 Claude 的约 10 个动作，有时超过 100 个；每轮 Claude 平均输出约 2,400 词。Claude 每轮做多少事，取决于谁在做决定：当用户掌握执行控制权（做出超过 80% 的执行决定）时，Claude 每轮约做 8 个动作；当 Claude 掌握规划控制权（做出超过 80% 的规划决定）时，它每轮做的动作最多，约 16 个。

### 发现二：专业知识越多，Claude 每次提示做的工作越多

新手会话里，每条提示平均引发约 5 个 Claude 动作、约 600 词输出；专家会话里，每条提示引发的动作链长一倍多（12 个动作），输出是五倍（3,200 词）。这个新手与专家之间的差距，在每种工作、每个任务价值档位里都存在。

报告把这个度量与先前关于 Claude Code 自主性的工作做了区分：先前的工作追踪的是智能体连续运行多久、用户多常自动批准它的动作；这里的决策归属度量捕捉的是整场会话里谁在做实质性决定，而每提示的产出与动作数度量的是每条人工提示能引发多少智能体的自主活动。

### 发现三：工作构成在七个月里明显移动，从修 bug 转向端到端的智能体使用

2025 年 10 月到 2026 年 4 月之间，工作构成变化很大。最清楚的变化是修 bug 的份额从 33% 降到 19%，降了将近一半。取而代之的是围绕代码的工作变多了：操作软件从 14% 升到 21%；写作与数据分析大约翻了一倍，从约 10% 升到 20%。

任务本身也变得更有价值。按自由职业等价价格估计，平均每场会话的估计价值在 10 月到 4 月之间上升了 27%（要点部分写的是平均约 25%，与正文的 27% 有出入，见未核实清单）。上升在许多种工作里都成立：新建、操作、修复类任务的价值分别大约增长了 43%、34% 与 32%。报告提醒，这些价格估计很粗糙，主要用来作任务之间、随时间的比较，不应按美元面值去读。

### 发现四：成功随专业知识上升，收益主要集中在低端

在全部成功度量上，会话里表现出的专业知识越多，会话越可能成功。新手评级的会话达到最严格的核实成功标准的比例是 15%，至少部分成功的比例是 77%；中级及以上评级的会话达到核实成功的比例是 28%–33%，至少部分成功的比例是 91%–92%。

收益的分布是不均匀的：从新手到中级的跃升最大，中级到专家之间斜率变平。报告的说法是，领域里“够用”的能力就抓住了大部分好处，深度的专精只在之外再加一点。

正文强调，这个比较已经做了控制：比较的是做同种工作、同样估计价值、同一个月、同类任务、同一职业组的人之间，专业知识不同带来的结果差异。附录表 A1 的回归就是这套控制的落实。

### 发现五：遇到麻烦时，专家更容易恢复，新手更容易放弃

在中途遇到麻烦的会话里，达到核实成功的比例从新手的 4% 上升到专家的 15%（已做上述全部控制）。用较宽松的度量，至少部分成功的比例新手是 60%，中级到专家是 80%–81%。

反过来，看失败的一面：新手用户在遇到麻烦的会话里，有 19% 最终放弃——也就是被判断为失败、并且一行代码都没写；其他所有级别的人放弃的比例是 5%–7%。报告的解读是，专业知识的一部分价值，在于有能力把智能体引向正确的方向。

### 发现六：职业的重要性不如专业知识

软件相关职业的人总体核实成功率约 30%，其他职业的人约 26%。在产出代码的会话里（至少增改一行代码），这两个数字是 34% 与 29%。用较宽松的成功定义，差距进一步缩小：产出代码的会话里，两组至少部分成功的比例分别是 89% 与 88%。

这个约五分的差距在七个月里既没有扩大也没有缩小，尽管两组的成功率都在上升。在数据里最大的十个职业中，每一个与软件工程师的成功率差距都在七分以内。管理职业的核实成功率最高，略高于软件工程职业。报告对这一点留了个口子：管理者的高成功率可能反映了管理技能向指挥智能体的迁移，也可能部分反映了度量本身——核实部分依赖记录里用户的明确肯定，而管理者可能更倾向于在得到想要的东西时说出来。

报告的要点部分把这个发现说得更强：“在编码任务上，每个主要职业的成功率都与软件工程师几乎相同。”正文的数字是 30% 对 26%（总体）、34% 对 29%（产出代码的会话），读的时候应以正文的数字为准。

### 发现七：分类器的验证——与遥测一致，与强模型大体一致，但没有人类 ground truth

附录花了相当篇幅验证分类器，因为整篇报告的结论都建立在模型打的标签上。验证分三条线。

第一，分类器与遥测的交叉核对。被分类器标为新建或修改代码的会话，超过 90% 在遥测里确实有代码改动。成功信号与失败信号也按预期方向追踪独立的结果判断：被判断为成功的会话比例，从成功信号 1 分时的 13% 上升到 5 分时的 90%；从失败信号 1 分时的 85% 下降到 5 分时的 3%。

第二，内部结果验证。作者把同样的分类器提示词跑在 Anthropic 内部的 Claude Code 会话上，那里的会话 ID 可以关联到可观察的工程结果（会话的提交是否合并进了主分支）。专业知识–成功梯度在这份样本上复现了，包括同一工程师内部的比较（比较同一个人在不同评级会话里的表现）：在作者固定效应的设定下，判断成功率大约每升一级专业知识上升 3–5 个百分点，并且评级更高的会话更可能产出最终合并的代码。

第三，强模型一致性验证。作者把报告的分类器（用报告里用的模型）在 SWE-chat 的 198 场会话上重跑一遍——SWE-chat 是来自公开 GitHub 仓库、跨多个工具的真实编码智能体会话公开数据集。再用一个强参考模型（Mythos Preview）给同样的会话打标签，把参考模型的标签当作可靠、一致的 ground truth 代理。分歧由一个盲法评判员（同样是 Mythos Preview）逐一裁决，区分是真正的歧义（两种标法都说得通），还是报告分类器的明确错误；最后一位作者盲法复核了所有被标为“值得关注”的分歧。

结果是：分类变量上，报告的分类器与参考模型在 78%–98% 的会话上一致；有序量表上，算相邻分值也算一致时一致率是 78%–99%，只算精确匹配时是 53%–68%。评判员认为绝大多数分歧是真正的歧义——每类分类器上“值得关注”的分歧只占 0%–3% 的会话（198 场里最多 5 场）。最后一步人工复核了 15 场被评判员标为值得关注的分歧，复核者同意了其中 11 场的裁决。

作者自己的结论是谨慎的：验证结果令人鼓舞，但提醒不要过度解读任何一个单独的标签；报告的大多数结论建立在相对比较（组间差异、随时间的变化）上，在这些比较上分类器更可靠——前提是分类器的错误在各组之间是相似的，而这一点作者承认没有充分验证。

## 四、作者的结论与局限

作者的结论有三条。第一，人机分工是清晰的：人做约 70% 的规划决定、只做约 20% 的执行决定；人决定建什么，智能体决定怎么建。第二，成功取决于使用者带来什么：领域专业知识越多，会话越可能成功、越能从麻烦中恢复、越不容易放弃；收益主要集中在新手到中级之间，中级到专家的差距不大。第三，职业背景的重要性不如专业知识：在编码任务上，每个主要职业的成功率都与软件工程师接近（总体核实成功率约 30% 对约 26%）；管理职业的核实成功率甚至略高于软件工程职业。

作者自述的局限，博客结尾列了三条。第一，**测不到真实世界的结果**。不知道会话里写的代码之后是被用了还是被丢弃了，也不知道它是否产出了有经济价值的制品。第二，**排除了非交互式使用**。无头调用与 SDK 调用占了相当大的一块活动，本报告不覆盖它们；为非交互式使用开发度量框架是未来工作的优先事项。第三，**所有分类都依赖模型读记录**。附录里展示了分类器按预期方向追踪独立遥测、并与强参考模型在多数会话上一致，但作者承认，大规模验证分类器仍然困难，Claude Code 会话可能太长、太复杂，以至于人类标签无法充当 ground truth。

作者还给出了两个“接下来看什么”的风向标。第一，如果专业知识的回报开始下降，那就意味着模型开始提供目前由用户带来的关键判断，工具的好处正在向领域专家之外扩散。第二，如果软件职业之外的人成功完成编码会话的份额继续增长，那就可能意味着软件生产正在成为每个领域日常工作的一部分，而不是单一职业的产品。这两个变化会改变谁从智能体编程中受益、受益多少，并影响劳动市场上什么最受重视。

## 五、精读点评

### 这篇工作好在哪里

先说优点。第一，规模与诚实度是匹配的。约 40 万次会话、23.5 万人、七个月的窗口，这是一份关于真实使用情况的罕见大数据；报告没有把它包装成因果结论，而是老老实实地按描述与相关性来写。附录的坦率程度尤其值得肯定：任务价值估计器的验证数字（log R² 只有 0.38、小任务高估 2.4 倍、大任务低估 7 倍、5,000 美元以上档内区分度基本为零）是直接不利于作者自己的数字，但作者原样公布了，还明确说这些估计只能作序数比较。

第二，验证工作做得比同类报告认真。分类器与遥测的交叉核对（超过 90% 的代码标签有遥测佐证、成功信号与结果判断按预期方向单调变化）、强模型一致性验证（198 场 SWE-chat 会话、盲法裁决、人工复核），以及最关键的一条——在 Anthropic 内部会话上用真实工程结果（提交是否合并进主分支）锚定专业知识–成功梯度，包括同一工程师内部的比较。这第三条验证是全篇最强的效度证据：它把一条建立在“模型读记录打分”上的梯度，接到了一个模型之外的真实结果上。

第三，报告对自己的度量保持了警惕。管理职业成功率最高的那一段，作者当场就指出了度量本身的可能偏差（核实部分依赖用户在记录里明确肯定，而管理者可能更倾向于说出来）。这种“在报出一个抓眼球的数字的同时立刻指出它可能只是度量偏差”的写法，是诚实报告的标志。

### 需要较真的问题

第一，**“专业知识”和“成功”是同一个模型读同一份记录打出来的分，这是全篇最承重的效度问题。** 专业知识分类器看的三个信号——表述具体程度、验证类型、纠正方向——与成功分类器看的证据（用户肯定、测试通过、提交代码）在同一份记录里是纠缠在一起的。一场会话里用户越是纠正 Claude、越是提出针对性的验证要求，专业知识评分就越高；而这些行为本身也正是成功会话里更可能出现的行为。换句话说，梯度的一部分可能不是“专业知识导致成功”，而是“成功会话的记录看起来更像专家写的”。作者用内部会话的真实合并结果部分缓解了这个担忧（梯度在真实结果上复现了），但内部样本的规模、构成与选择方式都没有报告，缓解的程度无法评估。

第二，**专业知识评级与会话长度、任务难度纠缠在一起。** 专家会话每条提示引发 12 个动作、3,200 词输出，新手只有 5 个动作、600 词——但这既可以读作“专家能让 Claude 做更多工作”，也可以读作“更长的会话给了分类器更多证据来打出高分”。一场会话越长，分类器看到用户纠正 Claude、提出针对性验证的机会就越多，专业知识评分自然越高。报告没有控制会话长度对专业知识评级本身的影响（表 A1 第 6 列控制了会话长度对成功率的影响，但那是另一回事）。同样，专家可能本来就接了更难、更大的任务——任务价值控制用的是一个 log R² 只有 0.38 的粗糙估计器，控制得并不干净。

第三，**职业分类的推断本身就有系统性偏差的风险。** 约 30% 的会话推不出职业、被排除在职业分析之外；能被推断出职业的会话，恰恰是记录里职业信号最明显的那一部分。职业之间的比较（软件 30% 对其他 26%）建立在这个被选择过的子集上。如果某些职业的人更倾向于在记录里留下职业信号、或更倾向于明确肯定 Claude 的工作，职业间的差距就会被扭曲。报告没有报告被排除的 30% 会话的成功率，所以这个选择偏差的大小无从判断。

第四，**任务价值的百分比建立在很粗糙的估计器上。** “平均会话价值上升 27%”这个数字，来自一个在留出样本上 log R² 只有 0.38、且偏差随价格区间反转的估计器（小任务高估约 2.4 倍、大任务低估约 7 倍）。作者自己说这些估计只能作序数比较，但“上升 27%”是一个基数比较，不是序数比较——如果 10 月和 4 月的任务构成不同（而报告恰恰显示构成变了：修复减少、操作与分析增加），估计器的区间依赖性偏差就可能把构成变化误读成价值变化。更何况要点部分的“约 25%”与正文的“27%”本身就不一致，两个数字里至少有一个是约数或口径不同。

第五，**样本的选择性没有被充分讨论。** 样本是 Claude Code 的现有用户——已经选择使用这个工具、并且留下来继续用的人。那些试过一次就放弃的人、那些从来不用的人，都不在样本里。七个月里观察到的“使用向端到端智能体工作移动”“任务价值上升”，既可以是用户学会了更好地用工具，也可以是用户构成变了（新手流失、重度用户留下）。报告没有分解“同一批用户的行为变化”与“用户构成变化”，所以时间趋势的解读要打折扣。

第六，**没有人类 ground truth，验证用的是另一个模型。** 强模型一致性验证的参考标准是 Mythos Preview——另一个模型，而不是人类判断。作者明确质疑人类标签是否还能充当复杂会话的 ground truth，这个质疑本身是合理的；但用模型验证模型，存在系统性共享偏差的风险：如果报告的分类器与参考模型犯的是同一种错误（例如都把“用户说了很多专业术语”当作专业知识），一致率会虚高。评判员也是同一个参考模型，裁决分歧时同样可能共享偏差。人工复核只覆盖了 15 场分歧、同意了 11 场，样本太小，起不到独立仲裁的作用。

### 科学问题还原：这篇工作真正移走了哪块石头

这篇工作的反常起点不是“智能体能写代码”——那是已知的。反常在于，**关于“谁能用好智能体”的常识可能是错的**：人们默认会写代码的人才能用好编程智能体，但真实使用数据里，决定成败的似乎是对问题本身的理解，而不是编程技能。反常不在于模型的能力，而在于能力与使用者之间的匹配关系——同样的模型、同样的问题，交给不同的人，结果差很多，而差的维度不是职业头衔。

不解决这个问题，关于智能体时代劳动市场的讨论会继续停留在两个极端之间：要么认为“人人都能靠智能体写代码了”，要么认为“只有程序员能用好它”。两种说法都错在把“会不会写代码”当成了关键变量。对实践来说，雇主会误判该招什么样的人、该培训什么技能；对领域来说，关于“智能体替代什么、奖励什么”的判断会建立在错误的变量上。

为什么之前没做？卡住的点是数据与隐私：要回答“真实使用中谁成功、为什么成功”，需要大规模的真实会话记录，但这些记录是用户的私人工作内容，不能直接读。blocker 是“没有可在不侵犯隐私的前提下分析真实使用的手段”。这篇工作的办法是隐私保护分析基础设施——模型读记录、只输出聚合数字，研究者本人从不直接读任何一份会话。移走的石头是这个基础设施，而不是某个统计技巧。

方法与问题的匹配点在于，分类器框架恰好对应它要回答的问题：工作模式回答“做什么”，决策归属回答“谁在做决定”，专业知识评级回答“使用者带来了什么”，成功度量回答“做成了没有”。但这个方法也有一个内在的上限：它只能回答“在记录里看起来是怎样的”，回答不了“真实世界里是怎样的”——代码写完之后是被用了还是被丢弃了，报告自己承认不知道。方法与问题的匹配在这里断了：要回答后者，需要把会话记录关联到真实世界的结果，而这正是隐私保护分析做不到的（除了 Anthropic 内部会话那个小样本）。

答案改变了什么？认知上，它确立了一个初步的、但有数据支撑的判断：智能体编程工具正在替代实现性的工作，同时奖励对问题有扎实理解的人；“够用”的领域能力就抓住了大部分好处，深度专精只在之外再加一点。实践上，它给出了一个可以直接照做的建议：培训与招聘的重心应该从“会不会写代码”转向“懂不懂要解决的问题”——因为前者正在被智能体吸收，后者才是人机协作里人不可替代的部分。改变有限的地方在于，它没有证明专业知识“导致”成功（观测数据、同一记录打分），也没有证明这个模式在 Claude Code 之外、或在非交互式使用里同样成立——所以这篇工作的结论是“真实使用数据里呈现出这样一幅图景”，不是“专业知识就是成功的原因”。

### 为什么链：为什么专业知识多的人更成功

最承重的主张是：会话里表现出的专业知识越多，会话越可能成功，新手核实成功率 15%，中级及以上 28%–33%。往下追一层：为什么会这样？报告给出的最近原因是两个相互补充的机制。第一，专家能让 Claude 每次提示做更多工作（12 个动作、3,200 词输出，对新手的 5 个动作、600 词），因为专家给出的指令更具体、验证要求更有针对性，Claude 不需要在猜测意图上浪费轮次。第二，专家在遇到麻烦时更能把智能体引回正轨：遇到麻烦的会话里，专家核实成功率 15%、新手只有 4%，新手放弃率 19%、其他人 5%–7%。这两个机制都有数字支撑，而且方向一致。

再往下追一层：为什么“更具体的指令”和“更有针对性的验证”会带来成功？这里报告没有直接检验，但附录的分类器定义给出了线索：专业知识的三个信号里，针对性验证（知道该检查什么）与纠正方向（抓住 Claude 的领域错误）本质上都是“知道正确答案长什么样”的能力。一个人如果不知道对账规则在月末结账时有个边界情况，他就不可能发现 Claude 在那里犯了错；反过来，一个知道边界情况的人，不仅能发现错误，还能给出修正的方向。所以机制的核心可能是“验证能力”——不是“会不会写代码”，而是“知不知道什么算对”。这个解释在报告里是隐含的，没有被实验直接检验。

还有一层值得追：为什么收益主要集中在新手到中级之间、中级到专家之间斜率变平？报告没有给出机制层面的解释。一个合理的推测是，验证能力存在一个门槛：过了“能发现明显错误、能给出明确指令”这个门槛，额外的领域深度带来的边际收益就小了——因为 Claude 本身已经能处理执行层面的细节，人的作用主要是守住方向与验证，而守住方向不需要无所不知。但这只是分析者的推测，报告没有检验它；另一种可能纯粹是度量造成的——五级量表在高端的区分度不足（精确匹配一致率只有 53%–68%），中级、高级、专家之间的标签噪声可能把真实的梯度抹平了。这两种解释预测不同：如果门槛解释是对的，那么在更难的任务上，中级与专家的差距应该重新拉大；如果标签噪声解释是对的，差距在任何任务上都拉不大。报告没有做这个区分。

### 四维价值 verdict

认知价值：中等偏高。它推翻了一个具体的、被广泛持有的信念——“会写代码的人才能用好编程智能体”——并用约 40 万次真实会话的数据给出了一个替代的判断：决定成败的是对任务领域的理解，而且“够用”的能力就抓住了大部分好处。如果这篇工作不存在，关于智能体时代什么技能值钱的讨论会继续停留在轶事与基准分数上。扣分项是，核心结论的因果含义很弱：观测数据、同一记录打分，梯度的一部分可能只是度量纠缠。

方法价值：中等偏高。它留下了一个可复用的框架：用隐私保护的分类器分析真实使用数据，描述“做什么、谁在做决定、做得成不成”——工作模式、决策归属、专业知识评级、核实成功这四个度量，别人可以直接搬到其他智能体工具、其他领域的使用分析上。附录公开了全部的分类器提示词，这一点尤其有价值。扣分项是，框架的验证用的是另一个模型而不是人类 ground truth，别人复用时同样要面对“模型验证模型”的问题。

边界价值：比较清晰。作者明确说了适用边界：只覆盖交互式使用（CLI、桌面应用、claude.ai），不包括第三方 IDE、SDK 与无头调用；测不到真实世界的结果；所有分类都依赖模型读记录。最容易误读的推论是“专业知识导致成功”——正确的读法是“在记录里，专业知识评级高与成功相关”；另一个容易误读的推论是“任务价值上升了 27%”——那个数字来自一个很粗糙的估计器，只能作序数比较。

启示价值：中等偏高。它使“在不侵犯隐私的前提下研究真实使用”成为一个具体的研究方向，也使“专业知识的回报会不会随模型变强而下降”成为一个可以追踪的风向标。最便宜的决定性实验是：**在 Anthropic 内部会话上，把专业知识–成功梯度与更多真实工程结果关联起来**——不只看提交是否合并，还要看合并的代码在生产环境里活了多久、有没有被回滚、有没有引发事故；判据是梯度是否在这些更硬的结果上复现。如果复现，观测到的梯度就从“记录里的相关”升级为“真实结果上的相关”；如果不复现，核实成功这个度量本身就要被重新审视。这个实验成本不高（内部数据已经存在、分类器已经写好），信息量大，而且能直接决定这篇工作的核心结论值不值得作为劳动市场的证据来对待。

### 效度评分

内部效度 2 分（满分 5 分）：这是观测研究，没有随机化、没有对照组，专业知识与成功都是模型对同一份记录的判断。作者用固定效应回归控制了工作种类、任务价值、月份、主题与职业组，但这些控制没有解决最核心的纠缠——专业知识评级本身就是从同一份记录里读出来的。内部会话的真实结果验证部分缓解了这个问题，但那个样本的规模与构成没有报告。

外部效度 2 分：结论只对“Claude Code 的交互式使用、2025 年 10 月到 2026 年 4 月、现有用户”成立。换别的工具、别的模型、非交互式使用、或不用这个工具的人群，结论是否成立，报告没有给出可以外推的依据。样本是自我选择的使用者，那些试过就放弃的人不在样本里。

构念效度 3 分：核心构念“专业知识”有明确的操作化——五级量表、三个信号、附录里逐级的定义与示例；“核实成功”也有明确的操作化——判断成功加至少一个硬信号。但“专业知识”这个构念本身没有被完全操作化：它量的是用户在记录里表现出来的样子，而不是用户真实的能力；一场会话里用户表现得像专家，可能是因为任务简单、也可能是因为 Claude 犯了很多容易纠正的错误。同样，“成功”量的是记录里看起来成功了，不是真实世界里成功了。

统计结论效度 3 分：样本量极大，回归用了用户聚类的标准误，控制逐列加入、首选设定明确，验证数字（log R²、一致率、信号单调性）都如实报告。但表 A1、表 A2 的系数数字在本次提取的附录文本中未能核对；任务价值估计器的验证显示其区分度有限；“上升 27%”与要点“约 25%”不一致。

可复现性 2 分：分类器提示词在附录里完整公开，方法描述足够详细，一个能干的读者可以按描述重建分析框架；但数据不公开（隐私原因）、代码未公开，别人无法直接重跑标题数字。验证用的参考模型 Mythos Preview 也不是公开可用的标准。

总体判断：这是一份规模很大、报告诚实、但因果含义很弱的描述性观测报告，结论是“真实使用数据里，人做规划、智能体做执行，领域专业知识（而不是编程技能）与成功相关”——这个描述性结论站得住，因为样本大、验证做了多条线、作者对度量的局限很坦率。但它的适用范围比标题看起来要窄：它没有证明专业知识导致成功，没有覆盖非交互式使用，也没有触及真实世界的结果。置信度中等：核心事实（分工比例、工作构成变化、成功率梯度）可信，因为样本量大、分类器与遥测一致、内部真实结果部分锚定了梯度；但关于“专业知识就是成功的原因”“任务价值上升了多少”这类判断，置信度应下调——这些问题这篇工作没有回答，有些数字建立在很粗糙的估计器上。

### 证伪器

- 主张“专业知识评级越高，会话越可能成功”的证伪器：用同样的分类器跑另一家公司的智能体编程工具的真实使用数据（或 Claude Code 非交互式使用的数据），如果成功率梯度消失或反转，该主张的普适性即被修正。
- 主张“职业背景的重要性不如专业知识”的证伪器：在职业推断覆盖率更高的样本上重跑职业比较（例如用用户自报职业而不是记录推断），如果软件职业与其他职业的差距扩大到远超五分，该主张即被修正。
- 主张“任务价值在七个月里上升了约四分之一”的证伪器：用不依赖模型定价的价值代理（例如任务的市场价格、完成任务所需的人工工时）重算，如果上升消失，该主张即被修正。

### 替代解释

替代解释一：专业知识–成功梯度不是“专业知识导致成功”，而是“成功会话的记录看起来更像专家写的”。预测差异：如果这个解释是对的，那么在那些 Claude 本身很少犯错、用户几乎没有机会纠正它的任务上，梯度应该变小或消失——因为没有纠错机会，专家与新手在记录里的表现就分不开了。区分实验：按 Claude 在会话里的错误率分层，看梯度是否随错误率变化。报告没有做这个实验；它的内部真实结果验证部分反驳了这个解释，但那个样本的规模与构成没有报告，不能完全排除。

替代解释二：梯度反映的是任务选择，而不是能力。预测差异：如果这个解释是对的，那么专家评级的用户接的任务本身就更容易成功（例如他们更会把大任务拆成小任务、更会挑 Claude 擅长的事），而在固定任务难度的条件下，梯度应该变小。区分实验：用任务难度的独立度量（例如任务的客观复杂度、而不是模型估计的价值）作控制，看梯度是否还存在。报告用模型估计的任务价值作了控制，但那个估计器的 log R² 只有 0.38，控制得不干净，所以这个替代解释没有被排除。

### 作者自述局限 vs 分析者发现的局限

作者自述的局限（测不到真实世界的结果、排除了非交互式使用、所有分类都依赖模型读记录）见上一节。分析者发现的、作者没有明说的局限有五条。第一，专业知识与成功是同一个模型对同一份记录的判断，两者纠缠，梯度的因果含义存疑；内部真实结果验证只部分缓解了这个问题，且样本细节未报告。第二，专业知识评级与会话长度、任务难度纠缠，报告没有控制会话长度对评级本身的影响。第三，职业分析排除了约 30% 推不出职业的会话，选择偏差的大小无从判断。第四，任务价值估计器的验证数字很弱（log R² 0.38、偏差随价格区间反转、5,000 美元以上档内区分度基本为零），“上升 27%”这个基数比较超出了作者自己说的“只能作序数比较”的适用范围；要点与正文的 25% 与 27% 也不一致。第五，样本是自我选择的使用者，七个月的时间趋势没有分解“同一批用户的行为变化”与“用户构成变化”。

### 接下来看什么

排第一的是启示价值里的最便宜的决定性实验：在 Anthropic 内部会话上，把专业知识–成功梯度与更多真实工程结果关联起来——不只看提交是否合并，还要看合并的代码在生产环境里活了多久、有没有被回滚、有没有引发事故。判据是梯度是否在这些更硬的结果上复现：如果复现，观测到的梯度就从“记录里的相关”升级为“真实结果上的相关”；如果不复现，核实成功这个度量本身就要被重新审视。这个实验比任何新的模型评估都更值得先做，因为它决定了这篇工作的核心结论值不值得作为劳动市场的证据来对待。

其次看两件事。一是区分“专业知识导致成功”与“成功会话看起来更像专家写的”：按 Claude 在会话里的错误率分层，看梯度是否随错误率变化——这个实验能直接检验度量纠缠的程度。二是看作者是否兑现“为非交互式使用开发度量框架”这个承诺：下一篇相关工作里有没有覆盖无头调用与 SDK 调用、有没有报告那部分使用的构成与成功率——如果有，说明这幅使用图景正在补全；如果没有，说明它还停留在交互式使用这一半。

## 六、§I 结论、结果与价值总览

一句话结论：约 40 万次真实 Claude Code 会话显示，人做约 70% 的规划决定、只做约 20% 的执行决定，任务领域的专业知识（而不是会不会写代码）与会话成功相关——新手核实成功率 15%，中级及以上 28%–33%——但“专业知识”和“成功”都是同一个模型读同一份记录打出来的分，这是一份描述性观测报告，没有证明因果。

核心结论：

1. 人机分工是清晰的：人平均做出约 70% 的规划决定、约 20% 的执行决定；典型会话约 4 轮，每条用户提示平均引发 Claude 约 10 个动作、约 2,400 词输出。置信度高，证据是博客“谁决定什么”一节的报告与遥测交叉核对。
2. 专业知识越多，每条提示引发的工作越多：新手每提示约 5 个动作、约 600 词，专家 12 个动作、3,200 词。置信度中等，证据是博客“专业知识水平”一节；会话长度与评级的纠缠没有被排除。
3. 工作构成在七个月里从修 bug 转向端到端的智能体使用：修复份额从 33% 降到 19%，操作从 14% 升到 21%，写作与数据分析从约 10% 升到约 20%。置信度高，证据是博客“工作”一节的月度份额。
4. 成功随专业知识上升，收益主要集中在低端：新手核实成功率 15%，中级及以上 28%–33%；至少部分成功新手 77%，中级及以上 91%–92%。置信度中等，证据是博客“成功取决于使用者带来什么”一节与附录表 A1、A2；表 A1、A2 的系数数字本次未能逐项核对。
5. 遇到麻烦时专家更容易恢复、新手更容易放弃：遇到麻烦的会话核实成功率新手 4%、专家 15%，放弃率新手 19%、其他人 5%–7%。置信度中等，证据同上。
6. 职业的重要性不如专业知识：软件相关职业核实成功率约 30%，其他职业约 26%；产出代码的会话 34% 对 29%；十个最大职业与软件工程师的差距在七分以内。置信度中等，证据是博客“职业的重要性可能不如专业知识”一节；约 30% 会话职业未分类、被排除在比较之外。
7. 任务价值的估计很粗糙：平均会话估计价值在七个月里上升了 27%（要点写约 25%），但估计器在留出样本上 log R² 只有 0.38，小任务高估约 2.4 倍、大任务低估约 7 倍。置信度低，证据是附录“任务价值估计器”一节的验证数字。
8. 作者承认的局限是：测不到真实世界的结果、排除了非交互式使用、所有分类都依赖模型读记录；并给出两个风向标（专业知识的回报是否下降、软件职业之外的人成功完成编码会话的份额是否继续增长）。置信度高，证据是博客“展望”一节与附录的验证章节。

科学价值总评：认知价值中等偏高——推翻了“会写代码的人才能用好编程智能体”这个信念，给出了真实使用数据里的替代判断，但因果含义弱。方法价值中等偏高——留下了隐私保护的使用分析框架与完整公开的分类器提示词，但验证用的是另一个模型而不是人类 ground truth。边界价值比较清晰——作者明确说了适用边界，最容易误读的是把“专业知识与成功相关”读成“专业知识导致成功”，以及把“任务价值上升 27%”当作精确的美元度量。启示价值中等偏高——最便宜的决定性实验是在内部会话上把梯度与更硬的真实工程结果关联起来。总体 verdict：这篇工作值得因为它用约 40 万次真实会话描出了智能体编程在实践中的分工图景、并给出了“领域专业知识比编程技能更重要”这个有数据支撑的初步判断而被记住；但读的时候应该把“记录里呈现出的相关”与“真实世界里的因果”分开——前者这篇工作回答了，后者它没有回答。

适用边界：这篇工作不证明专业知识导致成功，不证明任务价值真的上升了 27%（那个数字来自很粗糙的估计器），不证明结论在 Claude Code 之外、非交互式使用里、或不用这个工具的人群里同样成立，也不证明会话里写的代码在真实世界里被用了还是被丢弃了。任何人都不应该拿“新手 15%、中级以上 28%–33%”去论证“培训领域知识就能把成功率翻倍”——那是观测到的相关，而且两个数字都来自同一个模型对同一份记录的判断。它的正确用法是作为一幅描述性图景：智能体正在吸收实现性的工作，同时奖励对问题有扎实理解的人；以及作为一个可追踪的风向标——如果专业知识的回报开始下降，说明模型开始提供目前由用户带来的关键判断。
