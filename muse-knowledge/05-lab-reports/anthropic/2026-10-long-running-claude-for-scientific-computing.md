## 一、背景与问题

### 从“每步都盯着”到“放手让一队智能体干活”

现在大多数科学家用 AI 智能体的方式，还是对话循环：每一步都紧紧盯着，亲自管。过去一年左右，模型在长程任务上的表现显著变好了，于是出现了一种新的工作方式：只定高层目标，然后放一队智能体自主干活。这样一来，原本要花几天、几周甚至几个月才能完成的项目，现在几小时就能做完。

适合这种模式的科学任务有三个特征：工作范围明确、成功标准清楚、人类监督可以是偶尔的，而不是持续的。作者举了三类例子：重写一个数值求解器、把用古老 Fortran 方言写的遗留科学软件转成现代语言、拿着参考实现给一个大代码库排错。

Anthropic 的 C 编译器项目就是这种模式的一个版本：Claude 在大约 2,000 个会话里，从头写出一个能编译 Linux 内核的 C 编译器。这篇博文讲的是怎么把类似的模式搬到科学计算任务上，设想的读者是一个典型的学术实验室。

### 具体例子：一个作者本人并不专精的任务

作者拿一个具体例子贯穿全文：用 Claude Opus 4.6 实现一个可微版本的宇宙学 Boltzmann 求解器。这是一种数值代码，预测大爆炸余晖——宇宙微波背景（CMB，Cosmic Microwave Background）——的统计性质。它通过演化光子、重子、中微子和暗物质在早期宇宙中的耦合方程来做到这一点。

Boltzmann 求解器，比如 CLASS 和 CAMB，是宇宙学的核心科学基础设施，让研究者能用 Planck 和 Simons Observatory 这类巡天的数据来约束宇宙学模型。可微版本——能把梯度传过整个求解器——可以使用基于梯度的推断方法，大幅加速参数估计。用 JAX 来写是很自然的选择，因为它免费提供自动微分和加速器（比如 GPU）兼容性。

值得注意的是，这个任务不在作者的核心科学领域内。他对工具和科学有高层面的熟悉，但没有自己在合理时间内完成它的专业知识。而有专业知识的团队已经用 JAX 写过具备 CLASS 部分功能的可微求解器，这些工作通常代表数月到数年的研究者时间。这篇博文的着眼点是：一个非领域专家，只做最少的引导，智能体能不能走得更远。

### 这个任务和 C 编译器项目结构上不一样

作者明确指出，Boltzmann 求解器和 C 编译器项目在结构上不同。C 编译器可以分给大量并行智能体去做；Boltzmann 求解器则是一个深度耦合的流水线——早期宇宙复合过程建模里一个小小的数值误差或糟糕的近似，会微妙地改变下游的一切。

所以它需要另一套智能体技能。排错需要沿着整条链因果追踪，并调用领域知识，这更适合一个智能体按顺序工作、按需生成子智能体、并用参考实现来二分定位差异。

计算环境是一台运行 SLURM 作业调度器的 HPC 集群，但作者说核心思路——进度文件、测试预言机、规则明确的智能体提示词——不依赖在哪里运行 Claude Code。

## 二、方法与设计

这篇博文没有实验设计，只有一套工作流程。下面按博文自己的顺序讲这套流程。

### 先在本地把计划打磨好，写进 CLAUDE.md

转向“管理一队自主研究智能体”之后，作者认为人应该把大部分时间花在打磨一套指令上：在和 Claude 商量之后，清楚写出项目的交付物和相关背景。这些指令住在项目根目录下一个叫 CLAUDE.md 的文件里。Claude 会特别对待这个文件，把它留在上下文里，作为总体计划的参考。关键是，Claude 在工作过程中也可以编辑这些指令，在解决问题的同时为今后的工作更新它们。

博文链接了一份早期的 CLAUDE.md，展示总体计划和设计决策，是在第一次尝试写求解器之后成文的。作者先定下高层目标——在完全可微的前提下，与参考实现 CLASS 达到全部功能对等，并且在主要科学交付物上达到相对 CLASS 0.1% 的精度目标——然后和 Claude 反复迭代，直到计划看起来令人满意。0.1% 这个目标不是随便定的：它正是两款经典 Boltzmann 代码 CLASS 和 CAMB 之间典型的符合水平，所以算一个合理的科学目标。

### 跨会话记忆：一份进度文件就是实验笔记

进度文件，按惯例在这里叫 CHANGELOG.md，是智能体的便携长期记忆，起实验笔记的作用。CLAUDE.md 里指示 Claude 把进度记在这个文件里。

一份好的进度文件会记录当前状态、已完成的任务、失败的尝试以及它们为什么没成、关键检查点的精度表、已知的局限。其中失败的尝试很重要——没有它们，后续会话会重新尝试同样的死胡同。博文给了一个条目例子：“试过用 Tsit5 解微扰 ODE，系统太刚性，换成了 Kvaerno5。”博文链接了这个项目的实际 changelog，展示这些要素。

### 测试预言机：智能体得有办法知道自己有没有进步

更开放的、由智能体主导的科学发现在地平线上，但今天的长程自主科学工作关键取决于一点：智能体得有办法知道自己有没有在进步。对科学代码来说，这个办法可以是一个参考实现、一个可清晰量化的目标，或者一套已有的测试集。让智能体在工作时扩充测试集并持续跑测试也很有帮助，可以防止回归。

在这个例子任务里，Claude 被指示用 CLASS 的 C 源码作为参考实现，构建并持续运行单元测试。

### Git 协调：提交就是进度可见性

Git 是以不插手的方式监控与协调智能体进度的好办法。智能体应该在每完成一个有意义的工作单元后提交并推送。这样一来，万一出了问题就有一份可恢复的历史，进度在本地可见，而且即使计算配额在会话中途用完，工作也不会丢失。

实际做法可以是写进 CLAUDE.md 的一组指令，例如：“每完成一个有意义的工作单元就提交并推送。在每次提交前运行 `pytest tests/ -x -q`。绝不提交会破坏已有通过测试的代码。”

要引导智能体，可以随时 SSH 进集群，手动重新提示，或者更新它的指令。作者说，通常更顺手的做法是让本地的一台 Claude Code 替你 SSH 进去跑命令；下面讲的所有做法也都适用。

### 执行循环：在 tmux 里让它自己跑，偶尔看一眼

先在本地把计划迭代到看起来合理、并编码进 CLAUDE.md 之后，就可以在计算节点上用 tmux 这类终端复用器开一个 Claude Code 会话，告诉智能体代码库在哪，然后让它自己干。因为会话跑在 tmux 里，你可以断开、合上笔记本，偶尔回来检查进度。作者在做 Boltzmann 求解器时，会在等咖啡排队之类的间隙里在手机上看 GitHub 上的进展。

在 HPC 集群上，你可以通过 SLURM 申请一个节点。作业启动后，attach 进 tmux 会话，给 Claude Code 指方向（比如“读 CHANGELOG.md，接着做下一个任务”），确认它走在正确的轨道上就可以 detach。想检查、引导或开新任务时，随时可以重新 attach。

**Ralph 循环（Ralph loop）：**随着模型能力变强，它们需要的定制编排（比如提示词工程、RAG、往上下文里塞东西）越来越少。但在某个时间点，提供一定程度的脚手架仍然能提升能力。比如现在的模型会犯“智能体惰性”（agentic laziness）：被要求完成一个复杂的多部分任务时，有时会找个借口在做完之前就停下来（“天色已晚，明天再继续吧？”）。

绕开这个问题的办法，是一个有用的编排模式——Ralph 循环，本质上是一个 for 循环：当智能体宣称完成时，把它踢回上下文里，问它是不是真的做完了。这对长程任务很有用，因为智能体会承认任务还没达到要求，然后继续干下去。其他类似的模式还包括 GSD、特定领域的变体，以及 Claude Code 原生的 /loop 命令。

Ralph 可以通过 /plugin 安装。Claude Code 里一个典型的调用提示词是让 Claude 最多迭代 20 次，直到它用一句 "DONE" 咒语保证任务完成。

### 假设与未报告项

这篇博文的承重假设有几个。第一，科学任务的成功标准可以事先说清楚、并写成可检查的测试——没有这个假设，整套“放手让智能体跑”的做法就立不住；博文开篇就把适用范围划在这个条件上。第二，参考实现 CLASS 是对的——智能体对照 CLASS 排错，等于默认 CLASS 的输出就是 ground truth；如果 CLASS 本身在某个 regime 有问题，智能体会被带偏，博文没有讨论这一点。第三，进度文件加 Git 提交足以在多天、多会话里保持连贯性——博文的证据只有一个案例，没有对照。

未报告或说不清的项：这个项目一共开了多少个会话、跑了多少天、总共花了多少 token 或多少算力（只说“数日”、C 编译器项目“大约 2,000 个会话”，本项目没有给会话数）；Ralph 循环实际触发了多少次、有没有真的防止过早停工；精度走势图的逐项数值；0.1% 的精度目标最终有没有达成——博文只说“亚百分之一”，没有说是否达到了 0.1%；智能体在哪些具体环节上花了多少时间。

## 三、主要发现

### 结果：几天时间，从零做到亚百分之一精度

Claude 在几天里从零开始做这个项目，在各输出上达到了与参考实现 CLASS 亚百分之一（sub-percent）的符合程度。作者让 Claude 重建了项目过程中代码主要输出——各种 CMB 角功率谱——的精度，并标注了开发过程中的里程碑。它产出了一张图，展示通往亚百分之一精度的路径。图的逐项数值只在图里，正文没有给出。

### 智能体的开发轨迹有点笨拙

作者坦白，智能体的开发轨迹有点笨拙。比如测试覆盖有明显的缺口——有一段时间它只在一个单一的（基准，fiducial）参数点上测试代码，大幅缩小了它能发现 bug 的范围。它也会犯初级错误，比如在规范约定（gauge conventions）上绊倒，或者花几个小时追一个宇宙学家一眼就能看出来的 bug。但它一直在朝着亚百分之一精度这个既定目标持续取得进展。

### 一个副产品：作者顺带学了不少宇宙学

这个项目的一个副产品是，作者通过看 git 提交历史，学到了出乎意料多的关于 Boltzmann 求解器和它所建模的物理的知识。这个项目不是从他的核心科学领域里来的，但跟着 Claude 循序渐进的进展、查自己不认识的东西，成了一种有效的、潜移默化学习科学的办法。提交记录读起来像一份来自行动迅速、极其字面的博士后的实验笔记。

### 坦白的局限：还不是生产级

作者明确说，得到的求解器还不是生产级的：比如在每个 regime 上，它与参考实现 CLASS 的符合程度都没有达到可接受的精度。但它证明了，智能体驱动的开发可以把数月甚至数年的研究者工作压缩到几天里。

### 空闲时间的含义变了

这种压缩改变了“空闲时间”算什么。AI 研究里一个普遍体验是：晚上启动一个实验（比如一次训练），早上起来看到结果，很满足；不跑这个实验是有机会成本的。现在，不跑智能体也感觉有成本了：如果你有算力，又有成功标准明确的项目，那么每个晚上不让智能体替你干活，都是被留在桌上的潜在进展。

## 四、作者的结论与局限

作者的结论有三条。第一，对范围明确、成功标准清楚的科学任务，这套长程工作模式是成立的：写好计划、留好记忆、立好测试预言机、用 Git 协调、放进 tmux 里跑，偶尔检查一次就行。第二，智能体驱动的开发可以把数月甚至数年的研究者工作压缩到几天里——在这个例子里，一个非领域专家在几天内拿到了一个亚百分之一精度的可微 Boltzmann 求解器。第三，这种压缩改变了空闲时间的含义：有算力、有成功标准明确的项目时，每个晚上不让智能体干活，都是被留在桌上的潜在进展。

作者自述的局限，散落在结果一节里，有三条。第一，得到的求解器还不是生产级的，在每个 regime 上与 CLASS 的符合程度都没有达到可接受的精度。第二，智能体的开发轨迹有点笨拙：测试覆盖有缺口（有一段时间只在一个基准参数点上测试），会犯初级错误（规范约定、追着宇宙学家一眼能看出的 bug 花几小时）。第三，这个任务在结构上需要单智能体按顺序工作、按需生成子智能体，不像 C 编译器项目那样能分给大量并行智能体——也就是说，这套做法不是对所有任务都一样的，任务结构决定了编排方式。

## 五、精读点评

### 这篇博文到底证明了什么，又没证明什么

先说优点。这篇博文最可贵的地方是它老实、具体。它没有把一个案例包装成一种通用方法，而是把适用条件写在最前面：范围明确、成功标准清楚、监督可以是偶尔的。它也没有藏拙：测试覆盖的缺口、初级错误、还不是生产级，这三点都写在正文里。而且它给出的东西是可以直接拿走照抄的——CLAUDE.md、CHANGELOG.md、测试预言机、Git 提交规则、tmux 加 SLURM、Ralph 循环，每一步都有具体做法，不是口号。

但有几个地方需要较真。第一，正文里没有一条可以核查的逐项精度数字。唯一的 headline 结果是“亚百分之一精度”，而精度走势图的逐项数值只在图里。读者读完正文，只知道“达到了亚百分之一”，不知道在哪个输出上是多少、哪个 regime 最差、里程碑之间是怎么爬上去的。一篇以“精度”为核心证据的文章，正文却不给精度数字，这是最大的呈现短板。

第二，目标与结果之间有一道没有交代的缝。计划里定的目标是主要科学交付物上相对 CLASS 达到 0.1%，结果一节说的却是“亚百分之一”。亚百分之一可以是 0.9%，也可以是 0.05%——博文没有说 0.1% 的目标到底有没有达成。仓库 README 在博文之后给出了更细的数字（未透镜化 TT/EE 亚 0.2%），但那是仓库在继续改动之后的状态，不能当成博文发表时的结果来读。目标定得清楚、结果报得含糊，这个落差值得点名。

第三，这是一个 n=1 的案例研究，没有对照。没有“不用这套流程会怎样”的比较，没有“换一个科学代码、换一个非领域专家能不能复现”的证据。作者本人既是实验者又是汇报者，任务又是他自己挑的——挑的恰恰是一个适合这套模式的任务（有现成的参考实现 CLASS、有清晰的精度目标）。这不等于结论是错的，但等于结论的适用范围没有经过检验。

第四，成本没有报告。多少个会话、多少 token、多少算力、多少 wall-clock 时间、作者本人在引导和纠错上花了多少小时——正文一个数字也没给。“把数月到数年的工作压缩到几天”这个说法，分子是“几天”的智能体工作，分母是“数月到数年”的研究者时间，两边量的不是同一种东西：前者没有计入作者本人的引导时间、等候时间、以及智能体犯初级错误所浪费的算力。没有成本数字，压缩比就没法认真评估。

第五，六个做法里哪一个真正起了作用，博文没有分离。CLAUDE.md、CHANGELOG.md、测试预言机、Git、tmux、Ralph 循环——这六个要素是打包出现的。读者无法从正文判断：如果拿掉其中一个（比如没有 Ralph 循环、没有进度文件），结果会不会变差、变差多少。这篇博文的定位是手记，不是实验，所以这个缺口可以理解，但读的时候应该把它记下来，而不是默认六个要素同等重要。

### 科学问题还原：这篇工作真正移走了哪块石头

这篇工作的反常起点不是“模型变强了”，而是“科学家还在用对话循环的方式管智能体，而模型已经能胜任长程任务了”——工作方式落后于模型能力，中间隔着一套没人写下来的做法。

不解决这个问题，科学家会继续把时间花在每一步盯着智能体上，而模型明明可以在几小时里走完几天、几周甚至几个月的工作。更具体地说，一个非领域专家想做一个领域的科学计算任务时，过去的选项只有两个：自己花几个月学，或者找领域专家合作；这篇博文想打开第三个选项：让智能体去做，人只负责定目标和偶尔检查。

之前没法回答，是因为缺一个办法：既没有一套写下来的、普通实验室能照抄的流程，也没有一个具体的、从零到可用的示范。作者的办法是拿自己做实验：挑一个自己并不专精、但有明确参考实现和精度目标的任务，完整走一遍流程，再把流程写下来。这个办法的巧妙之处在于，它把“长程智能体能不能做科学计算”这个抽象问题，转化成了“一个非领域专家能不能在几天内拿到一个亚百分之一精度的求解器”这个可观测的问题——后者是可以回答的，前者是开放的。

方法与问题的匹配点在于，流程里的每一个要素都恰好对应长程工作里一个具体的失败模式：CLAUDE.md 对应“目标会漂移”，CHANGELOG.md 对应“跨会话会忘事、会重复踩同一个坑”，测试预言机对应“不知道自己有没有进步”，Git 对应“进度不可见、出错不可恢复”，tmux 对应“人不能一直守着”，Ralph 循环对应“模型会找借口提前停工”。六个要素各管一摊，合起来才构成一个能放手跑的系统。

答案改变了什么？认知上，它没有改变任何科学认知——Boltzmann 求解器的物理没有新发现，CLASS 和 CAMB 也没有被挑战。改变的是工作方式上的认知：对范围明确、成功标准清楚的任务，“放手让智能体跑几天、偶尔检查”是一个可行的选项，而且一个非领域专家也能靠它拿到可用的科学代码。实践上，它给出了一份可以直接照抄的清单。改变有限的地方在于，它没有证明这套做法在没有参考实现、没有清晰精度目标的任务上也成立——作者自己把适用范围划在了这个条件上，超出这个范围，结论就不适用。

### 为什么链：为什么这套做法能成立

最承重的主张是“长程智能体可以把数月到数年的科学计算工作压缩到几天”。往下追一层：为什么它能成立？博文给出的最近原因是两个具体的机制：第一，任务有一个可检查的成功标准——对照 CLASS 的精度目标，智能体随时可以知道自己对不对，不需要等人来判断；第二，记忆与协调机制让工作可以在多天、多会话里不断线——进度文件记住了失败的尝试，Git 记住了每一步，tmux 让会话一直活着。这两个机制合起来，让“放手跑几天”从一个冒险变成了一个可管理的流程。

再往下追一层：为什么“对照参考实现”这个条件这么关键？这里有一个分叉，博文没有完全分开。一种解释是，参考实现提供了 ground truth——没有它，智能体就不知道自己有没有进步，整个流程的第一块基石就没了。另一种解释是，参考实现提供的其实是“可分解的排错路径”——智能体可以拿着 CLASS 的 C 源码一段一段对照，用二分法定位差异，排错才变得可行。如果第一种解释是对的，那么任何能给出可检查成功标准的东西（比如一套已有的测试集、一个可量化的目标函数）都可以替代参考实现；如果第二种解释是对的，那么替代品必须还得提供“一段一段对照”的能力，单纯一个分数是不够的。博文没有做“换掉参考实现、只留一个分数”的对照，所以这两条解释目前是分不开的。

还有一层值得追：为什么是“几天”而不是“几小时”？博文没有给出时间分解，但从它的描述里能看到两个耗时的来源：智能体自己的笨拙（测试覆盖缺口、初级错误、追着一眼能看出的 bug 花几小时），以及人机之间往返的等待（作者偶尔才检查一次）。前者是模型能力的上限，后者是工作方式本身的代价——放手跑的代价就是反馈变慢。这两个来源加起来，才是“几天”这个数字的真实含义，而博文没有把它们分开算。

### 四维价值 verdict

认知价值：低。它没有推翻或确认任何科学信念，也没有给出新的科学发现。如果这篇博文不存在，宇宙学不会少知道什么，Boltzmann 求解器的物理也不会有任何不同。它的认知贡献在工作方式层面，不在科学层面。

方法价值：中等偏高。它留下了一套别人能直接拿走的东西：一份可复制的长程智能体工作流程——CLAUDE.md、CHANGELOG.md、测试预言机、Git 提交规则、tmux 加 SLURM、Ralph 循环，每一步都有具体做法和一个真实项目的示范。任何一个有明确成功标准的科学计算任务，现在都有了一个现成的起点。方法价值的上限取决于这套流程能不能被用到没有参考实现的任务上——博文没有展示这一点，而且它的六个要素没有经过分离检验，读者拿走的是一套打包的做法，不知道哪一个要素最关键。

边界价值：清晰，这是全篇做得最好的部分之一。作者明确说了适用边界：只适用于范围明确、成功标准清楚、监督可以是偶尔的任务；得到的求解器还不是生产级的；这个任务需要单智能体按顺序工作，不像 C 编译器项目那样能并行分包。最容易误读的推论是“智能体现在能替科学家做科研了”——作者明确说了不是，这个任务有现成的参考实现和精度目标，而且作者本人全程在引导和检查。另一个容易误读的推论是“几天就等于数月到数年”——两边量的不是同一种东西，成本没有报告。

启示价值：中等。它使“长程智能体科学计算”成为一个具体的研究与实践方向：把这套流程用到第二个科学代码、另一个领域、另一个非领域专家身上，看它能不能复现。最便宜的决定性实验是：找一个同样有参考实现和清晰精度目标、但属于另一个领域的科学计算任务，让一个非领域专家按这套流程从零做起，事先登记精度目标，并完整记录会话数、token 数、算力与人的引导时间。如果复现成功，说明这套流程的价值不依赖于宇宙学这个特例；如果复现失败、或者成本远高于“几天”的说法，说明这篇博文的结论只对这一个案例成立。这个实验成本低（复用已有流程与公开仓库），信息量大，而且能直接决定这套流程值不值得作为科学计算的工作方式来推广。

### 效度评分

内部效度 2 分（满分 5 分）：这是一个 n=1 的案例研究，没有对照组、没有消融、没有“不用这套流程会怎样”的比较。六个流程要素打包出现，哪个起了作用无法分离。作者本人的引导时间没有报告，无法排除“结果其实是人引导出来的、而不是智能体自主做出来的”这个混杂。

外部效度 2 分：结论只对“有参考实现、有清晰精度目标、范围明确的科学计算任务”成立。换一个没有参考实现的任务、换一个没有明确精度目标的任务、换一个领域，流程里的测试预言机这一环就立不住，整套做法是否还成立是未知的。作者自己也把适用范围划在了这个条件上。

构念效度 3 分：“工作被压缩了”这个构念的操作化是“从零到亚百分之一精度花了几天”——这个操作化是清晰的，但它只量了“智能体花了几天”，没有量“人花了多少引导时间、多少算力、多少等待时间”。两者之间的差距，就是“几天”这个说法与真实成本之间的差距，博文没有量这个差距。

统计结论效度 1 分：正文没有给出任何一条逐项精度数字，没有样本量、没有误差棒、没有统计检验——因为它本来就不是一个实验，而是一份手记。读者能相信结果的方向（做出了一个亚百分之一精度的求解器），但不应该把“亚百分之一”读成一个精确的数字，更不应该把它读成“达到了 0.1% 的目标”。

可复现性 3 分：博文把流程、指令文件、仓库链接都公开了，一个有能力的读者可以按描述重建这套工作方式，仓库里的 CLAUDE.md 与 CHANGELOG.md 也是公开的。但复现“这个结果”需要的不只是流程——还需要同样的模型版本、同样的提示词历史、同样的计算环境，而这些在博文里没有完整记录。复现流程的思路是可能的，复现具体结果需要拿到作者没有完整公开的材料。

总体判断：这是一份定位诚实、做法具体、界限划得清楚的长程智能体工作法手记，问题问得准（科学家的工作方式落后于模型能力）、流程给得全（六个要素各管一个失败模式）、局限写得坦白（还不是生产级、轨迹笨拙、只适用于有参考实现的任务），值得因为它留下了一套可照抄的流程而被记住。但它的证据比看起来要薄得多：n=1，没有对照，没有成本数字，正文没有给任何一条逐项精度数字，0.1% 的目标有没有达成也没有交代。置信度中等偏低：核心事实（几天内做出了一个亚百分之一精度的求解器、仓库是公开的）有多处相互印证的证据支撑；但“压缩比有多大”“六个要素里哪个最关键”“这套流程能不能用到别的任务上”，置信度应下调。

### 证伪器

- 主张“这套流程能把数月到数年的科学计算工作压缩到几天”的证伪器：在另一个领域、另一个有参考实现和清晰精度目标的任务上，让一个非领域专家按这套流程从零做起、并完整记录成本，如果花的时间与有经验的研究者手工完成相当、或者根本做不出来，该主张即被修正为“压缩只在宇宙学 Boltzmann 求解器这一个案例上成立”。
- 主张“测试预言机是长程工作成立的关键”的证伪器：拿掉参考实现、只留一个可量化的目标分数重做同一任务，如果智能体仍然能在几天内达到同样的精度，该主张即被修正为“可检查的成功标准就够了，不一定需要参考实现”。
- 主张“Ralph 循环能防止智能体提前停工”的证伪器：关掉 Ralph 循环重做同一任务，如果智能体同样能走完、不提前停工，该主张即被修正为“提前停工在这个任务上本来就不是问题”。

### 替代解释

替代解释一：几天做出来的不是“智能体的工作方式变好了”，而是“这个任务本来就适合智能体”。任务有现成的参考实现 CLASS、有清晰的 0.1% 精度目标、有成熟的 JAX 生态——这三个条件加起来，任务已经被转化成了一个“对照着抄、抄完再测”的工程问题。预测差异：如果这个解释是对的，那么换一个没有参考实现的任务，同一套流程应该做不出来。区分实验：拿掉参考实现重做——博文没有报告这个对照。

替代解释二：压缩比被夸大了，因为“几天”没有计入人的引导时间与智能体的浪费。作者在本地迭代计划、偶尔检查、纠正方向上花的时间，以及智能体追着一眼能看出的 bug 花的几小时，都没有被算进“几天”里。预测差异：如果这个解释是对的，那么完整记录人的引导时间与算力之后，压缩比会大幅缩水。区分实验：完整记录成本——博文没有报告这个数字。

替代解释三：结果的真正驱动力不是六个流程要素，而是模型本身（Claude Opus 4.6）足够强。换一个弱一点的模型，同一套流程可能做不出来。预测差异：如果这个解释是对的，那么换模型重做，精度或耗时应该大幅变差。区分实验：换模型重做同一任务——博文没有报告这个对照。

### 作者自述局限 vs 分析者发现的局限

作者自述的局限（还不是生产级、开发轨迹笨拙、任务结构决定了编排方式）见上一节。分析者发现的、作者没有明说的局限有五条。第一，正文没有给任何一条逐项精度数字，所有逐项精度只在图里，读者无法核查“亚百分之一”到底是多少。 第二，0.1% 的精度目标有没有达成没有交代，目标与结果之间有一道缝。第三，这是一个 n=1 的案例研究，没有对照、没有消融，六个流程要素里哪个最关键无法分离。第四，成本没有报告——会话数、token 数、算力、人的引导时间一个数字也没给，“压缩比”没法认真评估。第五，参考实现 CLASS 被默认是对的，博文没有讨论“如果参考实现本身在某个 regime 有问题，智能体会怎样”。

### 接下来看什么

排第一的是启示价值里的最便宜的决定性实验：在另一个领域、另一个有参考实现和清晰精度目标的科学计算任务上，让一个非领域专家按这套流程从零做起，事先登记精度目标，并完整记录会话数、token 数、算力与人的引导时间。判据是复现的精度与成本：如果复现成功，说明这套流程的价值不依赖于宇宙学这个特例；如果复现失败、或者成本远高于“几天”的说法，说明这篇博文的结论只对这一个案例成立。这个实验比任何新的模型评估都更值得先做，因为它决定了这套流程值不值得作为科学计算的工作方式来推广。

其次看两件事。一是成本记录：下一次类似的长程智能体项目，应该完整记录人的引导时间与算力成本——没有成本数字，“压缩比”就只是一个修辞。二是要素分离：拿掉其中一个流程要素（比如没有 Ralph 循环、没有进度文件）重做，看结果会不会变差——这能告诉读者六个要素里哪一个是真正承重的。
