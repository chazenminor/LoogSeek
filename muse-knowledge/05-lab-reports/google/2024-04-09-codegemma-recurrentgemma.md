## 一、背景与问题

### 公告之前是什么局面

2024 年 2 月，Google 发布了 Gemma，一个轻量级开放模型家族，用的是造 Gemini 的同一套研究与技术，有 2B 和 7B 两个尺寸。社区反响热烈，出现了不少微调变体、Kaggle 笔记本和工具集成。

Gemma 有两个明显的缺口。第一，它是个通用模型，没有为写代码专门优化过：代码补全要的是低延迟、能往中间填代码，不是通用对话。第二，它的架构就是标准 Transformer，推理时要把键值缓存（KV cache，key-value cache）整个存在显存里，序列越长缓存越大，采样越慢，内存越吃紧。

2024 年 4 月 9 日的公告一次补了这两个缺口，推出了 Gemma 家族的第一批变体：面向开发者的 CodeGemma（代码补全、生成与对话）和面向研究者的 RecurrentGemma（一个非 Transformer 的高效架构）。同一天还发布了 Gemma 1.1，对原有两个模型做了性能改进和问题修复，并放宽了使用条款。

所以这篇东西要回答的其实是两个不同的问题。代码模型的问题是：一个开放的轻量模型能不能在补全速度和代码质量上同时做到够用？循环架构的问题是：不用全局注意力，模型能不能在性能不掉的前提下，把推理的内存和吞吐问题解决掉？

## 二、方法与设计

先说清楚这批文档的性质。它是一次产品发布加两份技术报告，不是同行评审论文，也不是一项实验。按论文意义上的实验设计，它没有假设检验，没有随机化，没有预注册。下面按每份文档本来面目来评估它。

### CodeGemma 是怎么做的

CodeGemma 没有改架构。它直接拿 Gemma 的预训练模型继续训练，用的是同一套 Gemma 架构。v1.0 的三个模型都在 5000 亿 token 的数据上继续训练，数据以英文网页、数学和代码为主。2B 的 v1.1 训了 1 万亿 token。2B 模型训的是 100% 代码，7B 模型是 80% 代码加 20% 自然语言。代码语料来自公开代码库，做了去重和过滤，滤掉了评测代码的污染和部分个人敏感数据。

预训练模型用中间填充（FIM，fill-in-the-middle）任务训练：给一段代码的前缀和后缀，让模型填中间。填充率在多数模型里是 80%，2B v1.1 是 90%。模型同时支持两种排列：前缀–后缀–中间（PSM，prefix-suffix-middle）和后缀–前缀–中间（SPM，suffix-prefix-middle）。格式用四个控制 token 区分：`<|fim_prefix|>`、`<|fim_suffix|>`、`<|fim_middle|>` 和文件分隔符 `<|file_separator|>`。

报告还做了一个针对真实仓库场景的处理：多文件打包（multi-file packing）。很多代码任务要看整个仓库，不只一个文件。作者用两种启发式方法把相关的源文件拼进同一条训练样本：一种按依赖图打包，从文件顶部的 import 提取依赖、算最短路径、拓扑排序；另一种按单元测试做词法打包，把测试文件挨着它的实现文件放。

指令微调（instruction tuning）只做了 7B 模型。训练数据是 Gemma 微调数据的底子，加上开源数学数据集和合成代码指令数据。数学部分用了 MATH、GSM8K、MathQA 和程序生成的代数题，目的是补逻辑推理，因为推理能力对代码生成有帮助。代码指令数据按 OSS-Instruct 的做法合成问答对，再用一个语言模型筛掉没用或错误的问答。7B 指令版的 v1.1 与 v1.0 的区别，在于强化学习算法换成了基于 Gemma 1.1 的版本，以及合成数据的生成细节不同。

评估分四块：代码补全（HumanEval Infilling 的单行与多行指标）、代码生成（HumanEval、MBPP、跨语言的 BabelCode）、自然语言与数学推理（问答、常识、GSM8K、MATH），以及实用层面的部署建议。补全速度的测量条件写得很具体：用 Hugging Face Transformers 实现，在 g2-standard-4 的 GCE 实例上，bfloat16 精度，batch size 为 1，给每个 HumanEval Infilling 任务生成 128 个 token 的续写，单行任务 1033 个，多行任务 5815 个，时间是全部任务的总耗时。

### RecurrentGemma 是怎么做的

RecurrentGemma 的核心是 Griffin 架构（Griffin architecture），来自 De 等人 2024 年的论文。Griffin 不要全局注意力，改用两样东西的混合：线性循环（linear recurrences，具体是 RG-LRU，一种门控线性循环单元）处理长距离依赖，局部注意力（local attention）处理短距离的精细模式。局部注意力窗口是 2048 个 token。报告对 Griffin 只做了一处改动：输入嵌入乘上一个等于模型宽度平方根的常数；输入和输出嵌入是 tied 的，但输出那头不乘这个因子。

两个尺寸的超参是：2B 版总参数 2.7B（非嵌入 2.0B、嵌入 0.7B），宽度 2560，循环宽度 2560，MLP 扩展因子 3，深度 26 层，注意力头 10 个；9B 版总参数 8.58B（非嵌入 7.53B、嵌入 1.05B），宽度 4096，深度 38 层，注意力头 16 个。词表都是 256k，用的是 Gemma 同款 SentencePiece 分词器。词表这么大，嵌入层占了总参数里相当大的一块。

训练用 8192 个 token 的序列，两个尺寸都训了 2T token。数据与 Gemma 相同，主要是英文网页、数学和代码，滤掉了不安全言论、个人敏感数据和全部评测集。和 Gemma 一样，先在通用混合数据上训，再在一份更小、更高质量的数据上继续训。训练细节里提到的两点是：循环层（RG-LRU）的参数不加权重衰减（weight decay）；对平方根运算反向传播时，导数裁剪到最大值 1000，以保证稳定。

指令微调沿用 Gemma 的做法，包括一种新的 RLHF（基于人类反馈的强化学习）算法，对话格式用 `<start_of_turn>` 和 `<end_of_turn>` 控制 token 区分用户和模型回合。

评估分四块：18 项学术基准；人类评估，拿指令微调版去对 Mistral 7B v0.2 Instruct 打分，指令遵循约 1000 条提示，安全约 400 条提示；推理速度基准；安全学术基准。人类评估报告了胜、平、负的拆分和 95% 置信区间，平局均分后算胜率。

速度基准的测量条件也写得很具体。2B 在单块 TPUv5e 上测，9B 在单块 TPUv4 上测，用的是 Flax 实现加一个专用的 Pallas 核，在 TPU 上跑线性循环。采样吞吐的定义是：从 2k token 的提示出发，采样不同长度的序列，每秒能采多少 token，不计提示处理时间和把 token 编号转回文本的时间。作者自己也提醒，用 PyTorch 实现或在 GPU 上跑，吞吐会低一些。对照的 Gemma 推理用的是作者改过的 Gemma Flax 实现，而且作者说还特意做了进一步优化。

### 统计、算力与可得性

统计方面，两份报告都没有报告种子、运行次数和误差棒，只有人类评估给了 95% 置信区间。学术基准的数字都是单次运行的结果，没有不确定性。

训练算力方面，两份报告都没有报告硬件数量、训练时长和 FLOPs。CodeGemma 的模型卡提到训练用的是 TPUv5e，但那是模型卡里的信息，不是技术报告正文。优化器、学习率、batch size 这些超参，两份报告正文里都没有给出。CodeGemma 报告没有写上下文长度。

可复现性方面，RecurrentGemma 发布了 JAX 代码（包括 TPU 用的 Pallas 核）和一个 PyTorch 参考实现，仓库在 GitHub 上；CodeGemma 的权重和模型卡发布在 Kaggle、Hugging Face 和 Vertex AI Model Garden。训练数据本身没有发布，只有"与 Gemma 相同""公开代码库"这类描述。

按 NeurIPS / Pineau 检查表，下面这些项在两份报告里都是"未报告"：种子、运行次数、误差棒、训练算力、学习率等超参、解码设置、评估框架版本。CodeGemma 报告没有单独的局限一节；RecurrentGemma 报告也没有单独的局限一节，局限只在责任部署一段里提了一句。

## 三、主要发现

### 公告说了什么

公告把 CodeGemma 定位成开发者的代码助手，有三个变体：7B 预训练版，专做代码补全和生成；7B 指令微调版，做代码对话和指令遵循；2B 预训练版，做本地快速补全。公告说它训在 5000 亿 token 的英文网页、数学和代码数据上，能补全行、函数甚至整块代码，支持 Python、JavaScript、Java 等主流语言。

公告把 RecurrentGemma 定位成研究者的效率模型。它用循环神经网络加局部注意力，换来三点好处：内存占用更低，能在单 GPU 或 CPU 这类内存有限的设备上生成更长的样本；吞吐更高，因为内存省下来了，可以用更大的 batch，一次生成更多 token，尤其在生成长序列时；研究价值上，它证明非 Transformer 模型也能达到高性能。

公告还配了两张图。一张是 CodeGemma 与同类模型在单行与多行代码补全上的对比表，一张是 RecurrentGemma 与 Gemma 的最大采样吞吐对比曲线，提示长度 2k token，在 TPUv5e 上测。两张图里的数字在抓取到的页面文本里都没有，只能看图，见本节末尾的台账说明和文末未核实清单。

公告最后说，两个模型当天起就能在 Kaggle、Hugging Face 和 Vertex AI Model Garden 上拿到，支持 JAX、PyTorch、Hugging Face Transformers 和 Gemma.cpp，能跑在笔记本、台式机、NVIDIA GPU 和 Google Cloud TPU 上。CodeGemma 还额外支持 Keras、NVIDIA NeMo、TensorRT-LLM 和 Vertex AI。Gemma 1.1 同日发布，做了性能改进和问题修复，使用条款也放宽了。

### CodeGemma：代码能力确实上去了，补全速度是卖点

先看代码生成。HumanEval 上，2B 预训练版 31.1%，2B v1.1 是 37.8%，7B 预训练版 44.5%，7B 指令版 56.1%，7B 指令版 v1.1 是 60.4%。基线 Gemma 2B 预训练版是 22.0%，Gemma 7B 预训练版是 32.3%。MBPP 上，五个 CodeGemma 变体分别是 43.6%、49.2%、56.2%、54.2%、55.2%，基线 Gemma 2B 是 29.2%，Gemma 7B 是 44.4%。也就是说，继续训练确实把代码生成能力拉起来了，而且 7B 指令版 v1.1 是全家最高的。

再看代码补全，这是 2B 模型的卖点。HumanEval Infilling 单行指标上，2B 预训练版 78.41%，2B v1.1 是 79.28%，7B 预训练版 76.09%，7B 指令版 68.25%，7B 指令版 v1.1 是 77.44%。多行指标上，2B 预训练版 51.44%，2B v1.1 是 50.99%，7B 预训练版 58.44%，7B 指令版只有 20.05%，7B 指令版 v1.1 是 23.66%。

这里有个值得停下来看的现象：指令微调版的多行补全分数断崖式下跌，从 7B 预训练版的 58.44% 跌到 20% 出头。报告没有解释这一点。一个合理的推测是，指令微调没训过中间填充任务，模型学会了对话格式，却丢了往中间填代码的本事。报告没有验证这个推测，也没有给出任何消融。这意味着，7B 指令版并不适合拿来做补全；补全要用预训练版。

速度上，2B 预训练版确实快。在 128-token 续写、batch size 为 1 的条件下，单行任务总耗时 543 秒，多行任务 8479 秒；同级别的 DeepSeek Coder 是 990 秒和 13138 秒，StarCoder2 是 3665 秒和 20629 秒。报告的说法是，2B 模型在很多情况下比对手快将近一倍，而且质量没有明显妥协。这个"快将近一倍"只对 2B 预训练版成立：7B 预训练版单行 1505 秒、多行 22896 秒，与 DeepSeek Coder 的 1559 秒和 22387 秒基本打平。

多语言方面，BabelCode 翻译版的 HumanEval 上，7B 指令版 v1.1 在多数语言上都是全家最高。比如 Python 是 54.0%，C++ 是 46.6%，C# 是 54.7%，Java 是 50.3%。2B 预训练版在 Python 上只有 21.7%，小模型的跨语言生成能力明显弱一档。

数学推理是 CodeGemma 的一个意外亮点。7B 预训练版 GSM8K 44.2%、MATH 19.9%；7B 指令版 41.2% 和 20.9%；7B 指令版 v1.1 是 47.3% 和 22.3%。同级别的 DeepSeek Coder 是 43.2% 和 19.2%，StarCoder2 是 40.4%，MATH 未报告。报告把这个归功于指令微调里加的数学数据集。语言能力方面，报告用一张图对比了 CodeGemma 7B 与 Gemma 7B 指令版，结论是自然语言能力基本保留，7B 预训练版和指令版都比 Mistral 7B 高 7.2%，比 Llama-2 13B 高 19.1%。这两个百分比是报告正文的原话，图里的逐项分数没有以文字形式给出。

报告的实用建议很直白：2B 模型适合 IDE、本地环境和内存受限的场景；7B 模型适合托管部署和质量优先的场景。2B 模型对延迟敏感的补全任务是" exceptionally suitable"，7B 模型则胜在质量。

### RecurrentGemma：性能基本追平 Transformer，赢在推理速度

先看 2B 的学术基准。18 项基准的平均分，RecurrentGemma-2B 是 44.6，Gemma-2B 在 v1 里是 44.9，v2 重述为 45.0。差距在 0.4 个百分点以内。分项看，RecurrentGemma-2B 在 PIQA、SIQA、Boolq、Winogrande、ARC-c、BBH 上略高于 Gemma-2B，在 MMLU、GSM8K、TriviaQA、NQ 上低于它。落后最明显的是两项：MMLU 5-shot 是 38.4%，比 Gemma-2B 的 42.3% 低 3.9 个百分点；GSM8K 是 13.4%，比 17.7% 低 4.3 个百分点。代码基准基本打平：HumanEval 是 21.3% 对 22.0%，MBPP 是 28.8% 对 29.2%。

关键是训练量：RecurrentGemma-2B 只训了 2T token，Gemma-2B 训了 3T。也就是说，它用少一半的数据，拿到了基本相同的平均分。报告把这个解读为 Griffin 架构更数据高效。

9B 的数字只在 v2 里。18 项平均分是 56.1，Gemma-7B 是 56.9，差距 0.8 个百分点。分项里最亮眼的是 TriviaQA，70.5% 对 63.4%，高了 7.1 个百分点；最弱的是 MMLU，60.5% 对 64.3%，低 3.8 个百分点。GSM8K 是 42.6% 对 46.4%，也低了 3.8 个百分点。9B 只训了 2T token，Gemma-7B 训了 6T，是它的三倍。所以"少得多的数据、差不多的分数"这个说法，在 9B 上比 2B 上更成立。

人类评估上，RecurrentGemma-2B 指令版对 Mistral 7B v0.2 Instruct 的指令遵循胜率是 43.7%，95% 置信区间是 41.8% 到 45.6%；安全胜率是 59.8%，区间是 57.1% 到 62.6%。同条件下的 Gemma-1.1-2B 指令版是 45.0% 和 60.1%。两个模型对 Mistral 7B 都没赢下指令遵循，但都赢了安全项。9B 指令版的指令遵循胜率是 59.3%，区间是 57.4% 到 61.2%，安全胜率是 59.9%。9B 对 Mistral 7B 是两项都赢。

推理速度是 RecurrentGemma 真正的卖点。报告的结论是：采样吞吐不随序列变长而下降，而 Gemma 的吞吐随缓存变大而下降。提示处理速度两者相近，2B 模型约 4 万 token 每秒，9B 模型约 1.2 万 token 每秒。采样时，RecurrentGemma 约 6000 token 每秒，Gemma 明显更慢。9B 对 Gemma-7B 的提升最大，报告正文说"最高达两个数量级"，并马上补了一句：这主要是因为 Gemma-7B 用多头注意力（Multi-Head Attention），而 Gemma-2B 用多查询注意力（Multi-Query Attention）。也就是说，9B 那组对比里，对照组本身的缓存就比 2B 那组大得多。各长度下的逐点吞吐数值只在图 1 里，正文没有，见未核实清单。

安全基准上，2B 指令微调版比预训练版有好有坏。RealToxicity 从 9.8 降到 7.6（越低越好），TruthfulQA 从 35.1 升到 42.7，BOLD 从 39.3 升到 52.3。但也有变差的：BBQ 消歧项从 58.4 降到 50.8，Winobias 第二组从 90.0 降到 75.4，Toxigen 在 9B 上从预训练版的 58.8 升到指令版的 64.5（越低越好，也就是变差了）。指令微调并没有让所有安全指标一致变好。

## 四、作者的结论与局限

### 作者的结论

CodeGemma 报告的结论是：这组模型把代码补全与生成的水平推到了同级别开放模型的前列，同时保留了基底模型的自然语言能力。2B 模型是为延迟敏感的补全场景优化的，7B 模型是通用代码模型。报告最后说，Gemini 和 Gemma 的技术可以迁移到下游应用上，发布这些模型是为了让社区去建应用。

RecurrentGemma 报告的结论是：RecurrentGemma 在保持 Gemma 性能的同时，推理吞吐更高，尤其在长序列上。作者希望它能解锁资源受限环境下高性能小模型的新应用。

公告自己的结论更简单：Gemma 家族的第一批扩展到了，开发者有了代码模型，研究者有了高效架构，两个模型当天就能用。

### 作者自己说的局限

两份报告都没有单独的"局限"一节。最接近让步的，有下面几处。

RecurrentGemma 报告在责任部署一段里说：安全缓解措施沿用 Gemma 发布时的做法；模型经过了标准学术安全基准评估，发布前也经过独立团队的伦理与安全评估；但测试覆盖不了全部用例，建议用户在部署前针对自己的用例自行做安全测试。这等于承认，安全结论是暂时的、有条件的。

CodeGemma 报告的局限散见于实用考量一节：2B 和 7B 的取舍是部署取舍，不是能力高低；责任部署的详细讨论转引 Gemma 报告，不在这份报告里展开。

### 报告没有交代的事

CodeGemma 报告没有解释 7B 指令版多行补全暴跌的原因。它的真实世界评估（在仓库代码上随机遮掉片段再补、跑测试）用的是内部版本，不公开。模型在真实编码环境里与 Google 自有补全模型的对比，只提了一句，没有数字。

RecurrentGemma 报告没有展开 Griffin 架构本身的细节，全部推给 De 等人 2024 年的 Griffin 论文。长序列推理的评估只有吞吐，没有长上下文理解任务：它证明了生成长序列不慢，没有证明模型能理解长输入。9B 的人类评估安全胜率置信区间与 2B 的完全相同，都是 57.1% 到 62.6%，而胜率本身不同（59.9% 对 59.8%），这看起来像表格照抄，见未核实清单。

两份报告都没有训练算力、超参细节和统计不确定性。CodeGemma 的对照模型是 2024 年年中的同级开源代码模型，没有拿当时的闭源模型或更大模型做对照。RecurrentGemma 的对照只有一个：同尺寸的 Gemma。

## 五、精读点评

这一节是分析者的判断，和上面对报告的呈现分开写。

### 这次发布真正要回答的问题

这次发布拼了两个不同的问题，答案的质量也不一样。

CodeGemma 要回答的是一个工程问题：一个开放的轻量模型，能不能在补全速度和代码质量上同时做到够用？它的答案是分层的：2B 预训练版负责快，7B 指令版负责好。这个答案基本成立，数字也支持它。

RecurrentGemma 要回答的是一个架构问题：不用全局注意力的模型，能不能在性能不掉的前提下，把推理的内存墙解决掉？它的答案是：平均分上基本追平，吞吐上确实更快。这个答案也基本成立，但"基本追平"这个说法，比它听起来要弱一些。

### 科学问题还原：五问

**现象是什么？** 现象有两个。一个是，通用开放模型写代码不够好用：补全要低延迟，生成要懂仓库上下文，通用模型两头都不占。另一个是，Transformer 推理的内存随序列长度线性增长，KV 缓存成了长序列生成的瓶颈。反常不在某一次实验失败，而在两个缺口同时存在：开放模型家族里没有代码专家，也没有非 Transformer 的高效选择。

**为什么重要，不解决会怎样？** 对实践来说，不解决第一个问题，开发者要么用闭源代码助手，要么忍受通用开放模型在补全上的延迟和质量；不解决第二个问题，长序列推理只能靠堆显存，小模型在资源受限设备上跑不起来。对领域来说，如果开放模型家族里一直没有非 Transformer 的强基线，"Transformer 是唯一选择"这个默认就永远得不到检验。两个问题都不解决，不会有什么东西"错下去"，但开放生态会一直缺这两块拼图。

**为什么之前做不了？** 代码模型卡住的点不是方法不存在，而是没人把 Gemma 的底子往代码方向继续训够：中间填充训练、多文件打包、数学与合成指令数据的组合，是工程量的事，不是概念突破。循环架构卡住的点更实在：纯循环模型历史上一直比不过 Transformer，缺的是一个能把循环和局部注意力混好的具体配方。Griffin 论文给了配方，RecurrentGemma 是把这个配方做成开放模型的第一次尝试。所以两份工作的贡献性质不同：一个是把已知做法做到位，一个是把新架构验证到可用的程度。

**方法与问题是否匹配？** CodeGemma 的方法与问题基本匹配：要补全，就训中间填充；要懂仓库，就打包多文件；要推理，就加数学数据。每一处方法都对着一个具体需求。RecurrentGemma 的方法与问题也基本匹配：要省内存，就用固定尺寸的状态代替线性增长的缓存；要保性能，就用局部注意力补循环的短距离精度。匹配上有个缺口：报告用吞吐证明了"生成长序列不慢"，但没有用长上下文理解任务证明"理解长输入也不差"。方法回答的是效率问题，不是长上下文能力问题。

**答案改变了什么？** 认知上，RecurrentGemma 改变了一点东西：它证明了非 Transformer 架构在 2B 到 9B 这个尺寸上可以追平 Transformer 的平均分，而且用更少的训练 token。这个结论值得记住，但要加上限定：平均分追平不等于处处追平，MMLU 和 GSM8K 上它明显落后。实践上，CodeGemma 改变的是开放代码模型的选择面：2B 预训练版是一个真实可用的快速补全模型，7B 指令版 v1.1 是一个能用的代码对话模型。榜单意义上的"最优"宣称不应照单全收。

### 价值判断

认知价值是中等的。RecurrentGemma 确认了"循环加局部注意力可以追平 Transformer"这条路径的存在性，在 2B 和 9B 两个尺寸上都成立，而且训练 token 更少。这是一个真实的架构层面的证据，不是产品包装。但它没有确认机制：到底是循环本身更数据高效，还是 Gemma 基线训得不够、或者数据配比不同，报告区分不了。CodeGemma 的认知价值是低的：它没有提出新方法，只是把已知做法组合起来训了一个代码专家。

方法价值是中等的。RecurrentGemma 留下了可复用的东西：开源的 JAX 实现、TPU 用的 Pallas 核、PyTorch 参考实现，以及"固定尺寸状态加局部注意力"这个可照搬的配方。CodeGemma 留下的是可复用的做法：中间填充的训练细节、多文件打包的两种启发式、合成代码指令数据的流程。但两份报告都没有公开训练数据和完整超参，别人能拿走的是做法，不是可一键复现的配方。

边界价值是高的，这是这份精读记录最有价值的部分。它明确不证明的东西包括：RecurrentGemma 在长上下文理解上的能力、9B 在 4 月 9 日的发布状态、CodeGemma 指令版的补全能力、两份报告里任何数字的统计显著性。读者最容易误读的推论有两个：把"平均分追平"读成"处处一样好"，把"7B 指令版最强"读成"7B 指令版什么代码任务都最强"。边界写得越清，结论越可信。

启示价值在于，最便宜的决定性实验是等 token 对照训练：用相同的 token 数、相同的数据，训一个 Griffin 模型和一个 Transformer 模型，看平均分和 MMLU、GSM8K 这类短板项还差多少。具体设计在下面"接下来看什么"里写。

### 最弱的一环

最弱的一环在"性能相当"这四个字和它背后的对照之间。RecurrentGemma 的全部质量宣称，依赖于三件报告没有完全拿出来的东西。

第一，平均分掩盖了短板。18 项平均分只差 0.4 到 0.8 个百分点，但 MMLU 和 GSM8K 上落后 3.8 到 4.3 个百分点。平均分相等，不等于能力相等。MMLU 量的是知识密集的问答，GSM8K 量的是多步数学推理，这两项恰恰是固定尺寸状态最可能吃亏的地方：要把长知识链压进一个固定大小的状态里，信息会丢。

第二，对照不是等 token 对照。RecurrentGemma 训 2T token，Gemma-2B 训 3T，Gemma-7B 训 6T。数据量和架构两个变量同时变了，"更数据高效"的结论就混进了两种解释：可能是 Griffin 架构确实更高效，也可能是 Gemma 基线的数据配比或训练本身有浪费。报告没有跑等 token 的对照，区分不了。

第三，吞吐测量的实现不对称。RecurrentGemma 的数字来自作者写的 Flax 实现加专用 Pallas 核，对照的 Gemma 也是作者改过的实现。PyTorch 实现或 GPU 上的用户达不到这个数字，报告自己也承认了。9B 的"两个数量级"还有一层对照选择的问题：Gemma-7B 用多头注意力，缓存本来就大，而 Gemma-2B 用多查询注意力。同样是"对 Gemma"，2B 那组和 9B 那组的对照难度是不一样的。

CodeGemma 那边最弱的一环在"同级最优"的对照范围里。它的对手是 2024 年年中的开源代码模型，没有误差棒，没有闭源对照。HumanEval 上 7B 指令版 v1.1 的 60.4% 看起来很高，但 HumanEval 只有 164 道题，几个百分点的差距在统计上很脆弱。报告也没有报告任何一次运行的方差。

### 效度判断

下面是针对这两份报告作为证据的评分，满分 5 分，评的是证据，不是模型本身。

内部效度 2 分。两份报告都没有随机化、盲法和预注册，适用的威胁是基线不对称：RecurrentGemma 的对照不是等 token 的，CodeGemma 的对照是作者选的同级开源模型。测试集污染方面，RecurrentGemma 报告明确说了滤掉了评测集，CodeGemma 报告也说了去重和滤污染，这一点比很多公告强。给 2 分而不是 1 分，是因为评估程序至少部分有描述，测量条件写得具体。

外部效度 2 分。RecurrentGemma 从 18 项学术基准加一次吞吐测量，推广到"资源受限环境下的新应用"，但没有任何部署测量和长上下文理解任务。CodeGemma 从 HumanEval、MBPP 这类静态基准推广到"真实开发工作流"，但真实世界评估用的是内部版本，没有公开数字。能推广的是模型本身的可用性与速度事实。

构念效度 2 分。基准分被当作"代码能力""数学推理""语言理解"，人类评估胜率被当作"指令遵循能力"，吞吐被当作"推理效率"。每一步都是从分数跳到能力，中间没有桥接证据。吞吐那一步尤其值得警惕：采样吞吐不随长度下降，量的是生成速度，不是长上下文理解。

统计结论效度 1 分。两份报告都没有种子、运行次数和误差棒，只有人类评估给了置信区间。HumanEval 只有 164 道题，几个百分点的领先没有任何不确定性。MMLU 上 3.9 个百分点的落后同样没有不确定性，无法判断是不是噪声。

可复现性 2 分。RecurrentGemma 发布了 JAX 代码和 PyTorch 参考实现，CodeGemma 发布了权重和模型卡，这是加分项。但训练数据没有发布，超参没有给全，评估框架版本没有说明，别人很难一键重跑标题结果。

### 其他可能的解释

同一组数字，至少有三种别的解释也能说得通。

第一种是数据效率的归属问题。RecurrentGemma 用更少 token 拿到相近分数，报告的解释是 Griffin 架构更数据高效。另一种解释是，Gemma 基线的训练本身有浪费：3T 和 6T 的 token 里，可能有一部分对基准分数没有贡献，而 RecurrentGemma 的 2T 恰好是更精炼的数据配比。这种解释预测，等 token 对照下两者差距会缩小甚至反转。区分证据是等 token、等数据的对照训练。

第二种是状态压缩的代价被平均分藏起来了。RecurrentGemma 在 MMLU 和 GSM8K 上落后，可能是因为固定尺寸的状态在知识密集和多步推理任务上丢信息，而在常识、阅读理解这类任务上不受影响。这种解释预测，落后会集中在需要长程精确回忆的任务上，而不是均匀分布。区分证据是按任务类型拆分的误差分析，或者直接测长上下文回忆任务。

第三种是 CodeGemma 的提升来自数据而不是方法。CodeGemma 没有改架构，它的提升完全可以由"在 5000 亿到 1 万亿 token 代码数据上继续训练"来解释。中间填充和多文件打包可能有贡献，也可能只是锦上添花。这种解释预测，拿 Gemma 直接在同样数据上继续训、不用中间填充，也能拿到大部分提升。区分证据是一次消融：去掉中间填充和多文件打包，只做继续训练，看 HumanEval 和补全分数掉多少。

第四种是人类评估的胜率反映的是微调做法而不是架构。RecurrentGemma-2B 指令版和 Gemma-1.1-2B 指令版对 Mistral 7B 的胜率几乎相同（43.7% 对 45.0%），而它们的指令微调和 RLHF 做法是同一套。这说明，指令遵循能力可能主要由微调做法决定，架构差异在人类评估里根本没体现出来。

### 什么观察能反驳这些宣称

"性能相当"的宣称可以这样检验：等 token、等数据训练 Griffin 和 Transformer 各一个，看 18 项平均分和 MMLU、GSM8K 这类短板项。如果等 token 下 Griffin 明显落后，"更数据高效"的解释就被反驳了；如果平均分追平但 MMLU、GSM8K 仍然落后，"处处相当"就被反驳了，只剩下"平均相当"。

"吞吐优势"的宣称可以这样检验：用第三方实现（比如 Hugging Face Transformers 的标准实现）在 GPU 上重跑采样吞吐。如果优势大幅缩小甚至消失，"高效推理"的宣称就要加上"只在作者优化过的 Flax 加 TPU 实现上成立"这个限定。

"CodeGemma 同级最优"的宣称可以这样检验：在公开评估框架里重跑 HumanEval、MBPP 和 HumanEval Infilling，用固定提示和固定种子，对比同期其他开源代码模型。如果 7B 指令版 v1.1 的领先落进误差范围里，或者 2B 的速度优势在真实 IDE 负载下消失，宣称就被反驳了。

"7B 指令版是最好用的代码模型"的宣称可以这样检验：拿它做多行补全任务。如果分数仍然在 20% 出头，"最好用"就被反驳了，正确的说法是"最适合对话式代码生成，不适合补全"。

长上下文能力的宣称目前是不可反驳的，因为报告根本没有测长上下文理解。需要先补一个长上下文回忆或推理任务，才能写出反驳它的观察。

### 接下来看什么

最值得先做的，是等 token 对照训练。用相同的 2T token、相同的数据配比，训一个 Griffin 模型和一个 Transformer 模型，报告 18 项基准的逐项分数和误差棒。判据很简单：如果平均分追平且 MMLU、GSM8K 的差距消失，Griffin 更数据高效的说法就升级为可信；如果差距还在，"性能相当"就要降级为"平均分相当、知识与推理任务落后"。

其次是独立重跑 CodeGemma 的评估。在公开评估框架里，用固定提示和固定种子重跑 HumanEval、MBPP 和 HumanEval Infilling，对比同期开源代码模型，报告运行次数和方差。重点看两件事：7B 指令版 v1.1 的领先是不是在误差范围内，2B 的速度优势在 batch size 大于 1 时还剩多少。

再往后看三件事：RecurrentGemma 的长上下文理解评估，不只是吞吐，要测它在长输入上的回忆和推理；CodeGemma 的消融，去掉中间填充和多文件打包，看分数掉多少；Griffin 论文本身的细节，RecurrentGemma 报告把架构定义完全推给了那篇论文，读它才能判断循环部分的真正创新点。

最后是 9B 模型的后续。9B 是 2024 年 8 月才加进来的，它的数字来自修订版，不是 4 月 9 日的发布。后续有没有更大的 RecurrentGemma，或者 Griffin 架构有没有进 Gemini 主线，是判断这条路线有没有走下去的信号。

### 声称的贡献和实际支持的贡献

公告声称的贡献是 Gemma 家族的第一次扩展：开发者有了代码模型，研究者有了高效架构。文本本身支持的范围是：三个 CodeGemma 变体确实发布了，RecurrentGemma-2B 确实发布了，两个模型当天就能下载。

CodeGemma 报告声称的贡献是"同级别最优的代码补全与生成，同时保留自然语言能力"。文本支持的范围要窄一些：预训练版的补全和生成确实强，2B 确实快；但"最优"只在作者选的对照组里成立，指令版的多行补全是短板，语言能力保留的逐项数字只在图里。

RecurrentGemma 报告声称的贡献是"非 Transformer 架构达到 Gemma 的性能，同时推理更快"。文本支持的范围是：平均分确实接近，采样吞吐确实不随长度下降；但"性能相当"要加上短板项的限定，"更快"要加上实现与硬件的限定。

清晰度方面，给 3 分（满分 5 分）。两份报告结构清楚，方法与测量条件写得比一般公告具体得多。作为技术文档，它们的不透明之处在于：没有超参、没有统计不确定性、架构细节外包给另一篇论文、关键数字有的只在图里。

## I. 结论、结果与价值总览

### 一句话结论

作为一次发布，它可信地交付了两个开放模型：一个真实可用的快速代码补全模型，和一个平均分追平 Transformer、采样吞吐确实更高的循环架构模型；作为"性能相当""同级最优"的证据，它只在加了限定的条件下成立。

### 核心结论

1. **CodeGemma 2B 预训练版是真实可用的快速补全模型（置信度：高）。** 单行补全 78.41%、多行 51.44%，在 128-token 续写、batch size 为 1 的条件下比同级对手快将近一倍，数字台账里 C4、C5 两行有据可查。

2. **CodeGemma 7B 指令版 v1.1 是全家代码生成最强的变体，但不适合补全（置信度：中）。** HumanEval 60.4%、MBPP 55.2%，是五个变体里最高的；但它的多行补全只有 23.66%，预训练版是 58.44%。报告没有解释这个落差。

3. **RecurrentGemma-2B 平均分追平 Gemma-2B，但短板真实存在（置信度：中）。** 18 项平均分 44.6 对 44.9，只用 2T token 对 3T；但 MMLU 低 3.9 个百分点，GSM8K 低 4.3 个百分点。没有误差棒，无法判断这些差距里有多少是噪声。

4. **RecurrentGemma-9B 只在 8 月修订版里，不属于 4 月 9 日的发布（置信度：高）。** 它的平均分 56.1 对 Gemma-7B 的 56.9，TriviaQA 高 7.1 个百分点，MMLU 低 3.8 个百分点。引用 9B 数字时必须注明版本。

5. **吞吐优势真实，但要加实现与硬件的限定（置信度：中）。** 采样吞吐不随长度下降，9B 对 Gemma-7B 最高达两个数量级；但测量用的是作者优化过的 Flax 实现加专用核，单块 TPU，PyTorch 或 GPU 用户达不到。逐点数值只在图里，未核实。

### 关键结果

CodeGemma 的代码生成提升是确立的。7B 指令版 v1.1 的 HumanEval 是 60.4%，比基底 Gemma 7B 预训练版的 32.3% 高出一倍；MBPP 是 55.2%，比 44.4% 高 10.8 个百分点。2B 预训练版的 HumanEval 是 31.1%，比 Gemma 2B 的 22.0% 高 9.1 个百分点。

CodeGemma 的补全速度优势是部分确立的。2B 预训练版在单行任务上总耗时 543 秒，多行 8479 秒，同级 DeepSeek Coder 是 990 秒和 13138 秒。但 7B 预训练版与 DeepSeek Coder 基本打平，"快将近一倍"只对 2B 成立。

RecurrentGemma 的平均分追平是确立的，但要加短板限定。2B 平均 44.6 对 44.9，9B 平均 56.1 对 56.9。MMLU 和 GSM8K 的落后是确立的数字，但没有误差棒。

人类评估的胜率是确立的，但结论是"没赢"。2B 指令版对 Mistral 7B 的指令遵循胜率 43.7%，低于 50%，和 Gemma-1.1-2B 指令版的 45.0% 基本相同；9B 指令版是 59.3%，赢了。

吞吐的定性结论是确立的，定量逐点数值未核实。报告正文写明了提示处理约 4 万 token 每秒（2B）、约 1.2 万 token 每秒（9B），采样约 6000 token 每秒，Gemma 明显更慢。各长度下的逐点数值只在图 1 里。

### 科学价值总评

认知价值是中等的。RecurrentGemma 确认了循环加局部注意力可以追平 Transformer 这条路径，在两个尺寸上都成立，而且用更少的训练 token。CodeGemma 没有确认任何新认知，它只是把已知做法组合到位。

方法价值是中等的。RecurrentGemma 留下了开源实现和可照搬的配方；CodeGemma 留下了中间填充、多文件打包和合成指令数据的具体做法。两者都没有公开训练数据和完整超参，复现要靠猜。

边界价值是高的，这是这份精读记录最有价值的部分。它明确不证明：RecurrentGemma 的长上下文理解能力、9B 在 4 月 9 日的发布状态、CodeGemma 指令版的补全能力、任何数字的统计显著性。最容易误读的推论，是把"平均分追平"读成"处处一样好"，把"7B 指令版最强"读成"什么代码任务都最强"。

启示价值在于，最便宜的决定性实验是等 token 对照训练：用相同的 2T token、相同的数据，训一个 Griffin 模型和一个 Transformer 模型，看平均分和短板项还差多少。这个实验成本不高，只需要训练算力，不需要新方法，信息量最大，直接裁决最承重的"更数据高效"这个说法。

总体 verdict 是：这批工作值得被记住的，是两件具体的东西——一个真实可用的快速代码补全模型，和一个证明了非 Transformer 路线可行的开放基线。不值得被记住为"性能相当"或"同级最优"的榜单证据。

### 适用边界

不要用这批文档论证 RecurrentGemma 在所有任务上都等于 Gemma，不要用 9B 的数字论证 4 月 9 日发布了什么，不要用 7B 指令版论证补全能力，不要引用任何没有误差棒的基准差距为确立的胜负。

可以引用的是发布事实（三个 CodeGemma 变体、RecurrentGemma-2B、Gemma 1.1、当天可用），以及带条件的数字：2B 的补全速度、7B 指令版 v1.1 的代码生成分数、RecurrentGemma 的平均分与短板项、采样吞吐的定性结论。引用吞吐数字时，须同时说明实现与硬件条件。
