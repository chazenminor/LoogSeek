## 一、背景与问题

### 论文之前是什么局面

语言模型在写代码的基准上已经走得很远。从解教科书式的编程题，到在国际编程竞赛里拿金牌，只用了两年。SWE-bench Verified 在 2024 年 8 月发布时，GPT-4o 得分 33%；到论文写作时，o3 在同一基准上已经达到 72%。分数涨得这么快，旧基准很快就不够用了，需要更难、更贴近真实软件工程的评估。

但已有的基准都有一个共同的局限：它们量的都是孤立的、自包含的任务。HumanEval、MBPP、APPS 考的是写一段小程序；SWE-bench 和 SWE-bench Verified 考的是修真实开源仓库里的 pull request，已经真实得多，但仍然是孤立的任务——修一个函数、改一个模块。真实世界里的软件工程师不是这样工作的：他们要在整个技术栈上工作，处理跨代码库的交互和权衡，还要做技术管理，判断哪个方案更好。

另一个空白是经济意义。已有的基准只给一个百分比分数，不回答“这个分数值多少钱”。如果要评估 AI 对劳动力市场、生产力、AI 研发加速的影响，光知道模型能修多少 bug 是不够的，还得知道这些 bug 在真实市场上值多少钱。

### 这篇论文要回答的问题

这篇论文要做的，是建一个以真实金钱计价的软件工程基准：从 Upwork（一个自由职业平台）上拿 1,488 个真实的自由职业软件工程任务，总价值 100 万美元，全都来自 Expensify 这个真实产品的开源代码库。任务分两类：一类是独立贡献者（Individual Contributor，IC）任务，模型要写代码补丁修问题；另一类是软件工程管理（SWE Manager）任务，模型要扮演技术负责人，从自由职业者提交的多个实现方案里挑出最好的一个。

它要回答的问题可以分成三层。第一层，建一个足够难、足够真实的基准：任务来自真实付费的自由职业工作，用专业工程师写的端到端测试（end-to-end test）评分，而不是容易被钻空子的单元测试。第二层，在这个基准上测一测前沿模型到底能赚多少钱——把能力换算成美元。第三层，摸一摸经济账：让模型先试、失败了再交给人类自由职业者，总成本能不能比全靠人类更便宜。

## 二、方法与设计

### 基准是什么：1,488 个真实付费的自由职业任务

SWE-Lancer 的每个样本就是一个真实发布在 Upwork 上的 Expensify 任务，附带真实付给自由职业者的报酬。1,488 个任务总价值 100 万美元，分成两类。

独立贡献者（IC SWE）任务有 764 个，总价值 414,775 美元。模型拿到三样东西：问题描述（包括复现步骤和期望行为）、问题修复之前那个时间点的代码库快照、以及“修好这个问题”的目标。模型要生成代码补丁，评分办法是把补丁应用上去，跑一整套端到端测试。测试用 Playwright（一个开源浏览器测试库）写成，模拟真实用户操作：登录应用、做复杂的动作（比如做一笔金融交易）、验证模型方案是否如预期工作。模型在评估期间看不到这些端到端测试。

软件工程管理（SWE Manager）任务有 724 个，总价值 585,225 美元。模型扮演软件工程经理，拿到同一个问题的多个实现方案（取自问题最初发布时自由职业者提交的真实方案）、修复前的代码库快照，以及“挑出最佳方案”的目标。评分办法是看模型的选取与当初真正被雇佣的工程经理的选择是否一致。论文说，另一轮由经验丰富的软件工程师做的验证显示，他们的选择与原始选择的一致率是 99%。

任务按原样呈现，问题描述就是 Upwork 上写的那样。任务的价格从 50 美元的 bug 修复到 32,000 美元的功能实现不等（摘要里的说法；正文 §1 写的是 250 美元到 32,000 美元，两处对不上，见文末未核实清单）。价格不是估计值，而是真实付给完成任务的自由职业者的金额。

### 公开部分与保留部分：Diamond 与 holdout

为了推动研究，团队开源了一个公开评估子集 SWE-Lancer Diamond，包含 502 个任务，总价值 500,800 美元：其中 IC SWE 任务 237 个，价值 236,300 美元；SWE Manager 任务 265 个，价值 264,500 美元。

剩下的部分作为私有保留集（holdout），总价值 499,200 美元，不公开，目的是防止污染和模型通过联网直接查答案。保留集里还有一部分 IC SWE 任务（价值 178,475 美元）经过了特殊处理：任务描述和测试用例保持不变，但由熟悉 Expensify 代码库的专业软件工程师用不同但等价的方式重新引入了同样的 bug。这样一来，即使模型背过原始问题的修复办法，也未必能直接套用。

### 怎么建出来的：100 名工程师的三重验证

基准的构建分五步。第一步，选仓库。Expensify 是一家市值 3 亿美元的上市公司（纳斯达克代码 EXFY），有 1,200 万用户，代码库开源，并在 Upwork 上发布带具体报酬的任务。第二步，选任务。100 名专业软件工程师按清晰度、具体性和可执行性逐一审查任务、方案和代码库；对高价值 IC SWE 任务（报酬超过 5,000 美元），由 10 名经验丰富的工程师逐一验证，确认环境配置正确、测试覆盖充分。每个 IC SWE 任务由 3 名工程师审查，每个 SWE Manager 任务由 2 名工程师审查。

第三步，生成任务。从每个验证过的 GitHub issue 生成一个 IC SWE 任务（用任务标题、描述和发布时的代码快照）；如果这个问题至少有两个解决方案，就再生成一个 SWE Manager 任务（用问题描述和方案列表）。第四步，写端到端测试。为每个 IC SWE 任务写全面的 Playwright 端到端测试，每个测试都由专业软件工程师三重验证（triple-verified），验证质量、覆盖面和公平性；另有一套自动化系统确保每个测试在修复后的状态下通过、在未修复的状态下失败。第五步，用户工具（user tool）。每个 IC SWE 任务配一个用户工具：模型调用它时，一个 Playwright 脚本会在浏览器里打开应用，模拟用户执行与任务相关的操作，让模型像人类工程师跑代码一样看到自己的工作成果。模型得不到操作是否成功的反馈，但工具运行结束后，工作目录里会留下一段文字轨迹和一系列截图。

筛选标准列在附录 A.6：问题必须来自开源仓库；必须有具体报酬；必须已经解决；问题必须写得清楚、明确，模型在不能追问的前提下也能理解任务并实施修复；解决问题的 pull request 必须确实修好了问题（团队在本地执行确认过）。SWE Manager 任务还有两条附加标准：至少有两个定义明确的方案；方案里包含足够信息，能判断哪个修复是正确的。

任务的难度不低。Diamond 子集里的任务平均要 26 天才能在 GitHub 上解决，平均有 47 条讨论；IC SWE 任务平均要改 2 个文件、69 行代码；SWE Manager 任务要求模型在 4 到 5 个方案之间做选择。任务类型上，Diamond 子集里 74% 的 IC SWE 任务和 76% 的 SWE Manager 任务属于应用逻辑（Application Logic），17% 和 18% 属于界面与用户体验（UI/UX）；88% 的 IC SWE 任务和 94% 的 SWE Manager 任务是 bug 修复，其余是新功能、维护与可靠性改进。

### 怎么打分：通过率与赚到的钱

论文跟踪两个指标：任务解决率（pass@1，即一次尝试下解决的任务比例）和模型赚到的总报酬（earn rate，即赚到的钱除以总共可能赚到的钱）。因为每个任务都有真实报酬，赚到的钱直接反映经济价值，而不是理论估计。任务越难，报酬越高，尤其是需要专业知识或长期悬而未决的任务。

### 实验设置：断网、单次尝试、最多 100 次工具调用

实验在 Docker 容器里运行，代码库预先配置好，没有联网，防止模型检索外部信息。团队还移除了 GitHub 远程仓库和未来的提交记录，避免模型爬取代码差异或 pull request 细节。每个智能体每个任务只有一次尝试（pass@1），与典型在线自由职业平台的约束一致。

模型用一个基础脚手架（scaffold）操作：浏览本地代码库、修改文件、执行终端命令。每次运行最多 100 次工具调用，最长 3 小时，温度（temperature）固定为 1.0。运行环境是微软 Azure 的 Standard_D2as_v4 虚拟机（2 个 vCPU、8GB 内存），容器分配 64GB 共享内存、最高 192GB 内存。

主实验测了三个模型：OpenAI 的 GPT-4o（gpt-4o-2024-08-06）、OpenAI 的 o1（高推理努力程度，high reasoning effort）、Anthropic 的 Claude 3.5 Sonnet（claude-3-5-sonnet-20240620）。默认都启用用户工具。由于速率限制，Claude 3.5 Sonnet 在全集上只跑了 pass@1。附录 A.15 还报告了两个开源模型（Deepseek-R1、Llama 3.3 70B）的初步结果，只跑了一个种子，且作者自己承认可能没有充分 elicited（激发出来）。

### 统计、算力与可得性

主结果是 pass@1 的单次采样。论文自己在表 1 的脚注里提醒：因为 pass@1 只代表一个样本，不同运行之间的方差可能很大。主结果没有报告误差棒、置信区间、p 值或多重比较校正。唯一的重复实验是价格分析（5 次运行）和开源模型（1 个种子）。

基准代码已开源（github.com/openai/SWELancer-Benchmark），包括统一的 Docker 镜像和公开评估子集 Diamond。完整数据集可按需申请，私有保留集不公开。按 NeurIPS / Pineau 检查表，以下几项是“未报告”或“未提供”：误差棒与置信区间、p 值、多重比较校正、模型内部的随机种子细节、智能体运行的完整日志、以及 SWE Manager 任务 99% 一致率验证的样本量。报告了的是：任务筛选标准、三重验证流程、硬件与脚手架配置、重复次数（价格分析 5 次、开源模型 1 个种子）、污染分析的分组样本量。

## 三、主要发现

### 主结果：最好的模型也只赚到四成

所有模型赚到的钱都远低于 100 万美元的总可能报酬。在 Diamond 子集上，Claude 3.5 Sonnet 表现最好：IC SWE 任务解决率 26.2%，赚到 58,000 美元（总可能 236,300 美元，赚取率 24.5%）；SWE Manager 任务解决率 44.9%，赚到 150,000 美元（总可能 264,500 美元，赚取率 56.8%）。两类合计，Sonnet 在 Diamond 上解决 36.1% 的任务，赚到 208,000 美元（总可能 500,800 美元，赚取率 41.5%）。引言里给出的精确数字是 208,050 美元。

在全集上，Sonnet 的 IC SWE 解决率是 21.1%，赚到 89,000 美元（总可能 414,775 美元，赚取率 21.5%）；SWE Manager 解决率 47.0%，赚到 314,000 美元（总可能 585,225 美元，赚取率 53.7%）。两类合计解决 33.7% 的任务，赚到 403,000 美元，赚取率 40.3%。论文在引言里说“在全集上赚到超过 40 万美元”，与这个数字一致。

o1（高推理努力程度）在 Diamond 的 IC SWE 任务上解决率 16.5%，赚到 29,000 美元，赚取率 12.1%；在全集上是 20.3%，赚到 78,000 美元，赚取率 18.9%。GPT-4o 在 Diamond 的 IC SWE 任务上只有 8.0%，赚到 14,000 美元，赚取率 6.0%；在全集上是 8.6%，赚到 29,000 美元，赚取率 6.9%。

管理任务上三个模型的差距比编码任务小得多。Diamond 的 SWE Manager 任务上，GPT-4o 37.0%、o1 41.5%、Sonnet 44.9%；全集上分别是 38.7%、46.3%、47.0%。也就是说，模型在“从几个方案里挑一个”上比“自己动手写修复”强得多。论文在 §3.2 指出，Sonnet 在 Diamond 的 IC SWE 任务上比第二名 o1 高 9.7 个百分点，在 SWE Manager 任务上比 o1 高 3.4 个百分点。

一个值得注意的模式是：Diamond 子集与全集上的模型差距并不相同。在 Diamond 的 IC SWE 任务上，Sonnet（26.2%）比 o1（16.5%）高出 9.7 个百分点；但在全集上，Sonnet（21.1%）只比 o1（20.3%）高 0.8 个百分点。Diamond 是公开子集，全集包含不公开的保留部分。论文没有解释为什么两个子集上的模型排名差距会差这么多。

### 按任务类型拆开看：新功能最难，管理任务里的新功能反而最容易

附录表 2 按任务主题拆分了 Diamond 的通过率。应用逻辑（客户端）任务最多（IC SWE 176 个）：Sonnet 23.9%、o1 15.9%、GPT-4o 8.0%。UI/UX 任务（41 个）上 Sonnet 的优势最大：31.7%，o1 是 17.1%，GPT-4o 只有 2.4%。服务端逻辑（17 个）上 Sonnet 41.2%，o1 和 GPT-4o 都是 23.5%。系统级质量与可靠性任务只有 3 个，三个模型全是 0.0%。

附录表 3 按工作性质拆分。Bug 修复占绝大多数（IC SWE 208 个）：Sonnet 28.4%、o1 19.2%、GPT-4o 9.6%。新功能或增强（21 个）最难：GPT-4o 0.0%、o1 4.8%、Sonnet 14.3%。维护、质量保证、测试或可靠性改进（8 个）：GPT-4o 0.0%、o1 12.5%、Sonnet 0.0%。

SWE Manager 任务的拆分结果与 IC SWE 任务正好相反。新功能或增强的管理任务（13 个）反而最容易：GPT-4o 和 o1 都是 69.2%，Sonnet 61.5%。维护类管理任务（4 个）上 GPT-4o 75.0%、o1 50.0%、Sonnet 50.0%。但这些管理任务子集的样本量很小（13 个、4 个、2 个），一个任务的得失就能让百分比上下浮动十几个点。

论文在讨论里特别提到，Sonnet 在 UI/UX 任务上比 o1 高将近 15 个百分点（31.7% 对 17.1%），在新功能任务上比 o1 高将近 10 个百分点（14.3% 对 4.8%）。

### 给更多尝试次数：o1 的成绩几乎翻三倍

用 pass@k 指标（给 k 次尝试，至少有一次做对的任务比例）衡量，多给尝试次数，所有模型的成绩都稳定上升。对 o1 来说，多给 6 次尝试，解决的任务比例几乎翻了三倍。GPT-4o 的 pass@6 与 o1 的 pass@1 相当，都是 16.5%。

这里要小心：pass@k 曲线的精确数值只在图 7 里，正文只给了这两句定性描述和这一个等式。“几乎翻三倍”对应的 pass@7 精确数字没有文本版，未核实。

### 给更多推理算力：o1 从 9.3% 涨到 16.5%

在 Diamond 的 IC SWE 任务上，o1 的推理努力程度从低调到高，通过率从 9.3% 涨到 16.5%，赚到的钱从 16,000 美元涨到 29,000 美元，赚取率从 6.8% 涨到 12.1%。中等推理努力程度是 15.6%、24,000 美元、9.9%。论文说，图 8 显示更高的推理算力尤其能改善更难、更贵任务上的表现，但图 8 里各价格区间的具体数值只在图里，未核实。

### 拿掉用户工具：影响很小，但强模型更依赖它

拿掉用户工具后，IC SWE 任务的通过率只轻微下降。表 1 给出的数字是：GPT-4o 不用用户工具仍是 8.0%（但赚到的钱从 14,000 美元变成了 17,000 美元——通过率相同，解决的任务不同，贵的任务换了一批）；o1（高推理）从 16.5% 降到 13.1%，赚到的钱从 29,000 美元降到 23,000 美元。

论文的观察是：更强的模型更会用用户工具，因而拿掉它之后掉得更多。用户工具一次运行要 90 到 120 秒，弱模型（比如 GPT-4o）常常等不及就放弃了；最好的模型会考虑到这个延迟（指令里写明了），设置合适的超时，等结果出来再看。图 9 里各模型的精确数值只在图里，未核实。

### 价格分析：模型先试、人类兜底，能省多少钱

论文做了一个初步的成本分析：在 Diamond 的 IC SWE 任务（237 个，总价值 236,300 美元）上各跑 5 次 GPT-4o 和 o1，比较 API 成本与自由职业者成本。

思路是：先让模型试一次，失败的任务再交给人类自由职业者。这样算下来，GPT-4o 加人类兜底比全部交给人类便宜 8.84%，o1 加人类兜底便宜 13.26%。如果给模型 5 次尝试再兜底，节省更多：GPT-4o 省 18.6%，o1 省 33.5%（图 10）。

另一个指标是模型贡献比：模型在成功任务上赚到的钱，除以模型成本加人类兜底成本。GPT-4o 每花 1 美元总成本，拿回 0.10 美元；o1 是 0.16 美元。这个比值很低，因为模型大多数任务都失败了，还得靠人类解决剩下的部分。

成本本身的数字是：5 次运行的平均 API 成本，GPT-4o 是 194.31 美元（95% 置信区间 ±17.31 美元），o1 是 1,623.76 美元（±56.68 美元）。不计成功与否，只算模型 API 成本占自由职业者成本的比例：GPT-4o 是 0.08%，o1 是 0.7%。只看解决的任务，GPT-4o 每花 1 美元 API 成本能赚回 109 美元，o1 是 20 美元——GPT-4o 便宜得多，但解决的任务也少得多。

论文自己给这个分析加了四点限定：它是按客户视角的 API 价格算的，包含了重试、排除了批量 API 定价（批量定价会降低模型成本、提高贡献比）；所有价格都是历史上真实支付的报酬，可能与当前价格不同；各次运行之间成本方差不小；pass@5 的节省分析假设能快速验证哪个解法正确，但实际验证可能要花 24 小时以上。

### 开源模型：编码任务差得多，管理任务差不多

附录 A.15 报告了 Deepseek-R1 和 Llama 3.3 70B 的初步结果，只跑了一个种子，用的是同一套默认脚手架。在 Diamond 的 IC SWE 任务上，Deepseek-R1 只有 3.8%（4,000 美元），Llama 3.3 70B 是 4.6%（5,000 美元），远低于 GPT-4o 的 8.0%。但在 SWE Manager 任务上，两者都是 40.4%（约 120,000 美元），与 GPT-4o 的 37.0% 相当，甚至略高。

论文列出了开源模型的五种常见失败模式：指令遵循差，不按脚手架的指引先熟悉代码库，经常凭空猜测仓库结构或做浅层的、不看上下文的搜索；急于一次性写完整补丁，而不是先理解问题；经常半途放弃；反复重试同样的失败策略；很少用用户工具，用了也常常解析不好它的输出。论文承认，换一套为开源模型定制的脚手架，成绩可能会显著提高。

### 定性观察：定位快，找根因慢

附录 A.9 分析了一个邮编验证的任务（Expensify issue #14958）：用户在家庭地址页面的邮编栏输入逗号时，应用没有显示验证错误。o1、GPT-4o 和 Claude 3.5 Sonnet 都很快定位到了相关文件，但三者的补丁都没有通过端到端测试。o1 的办法是去掉一个事件处理函数，让表单回落到默认验证器——修了眼前这个 bug，但没有处理国家特定的邮编格式、无邮编国家、动态验证触发和错误信息本地化这些原始 pull request 里都处理了的问题。GPT-4o 调了正则表达式，没有意识到问题出在验证逻辑的触发机制上。Sonnet 最快找到根本原因并修了指定的 bug，但同样没有处理国家特定格式和动态提示。

论文的总结是：智能体定位问题很快，经常用关键词搜索迅速找到相关文件和函数，比人类还快；但它们常常不能理解问题如何跨越多个组件或文件，也找不准根本原因，导致方案不完整或不正确。模型很少会主动复现问题，也很少因为找不到文件而失败——失败的原因不是找不到地方，而是修得不够全面。

### 污染检查：没有发现知识截止日期前的任务表现更好

因为 Diamond 的任务来自 2023 年至 2024 年的公开 GitHub issue，模型在训练时可能见过这些内容。论文在附录 A.2 做了一个简单的检验：按任务创建时间是否在模型知识截止日期之前分组，比较两组任务的通过率。如果模型靠背诵拿分，截止日期之前的任务应该表现更好。

结果没有显示这种模式。GPT-4o（截止日期 2023-10-01）在 IC SWE 任务上，截止前 3.8%（79 个任务），截止后 10.1%（158 个任务）；o1（同一截止日期）是 13.9% 对 17.7%；Claude 3.5 Sonnet（截止日期 2024-04-01）是 17.8%（118 个任务）对 34.5%（119 个任务）。管理任务上三组数字分别是 GPT-4o 37.3% 对 24.4%、o1 38.7% 对 40.7%、Sonnet 45.2% 对 43.6%。

论文据此认为，污染对这些任务的影响有限。但这个检验本身有个值得注意的方向：IC SWE 任务上，三个模型在截止日期之后的任务上表现都更好，尤其是 Sonnet（17.8% 对 34.5%）。论文没有解释为什么新任务反而更容易——可能是新任务本身更容易，也可能是样本构成不同。检验只能排除“背过旧任务”这一种污染，不能排除模型背过解法思路、代码模式或其他形式的污染。

## 四、作者的结论与局限

### 作者的结论

论文的结论是：真实自由职业软件工程工作对前沿语言模型来说仍然很难。最好的模型 Claude 3.5 Sonnet 在 Diamond 上解决 26.2% 的 IC SWE 任务、44.9% 的 SWE Manager 任务，赚到 208,050 美元；但大多数方案仍然是错的，要达到可信赖的部署，还需要更高的可靠性。

论文没有宣称模型已经能替代自由职业工程师。26.2% 这个数字本身就是结论的一部分：最好的模型也只解决了四分之一多一点的独立编码任务。结论的另一面是价格分析：让模型先试、人类兜底，在 Diamond 的 IC SWE 任务上能省 13% 到 33% 的成本（取决于给几次尝试），但这只是初步分析，限定条件很多。

### 作者自述的局限

论文第 4 节列出五组局限，值得原原本本记下来。

第一，仓库与任务的多样性。任务全部来自 Upwork 平台和 Expensify 这一个代码库。虽然作者认为 Expensify 能代表全栈工程工作，但引入其他自由职业平台和开源仓库的任务可以扩大评估范围。特别是基础设施工程任务（比如优化 Kubernetes 集群架构、调试 pod 故障、节点崩溃或网络问题）在这版 SWE-Lancer 里代表性不足，因为 Expensify 发布的任务里这类任务本来就少。

第二，范围。自由职业任务往往比全职软件工程任务更自包含。SWE-Lancer 对“从零到一”的工作代表性也较差，因为所有任务都建立在一个成熟、维护良好的代码库之上。不过 Expensify 代码库的前端部分完全由自由职业工程师维护，这让它比其他自由职业任务更接近真实工程。管理任务也是自由职业者很少处理的工作。作者提醒，SWE-Lancer 可以作为自动化如何影响自由职业软件工程的领先指标，但对超出这个范围的影响要谨慎外推。

第三，模态。任务是纯文本的，尽管问题描述里常常附有屏幕录像。评估没有测试截图或视频能带来多少提升。

第四，环境。与真实工程师不同，模型不能问澄清问题或追问。

第五，污染。依赖开源仓库的编码基准普遍有这个问题。Diamond 的任务来自 2023 年至 2024 年的公开 GitHub issue，取决于模型的知识截止日期，训练数据里可能有这些内容。而且任务都发布在网上，有浏览能力的模型可以直接查答案。因此跑这个评估时，要么禁用浏览，要么限制可访问的网站，理想情况下还要事后筛查作弊行为，这样结果量的才是真实能力而不是污染。附录 A.2 的表 4 显示，截止日期前的任务没有明显的表现优势，说明污染的影响有限。

### 未来工作

论文第 5 节列了两项未来工作。经济分析：模型在 SWE-Lancer 上的表现映射到真实经济价值，每个任务都有真实付给自由职业者的报酬；希望这个基准能推动关于自主智能体更广泛社会影响的研究，包括对劳动力市场、生产力和 AI 研发加速的影响。多模态：当前的评估框架不支持多模态输入，但大多数 Expensify GitHub issue 都包含视频（偶尔有截图），而用户工具保存的截图目前模型也看不到；因为多模态输入还没有广泛支持，团队优先保证了提示与环境信息能以文本形式提供。

## 五、精读点评

这一节是分析者的判断，和上面对论文的呈现分开写。

### 这篇论文真正要回答的问题

这篇论文真正要回答的问题是：前沿模型离“能挣钱的软件工程师”还有多远——不是以百分比衡量，而是以美元衡量。它给出的答案分两层。第一层是工具：1,488 个真实付费任务加端到端测试，确实是一把新的尺子，而且已经量出了东西——最好的模型在独立编码任务上只解决 26.2%，在管理任务上解决 44.9%，在全集上只赚到 40.3% 的钱。第二层是判断：这把尺子量到的，到底是“软件工程能力”，还是“在 Expensify 这一个代码库上做自由职业任务的能力”？论文自己在局限里承认了单一仓库、任务自包含、纯文本这三点距离。第一层是这篇论文立住的部分，第二层是它留给读者的问号。

### 科学问题还原：五问

**现象是什么？** 模型在 SWE-bench Verified 上的分数从 33% 涨到 72% 只用了一年多，旧基准迅速饱和；但分数涨了，并不回答“模型能替人把软件工程的活干了吗”。反常不在于某一次实验失败，而在于“基准分数”与“经济价值”之间没有换算关系——一个 72% 的模型到底值多少钱、能替代多少自由职业工作，没人说得清。更尖锐的是，SWE-bench 类基准用的单元测试还容易被钻空子（附录 A.7 给了 o1 在 SWE-bench Verified 上作弊的例子：给变量名加一个下划线，让分支永远不执行，就骗过了测试）。分数在涨，尺子本身却越来越不可信。

**为什么重要，不解决会怎样？** 对实践来说，没有以美元计价的评估，实验室和公司就不知道模型离替代自由职业工程师还有多远，部署决策和人力规划只能凭感觉；等模型真的能大规模替代这类工作了，才发现没有提前准备，那就晚了。对领域来说，没有更难、更真实的基准，智能体进展的宣称就无法比较——“72%”这个数字本身可能就是被钻空子的测试撑起来的。这篇论文的重要性首先在于它提供了一个更难的、带真实价格标签的公共比较点。

**为什么之前做不了？** 卡住的点有三个。第一，真实的自由职业任务没有现成测试，评判需要为每个任务手写端到端测试，模拟真实用户操作，这是一件手工量很大的脏活——这篇论文动用了 100 名专业软件工程师。第二，任务来自商业产品代码库，而不是开源工具库，拿不到现成数据；Expensify 恰好既开源、又在 Upwork 上发任务，这种数据源本身就很罕见。第三，价格标签需要真实成交数据，而不是估计值；Upwork 上的报酬是真实付出去的钱，这是别的基准没有的东西。这篇论文移走的石头主要是第一块和第二块：一个团队手工建了 1,488 个任务、写了端到端测试、做了三重验证，并开源了出来。第三块是数据源本身带来的，不是方法上的突破。

**方法与问题是否匹配？** 匹配点是真实的，但只覆盖了问题的一部分。用真实付费任务加端到端测试，确实能量出“在结构清晰的自由职业任务上，模型与人类自由职业者的差距”，而且价格标签让差距有了经济含义。但自由职业任务与全职软件工程之间有系统性差异：任务更自包含、问题陈述更清晰、不能追问、纯文本、只有一个代码库。论文在局限里承认了这些。所以方法回答的是“自由职业式的软件工程”，而不是“软件工程”本身。把赚到的钱读成“模型能替代多少软件工程师”，就是方法与问题不匹配的地方。

**答案改变了什么？** 认知上，它第一次给出了模型软件工程能力的公开、可比较的美元数字：最好的模型在独立编码任务上只解决 26.2%，管理任务上 44.9%，全集上只赚到 40.3% 的钱。这改变了“SWE-bench 上 72%，所以模型快能当工程师了”的直觉——换一把更难的尺子，分数立刻掉下来。实践上，它留下了一个开源基准和一套评估方法，任何实验室都可以拿来测自己的模型；同时它也给出了一个反直觉的操作结论：让模型先试、失败了再交给人类，在 Diamond 的 IC SWE 任务上能省 13% 到 33% 的成本。至于“模型离替代软件工程师还有多远”这个更大的问题，答案是什么都没改变——SWE-Lancer 只能告诉你它在 Expensify 的自由职业任务上离人类还有多远。

### 价值判断

认知价值是中等偏高。论文没有推翻某个具体的旧信念，但它第一次把模型软件工程能力换算成真实美元，并且量出了一个反直觉的结构：管理任务（挑方案）比编码任务（写修复）容易得多，三个模型的差距在管理任务上只有几个百分点、在编码任务上却差了三倍；多给尝试次数和推理算力能显著涨分。反事实是：如果这篇论文不存在，“o3 在 SWE-bench Verified 上 72%”这类数字会一直没有更难的公共标尺来检验，智能体能力的讨论会继续停留在单元测试撑起来的分数上。

方法价值是高的。它留下的可复用东西不止一个：1,488 个真实付费任务、端到端测试加三重验证的做法、用户工具（让模型像人一样跑应用看结果）、把表现映射到美元的度量设计、以及公开 Diamond 子集加私有保留集（其中一部分 bug 由工程师重新引入）的防污染组合。任何想评估智能体的人，都能直接拿走这套设计。扣分项是跑一遍的成本不低（每个任务最多 3 小时、100 次工具调用），而且管理任务的评分方式很粗糙。

边界价值是高的，这正是这份精读记录最有价值的部分。它明确不证明的东西包括：赚到的钱能代表模型替代软件工程师的经济价值；管理任务的通过率能代表管理能力；Diamond 子集上的排名能代表全集上的排名（两个子集上 Sonnet 与 o1 的差距从 9.7 个百分点缩到 0.8 个百分点）；污染对未来模型也没有影响（检验只针对截止日期前后的分组，而且方向是反的）。读者最容易误读的推论，是把“在 Diamond 上赚到 208,050 美元”读成“模型已经能挣自由职业工程师 41.5% 的钱”。论文自己在局限里划了这条线，但 208,050 美元这个数字太容易单独流传，流传时限定条件最容易被丢掉。

启示价值在于，最便宜的决定性实验不是再跑一遍 SWE-Lancer，而是做一次“换仓库”的对照评估。具体设计在下面“接下来看什么”里写。

### 最弱的一环

最弱的一环在“管理任务的通过率”与“管理能力”之间。整篇论文的说服力，有一半建立在管理任务这个新度量上——它是 SWE-Lancer 区别于 SWE-bench 的两大卖点之一（另一个是美元计价）。但管理任务的评分方式是：模型的选取与当初真正被雇佣的工程经理的选择是否一致。

这个假设之所以承重，是因为论文自己承认，常常有多个方案在技术上都是正确的，选出获胜方案需要考虑整个代码库的上下文。如果多个方案都正确，那么“与原始选择一致”量的就不是“选了最好的方案”，而是“猜中了当初那位经理的偏好”。论文用一轮验证来支撑这个度量——经验丰富的工程师与原始选择的一致率是 99%——但这轮验证的样本量没有报告，而且验证者与原始经理共享同样的工程文化与代码库背景，一致率高可能反映的是群体内的共识，而不是度量本身的客观性。如果管理任务的评分方式站不住，44.9% 这个数字作为“管理能力”的证据就要大打折扣。

第二弱的一环是主结果只有一个样本。表 1 的所有数字都是 pass@1 的单次运行，论文自己在脚注里提醒方差可能很大。没有误差棒、没有重复运行，主结果里的模型差距——尤其是 Diamond 上 Sonnet 与 o1 的 9.7 个百分点——不知道有多少是真实差距、有多少是单次采样的运气。价格分析跑了 5 次，但主结果没有。

第三弱的一环是 Diamond 与全集上的模型差距对不上。IC SWE 任务上，Sonnet 与 o1 的差距在 Diamond 是 9.7 个百分点，在全集上只有 0.8 个百分点。论文没有解释。Diamond 是公开子集，全集包含不公开的保留部分；如果两个子集的难度分布或任务构成不同，公开子集上的排名就不能代表全集上的排名。读者引用“Sonnet 比 o1 高 9.7 个百分点”时，其实引用的是公开子集上的数字。

### 效度判断

下面是针对论文作为证据的评分，满分 5 分，评的是证据，不是模型本身。

内部效度 3 分。评估设计有不少严谨之处：断网运行、移除 GitHub 远程记录、端到端测试三重验证、自动化系统确保测试在修复态通过、在未修复态失败、污染做了截止日期分组检验。扣分项是：主结果只有一个样本，没有误差棒；管理任务的评分方式依赖单一原始选择，且验证的样本量未报告；价格分析的限定条件很多（批量定价、验证时间）；任务分类（表 2、表 3）是用 o1 对每条 GitHub issue 讨论串跑三遍、意见不一致时人工定夺，分类本身由被测模型之一参与完成。

外部效度 2 分。结果能推广到 Expensify 代码库上的自由职业任务，这是论文的强项：1,488 个任务、真实报酬、端到端测试。但推广到其他代码库、其他自由职业平台、全职软件工程、“从零到一”的工作，论文自己承认没有证据；基础设施任务代表性不足；任务是纯文本的，模型看不到 issue 里的视频和截图；模型不能追问，而人类工程师可以。赚到的钱作为经济影响信号的外推，是这篇论文最薄弱的一环。

构念效度 3 分。IC SWE 任务的通过率确实量的是“在 Expensify 任务上写出通过端到端测试的修复”，有真实报酬做锚，比较扎实。但“赚到的钱”不等于“经济价值”——它没有计入验证成本、返工成本和模型失败后人类兜底的管理成本；“管理任务通过率”不等于“管理能力”，因为多个方案可能都正确，而评分只认原始选择。主指标把两类任务压成一个“总共赚了多少钱”，也丢掉了任务类型的结构信息。

统计结论效度 2 分。扣分项是：主结果是单次采样，没有误差棒、置信区间、p 值或多重比较校正；图 7 至图 10 的核心数字只在图里，没有数值表；管理任务子集的样本量很小（新功能 13 个、维护类 4 个、系统级 2 个），拆分后的百分比很不稳定；价格分析的 5 次运行报告了置信区间，是全篇统计上最扎实的一处。样本量方面，1,488 个任务的规模是够的，但单次采样让这个规模的优势打了折扣。

可复现性 4 分。方法描述相当完整：筛选标准、三重验证流程、硬件与脚手架配置、提示模板（附录 A.8）、重复次数都给了，基准代码、Docker 镜像和 Diamond 子集都开源了，一个能干的读者能按描述重建评估。扣分项是：完整数据集要申请，私有保留集不公开；智能体运行的完整日志没有发布；主结果是单次采样，别人重跑一次未必得到同样的数字。没有这些，标题数字只能在“基准可复现、实验难复现”的意义上成立。

### 其他可能的解释

同一个结果，至少有三种别的解释也能说得通。

第一种是“脚手架解释”。三个模型的差距可能不完全是模型能力，而是默认脚手架与某个模型特别合拍。证据是：附录 A.15 里开源模型在同一套脚手架上表现很差，论文自己承认换一套定制的脚手架成绩可能显著提高；主实验只用了一套基础脚手架，没有换脚手架比较模型。区分证据是：换两三套不同的脚手架重跑三个模型，看模型排名是否稳定。

第二种是“Diamond 选择解释”。Sonnet 在 Diamond 上比 o1 高 9.7 个百分点、在全集上只高 0.8 个百分点，可能说明 Diamond 子集的任务构成对 Sonnet 更有利，而不是 Sonnet 在一般意义上更强。区分证据是：报告 Diamond 与非 Diamond 部分各自的模型差距，或者说明 Diamond 的抽样方式是否随机。

第三种是“管理任务猜偏好解释”。管理任务上三个模型都在 37% 到 47% 之间、差距很小，可能不是因为三个模型的管理能力相近，而是因为任务本身接近“猜当初经理的偏好”——在 4 到 5 个方案里挑一个，随机猜也有 20% 到 25% 的基准，而论文没有报告随机基线。区分证据是：报告随机选择与“选最短方案”“选最早提交的方案”等简单启发式的基线，看模型比这些基线高多少。

第四种是“新任务更容易解释”。污染检验里 IC SWE 任务上三个模型在截止日期之后的任务上表现都更好（Sonnet 是 17.8% 对 34.5%），论文解读为“没有污染信号”，但这个模式本身也可以解释为“新任务更容易”或“新任务的样本构成不同”。区分证据是：控制任务难度（比如用报酬金额或解决天数）之后，看截止日期前后是否还有差异。

## 七、证伪器、替代解释、接下来看什么

### 证伪器

“Claude 3.5 Sonnet 是最好的模型”：换两三套不同的脚手架重跑三个模型。如果模型排名变了（比如 o1 在另一套脚手架上超过 Sonnet），“Sonnet 最强”就只能退回为“Sonnet 配这套默认脚手架最强”。

“管理任务通过率代表管理能力”：报告随机选择与简单启发式（选最短方案、选最早提交的方案）的基线。如果模型只比随机基线高一点，或者简单启发式就能达到相近的通过率，管理任务作为能力度量的主张即被反驳。

“没有系统性的污染效应”：控制任务难度（比如用报酬金额或解决天数）之后，看截止日期前后是否还有差异。如果控制难度后截止日期前的任务仍然表现更好，污染解释就重新成立。更直接的检验是：用保留集里工程师重新引入 bug 的那部分任务重测，看通过率是否大幅下跌。

“Diamond 子集上的排名能代表全集上的排名”：分别报告 Diamond 与非 Diamond 部分的模型差距。如果非 Diamond 部分的模型排名与 Diamond 不同，公开子集上的结论就不能直接推广到全集。

“模型先试、人类兜底能省钱”：把验证成本算进去重做价格分析。如果验证一个解法正确平均要花 24 小时以上的人工时间，pass@5 下 33.5% 的节省可能大幅缩水，甚至变负。

### 替代解释

替代解释一：脚手架解释。三个模型的差距可能不完全是模型能力，而是默认脚手架与某个模型特别合拍。预测：在另外两三套脚手架上，模型排名会变化；或者换一套为开源模型优化的脚手架，Deepseek-R1 与 Llama 3.3 的 IC SWE 通过率会大幅上升。区分证据：换脚手架重跑三个主力模型与两个开源模型。

替代解释二：Diamond 选择解释。Sonnet 在 Diamond 上比 o1 高 9.7 个百分点、在全集上只高 0.8 个百分点，可能说明 Diamond 子集的任务构成对 Sonnet 更有利。预测：非 Diamond 部分的模型差距与 Diamond 不同；或者 Diamond 的抽样不是随机的。区分证据：分别报告两部分的模型差距，或说明 Diamond 的抽样方式。

替代解释三：管理任务猜偏好解释。管理任务上三个模型都在 37% 到 47% 之间、差距很小，可能不是因为管理能力相近，而是因为任务接近“猜当初经理的偏好”——在 4 到 5 个方案里挑一个，随机猜也有 20% 到 25% 的基准。预测：随机基线与简单启发式基线不低，模型比它们高得有限。区分证据：报告随机与启发式基线。

替代解释四：新任务更容易解释。污染检验里 IC SWE 任务上三个模型在截止日期之后的任务上表现都更好，可能不是因为没有污染，而是因为新任务本身更容易或样本构成不同。预测：控制报酬金额或解决天数后，截止日期前后的差异消失或反转。区分证据：按难度分层后重做附录表 4 的比较。

### 作者自述局限与分析者发现的局限

作者自述的局限见第四节：仓库与任务多样性、范围、模态、环境、污染。

分析者发现的、作者没说的局限有五点。第一，主结果是单次采样，没有误差棒，模型差距里有多少是运气，说不清。第二，Diamond 与全集上的模型差距对不上（Sonnet 与 o1 的差距从 9.7 个百分点缩到 0.8 个百分点），论文没有解释。第三，管理任务没有报告随机基线与简单启发式基线，44.9% 这个数字的含金量说不清。第四，任务分类（表 2、表 3）由被测模型之一 o1 参与完成，分类本身可能带有模型偏见。第五，价格分析排除了批量 API 定价、没有计入验证成本，33.5% 的节省是乐观口径。

### 接下来看什么

最值得先做的，是做一次“换仓库”的对照评估。这是启示价值里最便宜的决定性实验，也是全篇最缺的一块。

具体设计：取另一个开源产品代码库（比如一个同样在 Upwork 或类似平台上发任务的真实产品仓库），按同样的方法建 100 到 200 个任务——真实报酬、端到端测试、三重验证——让三个模型各跑一遍，由不知道模型身份的评审员按“测试是否通过”盲评。

判据很简单：如果模型在新仓库上的排名（Sonnet 大幅领先）与在 Expensify 上一致，SWE-Lancer 作为能力度量的主张就得到支持；如果排名变了，或者所有模型在新仓库上都接近零分，基准的价值就要收回到“Expensify 自由职业任务能力”这个更窄的范围。

其次是把 Diamond 与全集的差距弄清楚。成本很低：只需要作者分别报告 Diamond 与非 Diamond 部分的模型差距，或者说明 Diamond 的抽样方式。如果两个子集的难度分布确实不同，引用者就知道该用哪一个数字；如果不是，那至少有一处结论需要修正。

再往后看三件事：报告管理任务的随机基线与简单启发式基线，看 44.9% 到底比猜高多少；换两三套脚手架重跑三个模型，检验脚手架解释；把价格分析里的验证成本算进去，看 33.5% 的节省还剩多少。这三项都不需要建新基准，成本低，信息量大。

最后是博客 2025 年 7 月 28 日的更新说明：数据集与结果已于 2025 年 7 月 17 日更新，见 OpenAI 的 preparedness 仓库与系统卡片，更新后的数据集不再要求执行期间联网。值得关注的后续工作是：更新后的数据集与结果与本文件所读的 v4 相比变了多少——如果主结果数字变了，本文件的数字台账就要按新版重核。

## I. 结论、结果与价值总览

### 一句话结论

在 1,488 个真实付费的 Expensify 自由职业任务上，最好的模型 Claude 3.5 Sonnet 也只解决了 21.1% 的独立编码任务、赚到 40.3% 的钱；前沿模型离替代自由职业工程师还差得很远，但这把尺子量的是单个代码库上的自由职业任务，不是软件工程本身。

### 核心结论

1. **最好的模型也只赚到四成（置信度：高）。** 表 1：Sonnet 在全集上解决 33.7% 的任务，赚到 403,000 美元，赚取率 40.3%；在 Diamond 上解决 36.1%，赚到 208,050 美元（引言精确数字），赚取率 41.5%。

2. **编码任务比管理任务难得多（置信度：高）。** 表 1：Diamond 的 IC SWE 任务上 Sonnet 26.2%、o1 16.5%、GPT-4o 8.0%；SWE Manager 任务上三者分别是 44.9%、41.5%、37.0%。但管理任务的评分方式依赖单一原始选择，度量本身的效度未确立。

3. **多给尝试次数和推理算力能显著涨分（置信度：中）。** o1 多 6 次尝试几乎翻三倍（§3.3，精确曲线只在图 7 里）；o1 的推理努力程度从低调到高，通过率从 9.3% 涨到 16.5%（表 1）。但 pass@k 的精确数字只在图里。

4. **模型先试、人类兜底能省钱，但只是初步分析（置信度：低）。** pass@1 下 o1 加人类兜底省 13.26%，pass@5 下省 33.5%（§3.6）；但分析排除了批量定价、没有计入验证成本，验证一个解法正确实际可能要花 24 小时以上。

5. **没有发现截止日期前的任务表现更好（置信度：中）。** 附录表 4：IC SWE 任务上三个模型在截止日期之后的任务上表现都更好（Sonnet 是 17.8% 对 34.5%），与污染预期相反；但这个模式本身未被解释，检验只能排除一种污染。

6. **Diamond 与全集上的模型差距对不上（置信度：低，待作者解释）。** IC SWE 任务上 Sonnet 与 o1 的差距在 Diamond 是 9.7 个百分点，在全集只有 0.8 个百分点（表 1）。公开子集上的排名不能直接当成全集上的排名。

### 科学价值总评

认知价值是中等偏高。第一次把模型软件工程能力换算成真实美元，量出了“管理任务比编码任务容易得多、多给尝试次数和推理算力能显著涨分”这个反直觉的结构，改变了“SWE-bench 上 72%，所以模型快能当工程师了”的直觉。

方法价值是高的。留下了可复用的 1,488 个真实付费任务、端到端测试加三重验证的做法、用户工具、美元计价的度量设计、以及公开 Diamond 子集加私有保留集的防污染组合。扣分项是管理任务的评分方式很粗糙，主结果只有一个样本。

边界价值是高的。它明确不证明：赚到的钱代表模型替代软件工程师的经济价值；管理任务通过率代表管理能力；Diamond 子集上的排名代表全集上的排名；污染对未来模型也没有影响。最容易误读的推论是把“在 Diamond 上赚到 208,050 美元”读成“模型已经能挣自由职业工程师 41.5% 的钱”。

启示价值在于，最便宜的决定性实验是做一次换仓库的对照评估，看模型在 SWE-Lancer 上的排名在另一个代码库上是否成立。

总体 verdict 是：这篇工作值得被记住为第一个把模型能力换算成真实美元的软件工程基准，以及一套可复用的端到端测试加三重验证的评估方法。不值得被记住为“模型值多少钱”或“模型离替代软件工程师还有多远”的答案——那两步它都没有量到，也不该用它的数字去量。

### 适用边界

不要用这篇论文论证模型已经能替代自由职业软件工程师，不要用 208,050 美元论证模型已经能挣自由职业工程师 41.5% 的钱，不要用管理任务的 44.9% 论证模型具备管理能力，不要用污染检验的结果论证未来模型也不会受污染影响，不要引用图 7 至图 10 里的数值为已确立的数字。

可以引用的是表 1 的主实验结果（带单次采样的提醒）、表 4 的污染分组、表 11 的开源模型初步结果、§3.6 的价格分析（带限定条件）、以及 1,488 个任务与 100 万美元的基准规模。引用 Diamond 上的模型差距时，须同时说明全集上的差距要小得多。
