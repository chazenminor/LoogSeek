## 一、背景与问题

### 博客之前是什么局面

到 2025 年 3 月，OpenAI 的模型已经具备了高级推理（advanced reasoning）、多模态交互与新的安全技术，博客认为这些能力为处理智能体（agent）所需的多步骤复杂任务打下了基础。它把智能体定义为“代表用户独立完成任务的系统”（systems that independently accomplish tasks on behalf of users）。

但博客开篇点出的空白是工程层面的：客户反馈说，把这些模型能力变成可用于生产的智能体很难——往往要反复迭代提示词、自己写编排逻辑，而且缺乏可见性与内置支持。换句话说，模型已经能做多步骤任务了，但开发者手里没有现成的积木。

### 这篇博客要回答的问题

博客要宣布的不是一个研究发现，而是一套新的开发工具：第一批帮助开发者与企业构建“有用且可靠的智能体”的基础模块。具体是四样东西：新的 Responses API（响应 API），把 Chat Completions API（聊天补全 API）的简单性与 Assistants API（助手 API）的工具使用能力结合起来；三件内置工具——网络搜索（web search）、文件搜索（file search）、计算机使用（computer use）；新的 Agents SDK（智能体软件开发工具包），用来编排单智能体与多智能体工作流；以及集成的可观测性（observability）工具，用来追踪与检查智能体工作流的执行过程。

博客要让读者相信两件事。第一，开发智能体从此变简单了：一次 Responses API 调用就能用多个工具、走多个模型回合完成越来越复杂的任务；文件搜索“几行代码”就能集成；Agents SDK 让编排、多智能体交接与安全检查都有现成的抽象。第二，新工具的性能有数字支撑：网络搜索背后的搜索模型在 SimpleQA（简单问答基准）上得分 90% 与 88%；计算机使用模型 CUA（Computer-Using Agent，计算机使用智能体）在 OSWorld（操作系统世界基准）上 38.1%、WebArena（网络竞技场基准）上 58.1%、WebVoyager（网络漫游者基准）上 87%，博客称 OSWorld 一项创了新纪录。

## 二、方法与设计

### Responses API：一个新的 API 原语

Responses API 是博客的核心发布：一个用来调用 OpenAI 内置工具构建智能体的新 API 原语（API primitive）。它把 Chat Completions 的简单性与 Assistants API 的工具使用能力结合起来。博客说，随着模型能力继续演进，Responses API 会为构建智能体应用提供更灵活的基础；一次调用就能用多个工具、走多个模型回合，解决越来越复杂的任务。

博客列出的可用性改进有四项：统一的基于条目（item-based）的设计、更简单的多态（polymorphism）、直观的流式事件（streaming events），以及 `response.output_text` 这样的 SDK 辅助方法，方便取到模型的文本输出。博客还说，API 让开发者更容易把数据存在 OpenAI 一侧，从而用追踪（tracing）与评估（evaluations）等功能评估智能体表现；同时提醒，默认情况下 OpenAI 不用业务数据训练模型。

定价上，Responses API 本身不单独收费，token 与工具按定价页的标准费率计费。发布当天起向所有开发者开放。

### 对现有 API 的安排

博客用一节交代了三条 API 各自的去向，值得原原本本记下来，因为这是它对开发者最重要的承诺。

Chat Completions API 仍然是采用最广的 API，OpenAI 承诺继续支持它、继续向它发布新模型；不需要内置工具的开发者可以放心继续用它。但博客同时说，Responses API 是 Chat Completions 的超集（superset），性能相同，所以新集成建议从 Responses API 开始。

Assistants API 的去向更明确：根据 Assistants API 测试版的开发者反馈，OpenAI 把关键改进吸收进了 Responses API，使其更灵活、更快、更易用。OpenAI 正在努力实现两个 API 之间的功能对等，包括支持类似 Assistant 与 Thread 的对象以及 Code Interpreter（代码解释器）工具；一旦完成，将正式宣布 Assistants API 的弃用（deprecation），目标日落日期是 2026 年年中。弃用时将提供明确的迁移指南，让开发者保留全部数据并迁移应用。在正式宣布弃用之前，会继续向 Assistants API 发布新模型。博客的结论是：Responses API 代表 OpenAI 构建智能体的未来方向。

### 三件内置工具

**网络搜索（web search）。** 开发者可以用它获得快速、最新的、带清晰相关引用的网络答案。在 Responses API 里，网络搜索作为工具适用于 gpt-4o 与 gpt-4o-mini，可以与其他工具或函数调用搭配使用。博客说，早期测试里开发者用它做了购物助手、研究智能体、旅行预订智能体等需要实时网络信息的应用。博客举了一个客户例子：Hebbia 用网络搜索工具帮助资产管理、私募股权与信贷公司及律师事务所，从大量公开与私有数据集中快速提取可执行的洞见。

网络搜索由与 ChatGPT 搜索（ChatGPT search）相同的模型驱动。在 SimpleQA 上，GPT-4o search preview（预览版）与 GPT-4o mini search preview 分别得分 90% 与 88%。用网络搜索生成的回答包含指向来源的链接，例如新闻文章与博客文章，博客说这让内容所有者有机会触达更广泛的受众。任何网站或出版方都可以选择是否出现在 API 的网络搜索结果里。

网络搜索工具在 Responses API 里以预览（preview）形式向所有开发者开放。同时，开发者也可以在 Chat Completions API 里直接使用这两个经过微调的搜索模型（`gpt-4o-search-preview` 与 `gpt-4o-mini-search-preview`）。定价分别是每千次查询 30 美元与 25 美元。

**文件搜索（file search）。** 开发者可以用改进后的文件搜索工具，从大量文档中快速检索相关信息。它支持多种文件类型、查询优化（query optimization）、元数据过滤（metadata filtering）与自定义重排序（custom reranking）。博客说，用 Responses API 集成它只需几行代码。

博客列出的用途包括：让客服智能体方便地查阅常见问题（FAQ）、让法律助手快速引用过往案例、让编码智能体查询技术文档。客户例子是 Navan：它在 AI 驱动的旅行智能体里用文件搜索，从知识库文章（例如公司差旅政策）中快速给出精确答案；借助内置的查询优化与重排序，Navan 搭建了一个无需额外调参或配置的 RAG（检索增强生成）流水线；为每个用户组设专用向量存储（vector store），可以按账户设置与用户角色定制答案。

文件搜索工具在 Responses API 里向所有开发者开放，定价是每千次查询 2.50 美元，文件存储每 GB 每天 0.10 美元，首个 GB 免费。它继续在 Assistants API 里可用。博客还提到，向量存储（Vector Store）API 对象新增了一个搜索端点（endpoint），可以直接查询数据，供其他应用与 API 使用。

**计算机使用（computer use）。** 开发者可以用 Responses API 里的计算机使用工具构建能在计算机上完成任务的智能体，工具由与 Operator 相同的 CUA 模型驱动。博客说，这个研究预览（research preview）模型创下了新的最高纪录（state-of-the-art record）：OSWorld 上完整计算机使用任务成功率 38.1%，WebArena 上 58.1%，WebVoyager 上网络交互 87%。

工具的工作方式是：捕获模型生成的鼠标与键盘动作，开发者把这些动作直接翻译成自己环境里可执行的命令，从而实现计算机使用任务的自动化。博客列出的用途包括：在浏览器里做网络应用的质量保证（QA）、跨遗留系统执行数据录入任务。客户例子有两个：Unify 用计算机使用工具让智能体访问过去无法通过 API 获得的信息，例如通过在线地图核实一家企业是否扩大了房地产足迹；Luminai 在一个大型社区服务组织的试点里，用它在几天内自动处理了申请与用户注册流程，而传统的机器人流程自动化（RPA）花了几个月也没做成。

安全方面，博客说，在 Operator 去年发布 CUA 之前，团队做了广泛的安全测试与红队测试，覆盖误用、模型错误与前沿风险三类风险；为了把 Operator 的能力通过 API 扩展到本地操作系统，又做了额外的安全评估与红队测试，并给开发者加了缓解措施：防范提示注入（prompt injection）的安全检查、敏感任务的确认提示、帮助开发者隔离环境的工具、以及对潜在违规行为的增强检测。博客同时承认，这些缓解措施有帮助，但模型仍然容易犯无意的错误，尤其是在非浏览器环境里——CUA 在 OSWorld 上的表现目前是 38.1%，说明它在操作系统任务自动化上还不够可靠，建议在这些场景里保留人工监督。更多 API 安全工作的细节，博客指向一份更新版的系统卡。

计算机使用工具从发布当天起，以研究预览形式向使用层级（usage tiers）3 至 5 的部分开发者开放。定价是每百万输入 token 3 美元、每百万输出 token 12 美元。博客还给了一个 GitHub 上的示例应用链接，展示如何用这个工具构建应用。

### Agents SDK：编排多智能体工作流的开源框架

除了核心的智能体逻辑与工具接入，开发者还需要编排智能体工作流。新的开源 Agents SDK 简化了多智能体工作流的编排，相比去年发布的实验性 SDK Swarm 有显著改进——Swarm 被开发者社区广泛采用，并被多家客户成功部署。

博客列出的改进有四项：智能体（Agents），即易于配置、带明确指令与内置工具的大语言模型；交接（Handoffs），即在智能体之间智能地转移控制权；护栏（Guardrails），即可配置的输入与输出验证安全检查；追踪与可观测性（Tracing & Observability），即可视化智能体执行轨迹，便于调试与优化性能。

SDK 适用的场景包括客服自动化、多步骤研究、内容生成、代码审查与销售 prospecting（潜在客户挖掘）。客户例子有两个：Coinbase 用 Agents SDK 在几小时内快速原型化并部署了 AgentKit，一个让 AI 智能体与加密钱包及各类链上活动无缝交互的工具包；Box 在几天内创建了利用网络搜索与 Agents SDK 的智能体，让企业能搜索、查询并提取存储在 Box 内与公开互联网上的非结构化数据中的洞见，同时遵守企业内部的权限与安全政策。

Agents SDK 可与 Responses API 与 Chat Completions API 配合使用；只要对方提供 Chat Completions 风格的 API 端点，它也能与其他提供商的模型一起工作。发布时可立即集成进 Python 代码库，Node.js 支持即将推出。博客还提到，设计 Agents SDK 时，团队受到了社区优秀工作的启发，包括 Pydantic、Griffe 与 MkDocs，并承诺把它作为开源框架持续建设。

### 展望：构建智能体的平台

博客的收尾是一节展望，没有新的事实性主张。OpenAI 认为智能体很快会成为劳动力中不可或缺的一部分，显著提升各行业的生产力；随着模型能力越来越偏向智能体化（agentic），公司将继续投资 API 之间的深度集成与新工具，帮助开发者在生产环境中部署、评估与优化智能体。目标是给开发者一个无缝的平台体验。

## 三、主要发现

博客的主要发现其实是两组数字：搜索模型的 SimpleQA 分数，与 CUA 的三个计算机使用基准分数。其余内容是产品描述与定价，没有研究发现。

### SimpleQA：90% 与 88%

在 SimpleQA 这个评估大语言模型回答简短事实性问题准确率的基准上，GPT-4o search preview 得 90%，GPT-4o mini search preview 得 88%。博客没有给出这个基准的样本量、评估方法、运行次数或误差范围，也没有给出不带搜索的同一模型的分数，所以读者无法判断 90% 里有多少来自搜索本身、有多少来自模型本身。

值得注意的一点是，这两个分数出现在网络搜索一节的正文里，而不是一张独立的表格里；博客还配了一张标题为“SimpleQA Accuracy（越高越好）”的图，但图的数值没有在正文里重复——本篇只采用正文里写明的 90% 与 88%，不从图里读数。

### 计算机使用：38.1%、58.1%、87%

博客正文与一张对照表给出了 CUA 在三个基准上的成绩：OSWorld 38.1%、WebArena 58.1%、WebVoyager 87%。对照表还列出了此前最优成绩（Previous SOTA）与人类表现。

OSWorld 上，CUA 的 38.1% 对此前最优 22.0%（通用接口的计算机使用智能体），人类 72.4%。WebArena 上，CUA 的 58.1% 对此前最优 36.2%（通用接口），以及网络浏览智能体的此前最优 57.1%，人类 78.2%。WebVoyager 上，CUA 的 87.0% 与网络浏览智能体的此前最优 87.0% 持平，人类表现未列出。

博客称 CUA 在 OSWorld 上创了新纪录——这个说法只对 OSWorld 成立：38.1% 对 22.0% 是大幅领先。WebArena 上 58.1% 对网络浏览智能体的 57.1% 只有 1 个百分点的差距，而 WebVoyager 上 87% 与此前最优完全相同。博客没有说明这些基准的样本量、运行次数、误差范围与评估协议，只在表下给了一个“评估细节见此处”的链接，本篇精读没有追读那份评估细节文档，见文末未核实清单。

博客自己也点出了 38.1% 的另一面：在计算机使用一节的末尾，它明确说这个数字意味着模型在操作系统任务自动化上“还不够高度可靠”（not yet highly reliable），并建议保留人工监督。这是博客里少有的、把自己的基准分数往回拉的自我限定，值得肯定。

## 四、作者的结论与局限

### 作者的结论

博客没有写“结论”一节，它的结论就是发布本身：Responses API、三件内置工具与 Agents SDK 从今天起可用，开发者可以用它们更简单地构建、部署与扩展可靠、高性能的 AI 智能体；Assistants API 将在实现功能对等后走向弃用，目标日落日期 2026 年年中；Responses API 是未来的方向。

### 作者自述的局限

博客没有单独的“局限”一节，但它在计算机使用一节里明确写了两条自我限定。第一，CUA 仍然容易犯无意的错误，尤其是在非浏览器环境里；OSWorld 上 38.1% 的成绩说明它在操作系统任务自动化上还不够可靠。第二，这些场景里建议保留人工监督。

除此之外，博客没有讨论任何其他局限：没有提到网络搜索的引用是否总能准确、文件搜索的检索质量如何衡量、Agents SDK 在大规模多智能体编排里的表现如何。博客也没有给出任何评估方法，读者无法复核它公布的任何一个数字。

### 安全工作

博客在计算机使用一节里交代了安全工作：Operator 发布前做过广泛的安全测试与红队测试；把 CUA 通过 API 扩展到本地操作系统时，又做了额外的安全评估与红队测试，并给开发者加了四项缓解措施（提示注入安全检查、敏感任务确认提示、环境隔离工具、违规检测增强）。更多细节指向一份更新版的系统卡，本篇精读没有以系统卡为主源。

## 五、精读点评

这一节是分析者的判断，和上面对博客的呈现分开写。

### 这篇博客真正要回答的问题

这篇博客真正要回答的问题不是一个科学问题，而是一个平台问题：开发者想用 OpenAI 的模型做智能体，但手里只有“聊天补全”与“助手”两个各有短板的 API——前者简单但没有内置工具，后者有工具但处于测试版、难用且难观测。博客给出的答案是：Responses API 把两者的优点拼在一起，再配三件内置工具与一个开源编排 SDK。

但博客真正留下的、值得追问的问题是另一层：把“工具调用”与“编排”做成平台原语，到底在多大程度上解决了“智能体不可靠”这个问题，又在多大程度上只是把不可靠从提示词与胶水代码里挪到了工具与 SDK 里？博客没有回答这个问题，因为它没有给出任何能区分这两者的证据——没有可靠性评估，没有失败案例分析，没有与 Assistants API 的对照比较。

### 科学问题还原：五问

**现象是什么？** 模型已经能处理多步骤复杂任务，但开发者把它们变成生产级智能体时仍然困难：要反复迭代提示词、自己写编排逻辑、缺乏可见性。反常不在于模型能力不足，而在于“模型会做事”与“开发者能可靠地让它做事”之间有一道工程鸿沟。

**为什么重要，不解决会怎样？** 对实践来说，不解决它，每个想做智能体的团队都要自己重写提示词管理、工具调用、编排与观测，成本高、质量参差；对 OpenAI 来说，不解决它，开发者会继续停留在 Chat Completions 上做一次性调用，或者被 Assistants API 测试版的粗糙体验挡住，智能体生态就长不起来。博客把这件事上升到“智能体将成为劳动力的一部分”的高度，这个说法本身无法从博客的内容里验证，它更像是一种愿景修辞，而不是论证。

**为什么之前做不了？** 博客没有明说 blocker，只在字里行间暗示了两点：第一，需要一个既简单、又能调用内置工具的 API 原语，而 Chat Completions 与 Assistants API 各占一头，拼不起来；第二，需要把搜索、文件检索、计算机使用这些能力做成可直接调用的内置工具，而不是让每个开发者自己接外部供应商。博客没有交代 Responses API 的设计从哪来、为什么是这个形状，所以 blocker 是否真的被移走了，读者无从判断——只能看到它宣布了一个新的原语。

**方法与问题是否匹配？** 从产品角度看，匹配点是真实的：问题是“开发智能体太难、太散”，方法是“一个统一的 API 原语加三件内置工具加一个编排 SDK”。但从证据角度看，方法与宣称的匹配没有被证明：博客用 SimpleQA 与三个计算机使用基准的分数来证明“新工具好用”，而这些分数量的是“搜索模型答对事实问题”与“CUA 在基准任务上的成功率”，不是“开发者用这套工具构建智能体变得更容易、更可靠”。用基准分数证明开发体验，中间隔了一层没有被检验的跳跃。

**答案改变了什么？** 认知上，什么都没有改变——博客没有提出新发现，也没有推翻任何旧信念。实践上，它改变了三件事：从 2025 年 3 月起，开发者有了一个官方推荐的智能体 API 原语（Responses API）；网络搜索、文件搜索、计算机使用成了可直接调用的内置工具；多智能体编排有了一个开源的官方 SDK，以及 Assistants API 明确的弃用时间表（目标 2026 年年中）。至于“用这套工具做出来的智能体到底有多可靠”，答案是什么都没有确立——博客自己承认 CUA 在 OSWorld 上只有 38.1%、还不够可靠，而其他工具的可靠性根本没有被衡量。

### 价值判断

认知价值是低的。博客没有提出、检验或推翻任何科学主张；它宣布了一套 API 与工具，并给出了几组基准分数。反事实是：如果这篇博客不存在，Responses API、内置工具与 Agents SDK 仍然存在，SimpleQA 与 OSWorld 的分数仍然可以从开发者文档与基准排行榜上查到；博客没有留下任何离开它就不存在的认知。

方法价值是低的。博客没有留下任何别人能拿走复用的方法、评估协议、数据或代码；唯一可复用的，是它展示的产品形态本身——“一个 API 原语加内置工具加编排 SDK”这个组合思路——但这只是一个平台设计方向，不是方法。不过，对开发者来说，Agents SDK 作为开源框架本身是有实用价值的：它是代码，不是主张，博客的价值在这里是“宣布它的存在”，而不是“证明它有效”。

边界价值是中等偏高，这正是这份精读记录最有价值的部分。博客明确不证明的东西包括：SimpleQA 的 90% 能代表网络搜索工具在真实任务里的表现；38.1% 与 58.1% 能代表 CUA 在真实操作系统与网络任务里的可靠性；用这套工具构建智能体比用 Chat Completions 或 Assistants API 更容易、更可靠；Agents SDK 的编排抽象在真实的多智能体系统里够用。读者最容易误读的推论，是把“OSWorld 新纪录”读成“CUA 已经能可靠地操作计算机了”——博客自己在同一节里就否认了这个读法，但标题与开篇的语气恰恰在鼓励这种读法。

启示价值在于，最便宜的决定性实验不是再跑一遍基准，而是做一次“开发者对照”：让两组开发者用 Responses API 与用 Chat Completions 加自写胶水代码完成同一个智能体任务，比较完成时间、代码量与上线后的失败率。具体设计在下面“接下来看什么”里写。

### 最弱的一环

最弱的一环在“基准分数”与“开发智能体变容易、变可靠”之间。整篇博客的说服力，最终依赖于一个没有被检验的假设：SimpleQA 与 OSWorld/WebArena/WebVoyager 上的高分，意味着这套工具能帮开发者构建有用且可靠的智能体。

这个假设之所以承重，是因为它是博客全部证据的支点——博客没有别的证据。如果这个假设不成立，几组分数就只证明了“搜索模型答题答得准、CUA 在基准任务上比前人好”，而博客开篇承诺的“有用且可靠的智能体”就没有任何证据支撑。博客没有给出任何能裁决它的证据：没有开发者对照实验，没有上线后的可靠性数据，没有失败案例的分析。

第二弱的一环是评估条件的透明度。SimpleQA 的 90% 与 88% 没有样本量、运行次数与误差范围；三个计算机使用基准的分数没有评估协议（博客只给了一个链接，本篇没有追读）；WebArena 上 58.1% 对网络浏览智能体 57.1% 的 1 个百分点差距，读者无法判断是真实提升还是噪声；WebVoyager 上 87% 与此前最优完全持平，却被放在同一张“新纪录”语境的表里。

第三弱的一环是 Assistants API 弃用的承诺。博客说目标日落日期是 2026 年年中，但前提是“实现功能对等”——这个前提本身没有时间表，也没有衡量标准。开发者读到的是一句有条件的承诺，而不是一个确定的路线图。

### 效度判断

下面是针对博客作为证据的评分，满分 5 分，评的是证据，不是产品本身。

内部效度 1 分。博客没有描述任何评估方法：没有样本量、没有运行次数、没有误差范围、没有对照组、没有统计检验。唯一值得肯定的是它在计算机使用一节里主动承认 38.1% 意味着“还不够高度可靠”，并建议保留人工监督。

外部效度 2 分。结果能推广到什么范围，博客没有讨论。SimpleQA 是简短事实问答，推广到真实的搜索任务没有证据；OSWorld、WebArena、WebVoyager 都是基准任务，推广到真实的操作系统与网络任务没有证据；三个客户例子（Hebbia、Navan、Unify、Luminai、Coinbase、Box）都是博客挑选的成功案例，没有对照组，也没有失败案例。

构念效度 1 分。博客声称这套工具帮助开发者构建“有用且可靠的智能体”，但它用来证明这一点的指标是搜索模型的问答准确率与 CUA 的基准成功率。准确率与成功率量的是“工具在基准上表现如何”，不是“开发者构建智能体是否更容易、做出来的智能体是否可靠”——指标与声称的构念之间隔了一层没有被检验的跳跃。

统计结论效度 1 分。博客没有报告任何统计量：没有误差棒、没有运行次数、没有显著性检验、没有多重比较。WebArena 上 1 个百分点的差距，读者无法判断是真实提升还是噪声。

可复现性 1 分。博客没有给出任何可复现的材料：没有评估协议、没有数据、没有代码（Agents SDK 本身是开源的，但博客没有给出它的仓库状态或版本号，SDK 的代码不属于博客的证据）、没有提示词。一个能干的读者按博客的描述，无法重跑它的任何一张成绩单。博客的价值不在复现，而在宣布产品与公布分数。

### 其他可能的解释

同一个结果，至少有三种别的解释也能说得通。

第一种是“模型解释”。SimpleQA 的 90% 与 88% 可能主要来自 GPT-4o 与 GPT-4o-mini 本身的事实知识，而不是来自网络搜索工具。证据是：博客没有给出不带搜索的同一模型的 SimpleQA 分数，读者无法分清 90% 里有多少是搜索带来的。区分证据是：同一模型带搜索与不带搜索的对照分数，博客没有给出。

第二种是“基准解释”。CUA 在 OSWorld 上 38.1% 对 22.0% 的大幅领先，可能反映的是它擅长基准任务的特定形式，而不是擅长真实的计算机操作。预测是：如果让 CUA 在真实的、没有标准答案的操作系统任务上工作，它的成功率会明显低于 38.1%。区分证据是：一次真实任务的对照评估，或者公布评估细节文档里的任务分布与失败模式。

第三种是“挑选解释”。博客列出的六个客户例子（Hebbia、Navan、Unify、Luminai、Coinbase、Box）都是成功案例，没有失败案例，也没有说明这些客户是怎么挑出来的。预测是：如果随机抽取一批早期使用者，他们的体验会明显不如博客里的例子。区分证据是：一次对早期使用者的系统性回访，而不是博客挑选的案例。

## 七、证伪器、替代解释、接下来看什么

### 证伪器

“这套工具帮助开发者构建有用且可靠的智能体”：让两组开发者用 Responses API 与用 Chat Completions 加自写胶水代码完成同一个智能体任务，比较完成时间、代码量与上线后的失败率。如果 Responses API 组没有更快、代码没有更少、上线后的失败率没有更低，“更容易、更可靠”的说法即被反驳。

“SimpleQA 90% 证明网络搜索工具好用”：给同一模型去掉网络搜索重测 SimpleQA。如果分数没有明显下跌，90% 里的大头就是模型本身的事实知识，而不是搜索工具带来的。

“CUA 在 OSWorld 上创了新纪录，意味着它能可靠地操作计算机”：让 CUA 在真实的、没有标准答案的操作系统任务上工作，并与人类操作员对照。如果它的成功率远低于 38.1%，或者错误造成的损失不可接受，“可靠”的说法即被反驳——博客自己已经在同一节里否认了这个读法。

“Assistants API 将在 2026 年年中日落”：到 2026 年年中看 OpenAI 是否正式宣布了弃用与迁移指南。如果没有宣布，或者功能对等仍未实现，这个时间表即被证伪。

### 替代解释

替代解释一：模型解释。SimpleQA 的 90% 与 88% 可能主要来自 GPT-4o 与 GPT-4o-mini 本身的事实知识，而不是网络搜索工具。预测：去掉搜索后分数没有明显下跌。区分证据：同一模型带搜索与不带搜索的对照分数，博客没有给出。

替代解释二：基准解释。CUA 在 OSWorld 上 38.1% 对 22.0% 的领先，可能反映的是它擅长基准任务的特定形式，而不是擅长真实的计算机操作。预测：真实任务上的成功率明显低于 38.1%。区分证据：一次真实任务的对照评估，或公布评估细节文档里的任务分布与失败模式。

替代解释三：挑选解释。博客的六个客户例子都是成功案例，可能不代表早期使用者的普遍体验。预测：随机抽取的早期使用者体验明显不如博客里的例子。区分证据：一次对早期使用者的系统性回访。

### 作者自述局限与分析者发现的局限

作者自述的局限见第四节：CUA 容易犯无意的错误，尤其是在非浏览器环境里；OSWorld 上 38.1% 说明它在操作系统任务自动化上还不够可靠；建议保留人工监督。

分析者发现的、作者没说的局限有四点。第一，博客没有给出任何评估方法：没有样本量、运行次数、误差范围、对照组、统计检验，读者无法复核任何一张成绩单。第二，SimpleQA 的 90% 没有不带搜索的对照分数，读者无法分清多少来自搜索、多少来自模型本身。第三，WebArena 上 58.1% 对网络浏览智能体 57.1% 只有 1 个百分点的差距，WebVoyager 上 87% 与此前最优完全持平，但博客把三组数字放在同一张“新纪录”语境的表里，容易让读者误读为三项全面领先。第四，博客的原始发布日期无法从页面正文核实（索引日期 2025-03-11 与社区帖、TechCrunch 报道一致，但页面正文没有显示日期），而页面又是不断变化的活页面，引用时需要说明读的是哪个版本。

### 接下来看什么

最值得先做的，是做一次“开发者对照”实验。这是启示价值里最便宜的决定性实验，也是全篇最缺的一块。

具体设计：取一个真实的智能体任务（比如一个带文件检索与网络搜索的客服智能体），让两组水平相当的开发者分别用 Responses API 与用 Chat Completions 加自写胶水代码实现，比较完成时间、代码行数、上线后一周的任务失败率与调试时间。

判据很简单：如果 Responses API 组的完成时间与代码量明显更少、上线后的失败率明显更低，博客“更容易、更可靠”的说法就得到支持；如果两组没有明显差别，博客的说法就被证伪，这套工具的价值就要收回到“把工具调用做成了官方原语”这个更窄的范围。

其次是补上搜索对照：给同一模型去掉网络搜索重测 SimpleQA，看 90% 里有多少是搜索带来的。成本很低，只需要 OpenAI 公布一个数字。

再往后看三件事：追读博客链接指向的评估细节文档与更新版系统卡，看三个计算机使用基准的评估协议与失败模式；到 2026 年年中核对 Assistants API 是否如期宣布弃用；跟踪 Responses API 后续新增的工具（博客预告了未来几周与几个月内会发布更多工具），看这套原语是否真的成了 OpenAI 智能体平台的主干——后续的发布帖（例如 Responses API 新工具与功能的更新）已经证实了这一点，但那是发布之后的事，不属于本篇的核实范围。

### 未解问题

用这套工具构建智能体，到底比以前更容易、更可靠多少？说不清，需要一次开发者对照实验。

SimpleQA 的 90% 里有多少来自搜索、多少来自模型本身？说不清，需要同一模型带搜索与不带搜索的对照分数。

## I. 结论、结果与价值总览

### 一句话结论

这是一篇工程/API 发布帖，不是研究论文——它宣布了 Responses API、三件内置工具（网络搜索、文件搜索、计算机使用）与开源的 Agents SDK，并用 SimpleQA 上 90% 与 88%、OSWorld 上 38.1% 这几组正文里可核对的分数为新工具背书；但博客没有给出任何评估方法，读完只能知道它发布了什么、声称跑出什么分，不知道这些分是怎么测出来的。

### 核心结论

1. **Responses API 是 OpenAI 智能体开发的新原语（置信度：高）。** 它把 Chat Completions 的简单性与 Assistants API 的工具使用能力结合起来，发布当天向所有开发者开放；Assistants API 将在实现功能对等后走向弃用，目标日落日期 2026 年年中。

2. **三件内置工具随 Responses API 一起发布（置信度：高）。** 网络搜索适用于 gpt-4o 与 gpt-4o-mini，预览形式开放；文件搜索向所有开发者开放；计算机使用以研究预览形式向使用层级 3–5 的部分开发者开放。

3. **搜索模型在 SimpleQA 上得分 90% 与 88%（置信度：高）。** 博客正文原文；但没有不带搜索的对照分数，无法分清多少来自搜索、多少来自模型本身。

4. **CUA 在 OSWorld 上 38.1%，创了新纪录，但绝对值仍然很低（置信度：高）。** 博客正文与对照表原文；WebArena 58.1% 对网络浏览智能体只领先 1 个百分点，WebVoyager 87% 与此前最优持平。

5. **这篇博客没有确立任何科学结论（置信度：高）。** 它确立的只是一组产品事实：2025 年 3 月，OpenAI 发布了 Responses API、内置工具与 Agents SDK，定下了 Assistants API 的弃用时间表，并公布了几组基准分数。

### 科学价值总评

认知价值是低的。博客没有提出、检验或推翻任何科学主张；它宣布了一套 API 与工具，并给出了几组基准分数。如果这篇博客不存在，Responses API、内置工具与 Agents SDK 仍然存在，它们的分数仍然可以从开发者文档与基准排行榜上查到。

方法价值是低的。博客没有留下任何可复用的方法、评估协议、数据或代码；唯一可复用的，是“一个 API 原语加内置工具加编排 SDK”这个平台设计思路，以及 Agents SDK 本身作为开源框架的实用价值。

边界价值是中等偏高。它明确不证明：SimpleQA 的 90% 能代表网络搜索在真实任务里的表现；38.1% 能代表 CUA 在真实操作系统任务里的可靠性；用这套工具构建智能体比以前更容易、更可靠。最容易误读的推论，是把“OSWorld 新纪录”读成“CUA 已经能可靠地操作计算机了”——博客自己在同一节里就否认了这个读法。

总体 verdict 是：这篇工作值得被记住为 Responses API 与 Agents SDK 的发布记录，以及 SimpleQA 90%/88% 与 OSWorld 38.1% 这几组分数的原始出处。不值得被记住为“智能体问题已经解决了”的证据——那一步博客没有证明，也不该用它的数字去证明。
