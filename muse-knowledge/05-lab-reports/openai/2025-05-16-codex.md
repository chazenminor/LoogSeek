## 一、背景与问题

### 发布之前是什么局面

到 2025 年 5 月，编码助手的主流形态还是“结对编程”：人在编辑器里写代码，模型在旁边补全、回答问题、改一小段。人在，模型才动；人一走，工作就停。这种形态适合短平快的改动，但不适合那些“说清楚了就能自己干”的任务：修一个 bug、给一个模块加测试、重构一段代码、给仓库搭个新功能。工程师真正想要的，是把一个定义清楚的任务交出去，过一会儿回来验收。

OpenAI 在这篇博客里要推的，就是从“结对”到“委派”的那一步：一个云端软件工程智能体（software engineering agent），一次能并行处理多个任务，每个任务在自己的沙箱里跑，跑完交出一个可以直接审阅、可以直接开拉取请求（pull request，PR）的改动。

这篇博客没有提出一个科学问题，也没有要验证的假设。它要回答的问题是产品层面的：Codex 是什么、怎么用、凭什么可信、多少钱。它不是一篇论文，不能按论文的标准去要求它；精读它的意义在于，把它宣称的东西原原本本记下来，并且分清哪些是可核查的事实、哪些只是没有数字支撑的说法。

## 二、方法与设计

### Codex 是什么，怎么工作

Codex 是一个云端软件工程智能体，可以同时处理多个任务。每个任务在自己的云沙箱环境（cloud sandbox environment）里独立运行，沙箱预先装载了用户的代码仓库。用户通过 ChatGPT 侧边栏使用它：输入提示、点击“Code”就分配一个编码任务；点击“Ask”就是向 Codex 提问，问它关于代码库的问题。

每个任务的环境是隔离的，预先装载了代码库。Codex 可以读写文件，也可以运行命令，包括测试框架（test harness）、代码检查器（linter）和类型检查器（type checker）。任务完成通常需要 1 到 30 分钟，取决于复杂度，用户可以实时监控进度。

任务完成后，Codex 把改动提交在自己的环境里。它通过引用终端日志（terminal logs）和测试输出（test outputs）来提供可验证的证据，让用户能追踪任务完成过程中的每一步。用户随后可以审阅结果、要求进一步修改、打开一个 GitHub 拉取请求，或者直接把改动合并到本地环境里。产品里可以配置 Codex 的环境，让它尽可能贴近用户真实的开发环境。

### 驱动它的模型：codex-1

Codex 由 codex-1 驱动。codex-1 是 OpenAI o3 的一个版本，针对软件工程做了优化。它用真实世界的编码任务，在多种环境里通过强化学习（reinforcement learning）训练，目标是生成贴近人类风格、符合拉取请求偏好的代码，精确遵循指令，并能反复运行测试，直到拿到通过的结果。

博客说，在编码评估与内部基准上，即使没有 AGENTS.md 文件或自定义脚手架（scaffolding），codex-1 也表现出强劲的性能。但这句话没有配任何正文数字：评估细节只在图表里，见第六节与文末未核实清单。

Codex 可以由仓库里的 AGENTS.md 文件引导。AGENTS.md 是文本文件，类似 README.md，用户可以在里面告诉 Codex 如何导航代码库、测试时运行哪些命令、以及怎样遵守项目的标准实践。博客的说法是，像人类开发者一样，Codex 智能体在配好开发环境、可靠的测试配置和清晰的文档时表现最好。

### 安全设计：可验证、可拒绝、隔离执行

博客把安全放在产品设计的核心位置，分了三层。

第一层是可验证。Codex 发布为研究预览（research preview），符合 OpenAI 的迭代部署（iterative deployment）策略。用户可以通过引用、终端日志和测试结果检查 Codex 的工作。当智能体不确定或遇到测试失败时，它会明确把这些问题告诉用户，让用户在知情的情况下决定如何推进。但博客同时强调，用户仍然必须在集成和执行之前，手动审阅并验证所有智能体生成的代码。

第二层是防滥用。博客说，防范 AI 驱动的软件工程被恶意使用（例如开发恶意软件）越来越重要；同时，保护措施也不应过度阻碍合法的有益应用——有些合法应用会用到与恶意软件开发相同的技术，例如底层内核工程。为了平衡安全与效用，Codex 接受了训练，能够识别并精确拒绝以开发恶意软件为目标的请求，同时清楚区分并支持合法任务。OpenAI 还加强了政策框架，并做了严格的安全评估，相关评估反映在一篇 o3 系统卡增补文件里。

第三层是隔离执行。Codex 智能体完全运行在云端一个安全、隔离的容器里。在任务执行期间，发布时的配置是禁用互联网访问的，智能体只能接触用户通过 GitHub 仓库提供的代码，以及用户通过安装脚本（setup script）配置的预装依赖。它不能访问外部网站、API 或其他服务。博客加了一句注释：这描述的是发布时的配置，当前的联网选项见另外的文档。页面顶部的 2025 年 6 月 3 日更新也证实了这一点：Codex 后来允许用户在任务执行期间提供互联网访问。

### Codex CLI 的更新

博客还宣布了 Codex CLI 的更新。Codex CLI 是上个月发布的轻量级开源编码智能体，在终端里运行，把 o3 和 o4-mini 这样的模型带进本地工作流。

这次发布了一个更小的 codex-1 版本——一个为 Codex CLI 专门设计的 o4-mini 版本。这个新模型支持更快的 CLI 工作流，针对低延迟的代码问答（Q&A）与编辑做了优化，同时保留了在指令遵循与风格上的同样优势。它现在是 Codex CLI 的默认模型，也以 codex-mini-latest 的名字出现在 API 里，底层快照（snapshot）会随着改进定期更新。

连接开发者账号也变容易了：不用再手动生成和配置 API 令牌，用户可以用 ChatGPT 账号登录，选择 API 组织，系统会自动生成并配置 API 密钥。用 ChatGPT 登录 Codex CLI 的 Plus 和 Pro 用户，从当天起可以在接下来的 30 天里分别兑换 5 美元和 50 美元的免费 API 额度。

## 三、主要发现

### 发布内容：向谁开放，多少钱

发布当天，Codex 开始向全球的 ChatGPT Pro、Enterprise 和 Business 用户推出，Plus 和 Edu 的支持随后到来。页面顶部的 2025 年 6 月 3 日更新说明，Codex 已向 ChatGPT Plus 用户开放。用户在接下来的几周里可以免费获得慷慨的访问额度，之后 OpenAI 将推出限速访问（rate-limited access）与灵活的定价选项，允许按需购买更多用量。

面向开发者的 codex-mini-latest 模型通过 Responses API 提供，定价是每百万输入 token 1.50 美元、每百万输出 token 6 美元，提示缓存（prompt caching）有 75% 的折扣。

### 早期使用情况

博客说，OpenAI 内部的技术团队已经开始把 Codex 当作日常工具的一部分。OpenAI 的工程师最常用它来分担重复的、范围明确的任务，例如重构、重命名和写测试，这些任务原本会打断注意力。它同样适用于搭建新功能、连接组件、修 bug 和起草文档。团队正在形成新的工作习惯：在值班时分流待办问题、在一天开始时规划任务、把后台工作交出去以保持推进。博客的说法是，通过减少上下文切换、把被遗忘的待办事项翻出来，Codex 帮助工程师更快交付、保持专注。

发布之前，OpenAI 还与一小批外部测试者合作，了解 Codex 在不同代码库、开发流程和团队里的表现。博客点名了四家：Cisco 正在探索 Codex 如何帮助其工程团队更快实现雄心勃勃的想法，作为早期设计伙伴，Cisco 通过在产品组合中评估 Codex 提供反馈；Temporal 用 Codex 加速功能开发、调试、编写和执行测试、重构大型代码库，并在后台运行复杂任务以保持工程师的心流；Superhuman 用 Codex 加速小而重复的任务，例如提高测试覆盖率、修复集成失败，并让产品经理无需拉上工程师就能贡献轻量级的代码改动（代码审阅除外）；Kodiak 用 Codex 编写调试工具、提高测试覆盖率、重构代码，加速其自动驾驶技术 Kodiak Driver 的开发，Codex 也成了有价值的参考工具，帮助工程师理解不熟悉的代码。

基于早期测试者的经验，博客建议把范围明确的任务同时分配给多个智能体，并尝试不同类型的任务与提示，以有效探索模型的能力。

### 博客自己承认的局限

作为研究预览，Codex 目前缺少一些功能，例如面向前端工作的图像输入（image inputs），以及在智能体工作时中途纠正（course-correct）它的能力。此外，把任务委派给远程智能体比交互式编辑耗时更长，这需要适应。

博客对未来的设想是：开发者驱动自己想亲自做的工作，把其余的委派给智能体。OpenAI 正在构建一套 Codex 工具，支持实时协作与异步委派两种模式。博客认为，Codex 在 ChatGPT 里引入的异步、多智能体工作流，会成为工程师生产高质量代码的默认方式。未来，开发者将能提供任务中的指导、协作制定实现策略、收到主动的进度更新，并通过更深的集成使用自己已有的工具：今天 Codex 连接 GitHub，未来可以从 Codex CLI、ChatGPT 桌面版，甚至问题追踪器（issue tracker）或持续集成（CI）系统里分配任务。

### 附录：codex-1 的系统提示

博客附录分享了 codex-1 的系统提示（system message），目的是帮助开发者理解模型的默认行为，并在自定义工作流里有效使用 Codex。例如，codex-1 的系统提示鼓励 Codex 运行 AGENTS.md 文件里提到的所有测试；如果时间紧张，用户可以要求它跳过这些测试。

## 四、作者的结论与局限

### 作者的结论

博客没有研究结论。它要传达的信息是三句：Codex 已经可以用了，是一个能并行处理任务的云端编码智能体；它由针对软件工程优化的 codex-1 驱动；它的安全设计建立在可验证的证据、精确拒绝恶意请求和隔离执行这三层上。

关于未来，博客的判断是：实时结对与任务委派这两种模式最终会汇合，开发者将在 IDE 与日常工具里与 AI 智能体协作，提出建议、接手较长的任务。软件工程是第一批经历显著 AI 生产力提升的行业之一，OpenAI 对此表示乐观，同时也在与合作伙伴一起研究广泛采用智能体对开发者工作流、技能发展的影响。

### 作者自述的局限

博客明确承认的局限有三点：第一，作为研究预览，Codex 缺少图像输入，无法做前端工作；第二，无法在智能体工作时中途纠正它；第三，委派给远程智能体比交互式编辑更耗时。

除此之外，博客没有列出别的局限。特别是，它没有报告任何可核查的基准数字，也没有给出评估方法的细节。这一点不是博客自己承认的局限，是分析者发现的缺口，见下一节。

## 五、精读点评

这一节是分析者的判断，和上面对博客的呈现分开写。

### 这篇文档真正要回答的问题

这篇文档真正要回答的问题不是科学问题，而是产品问题：一个能并行干活的云端编码智能体，值不值得你现在就用。它给出的答案分两层。第一层是产品形态本身：每个任务一个隔离沙箱、预装代码库、能读写文件和跑测试、1 到 30 分钟交活、交活时附上终端日志和测试输出作证据、可以开 GitHub 拉取请求——这套形态是具体的、可核查的。第二层是“它有多强”：博客说 codex-1 在编码评估与内部基准上表现强劲，但没有给出任何正文数字，唯一的评估细节是一张图和一句关于 23 个 SWE-bench Verified 样本被排除的脚注。第二层是这篇博客立不住的部分。

### 科学问题还原：五问

**现象是什么？** 编码助手停留在“结对”形态：人不动，模型不动；人一走，工作就停。重复的、范围明确的任务不断打断工程师的注意力。反常不在于某一次实验失败，而在于“模型能写代码”和“模型能独立干完一个任务”之间没有现成的产品形态——前者已经有了，后者还没有。

**为什么重要，不解决会怎样？** 对实践来说，不解决它，工程师就只能把时间花在重复的、范围明确的任务上，上下文切换的成本一直存在；对领域来说，不解决它，编码智能体就只能停留在“助手”这个位置，异步委派、多智能体并行这条路就走不通。这篇博客的重要性首先在于它宣布了一个可用的产品形态，而不是提出了一个新发现。

**为什么之前做不了？** 博客没有回答这个问题。分析者能从产品描述里推断的 blocker 有三个：一是执行环境，要给每个任务一个隔离的、预装了代码库的沙箱；二是可验证性，要让用户能追踪智能体的每一步，而不是只拿到一个结果；三是安全，要在不阻碍合法用途的前提下拒绝恶意软件开发。但这三点是分析者的推断，博客本身没有把它们写成“之前卡住的点”。

**方法与问题是否匹配？** 这篇文档没有方法，也就没有方法与问题的匹配问题。它提供的不是一个实验设计，而是一个产品：codex-1 模型、沙箱执行、AGENTS.md 引导、终端日志作证据。这套产品设计回答的是“怎么把编码任务委派出去”，而不是“模型的能力有多强”。把博客里的“强劲表现”读成一个评估结论，就是方法与问题不匹配的地方——博客根本没有做评估报告该做的事。

**答案改变了什么？** 认知上，什么都没改变——博客没有提供任何新证据来改变我们对模型编码能力的认识。实践上，它改变了一件事：从 2025 年 5 月 16 日起，ChatGPT Pro、Enterprise 和 Business 用户可以直接用上一个云端并行编码智能体，Plus 用户在 6 月 3 日之后也能用；开发者可以通过 API 用上 codex-mini-latest，每百万输入 token 1.50 美元、每百万输出 token 6 美元。这是一次产品发布，不是一次认知更新。

### 价值判断

认知价值是低的。博客没有推翻或确认任何信念，也没有给出任何可复核的数字。反事实是：如果这篇博客不存在，我们对 codex-1 编码能力的认识不会有任何不同——因为它本来就没有提供认识它的证据。

方法价值是低的。它留下的可复用东西只有两样：一是 AGENTS.md 这个约定——用仓库里的文本文件告诉智能体如何导航代码库、跑哪些测试、遵守哪些规范；二是“终端日志加测试输出作证据”这个可验证性设计。这两样都是产品设计层面的做法，不是研究方法。附录分享的 codex-1 系统提示对开发者有用，但它是一份配置，不是一项方法。

边界价值是中等偏高的，这正是这份精读记录最有价值的部分。它明确不证明的东西包括：codex-1 在 SWE-bench Verified 上的具体分数（只在图里）；codex-1 比 o3 强多少（博客只说“始终产出更干净的补丁”，没有数字）；内部基准上的“强劲表现”到底是多少；以及 Codex 在真实代码库上的任务成功率。读者最容易误读的推论，是把博客里的“强劲表现”读成“codex-1 在 SWE-bench 上拿了某个高分”——那个分数在正文里根本不存在，图里的数字本次精读没有核实，不能引用。

### 最弱的一环

## 七、证伪器、替代解释、接下来看什么

“codex-1 在编码评估上表现强劲”：找到发布时配套的评估数字（SWE-bench Verified 的通过率、与 o3 的对照、内部基准的任务数与分数）。如果 codex-1 的分数与 o3 相当或更低，“强劲表现”就只能退回为“与 o3 相当”。

## I. 结论、结果与价值总览

### 一句话结论

这是一篇产品发布博客，不是研究论文：它宣布了云端并行编码智能体 Codex 与 codex-1 模型，给出了具体的工作方式、安全设计与定价，但关于模型能力，没有给出任何正文里可核查的数字。

### 核心结论

1. **Codex 是一个云端并行编码智能体（置信度：高）。** 每个任务在自己的沙箱里独立运行，预装代码库，能读写文件、跑测试，1 到 30 分钟交活，交活时附上终端日志与测试输出作证据，可以开 GitHub 拉取请求。

2. **codex-1 是针对软件工程优化的 o3 版本（置信度：高）。** 用真实世界编码任务做强化学习训练，目标是贴近人类风格、符合拉取请求偏好、精确遵循指令、反复跑测试直到通过。Codex CLI 的默认模型是更小的 o4-mini 版本 codex-mini-latest。

3. **“强劲表现”没有数字支撑（置信度：高）。** 博客说 codex-1 在编码评估与内部基准上表现强劲，但正文没有给出任何分数；SWE-bench Verified 的数字只在图里，本次精读未核实；内部基准的任务数与评分方式没有说明。

4. **安全设计有三层，但可核查性有限（置信度：中）。** 可验证的证据（终端日志与测试输出）、精确拒绝恶意请求、隔离执行（发布时禁用互联网访问）——前两层的具体效果没有数字，第三层有明确的发布时配置，并被 6 月 3 日的更新修改。

5. **定价与开放范围是明确的（置信度：高）。** codex-mini-latest 每百万输入 token 1.50 美元、每百万输出 token 6 美元，提示缓存 75% 折扣；发布时向 Pro、Enterprise、Business 开放，Plus 用户在 2025 年 6 月 3 日之后可用；Codex CLI 登录用户可兑换 5 美元（Plus）或 50 美元（Pro）的免费 API 额度，30 天内有效。
