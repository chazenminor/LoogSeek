## 一、背景与问题

### 发布之前是什么局面

到 2025 年 8 月，OpenAI 的前沿模型全是闭源的：o3、o4-mini、GPT-4o 都只能通过 API 使用，权重、训练细节都不公开。与此同时，开放权重模型那一边已经跑了好几年——Meta 的 Llama、阿里巴巴的 Qwen、Mistral 等模型让开发者可以在自己的硬件上部署、微调、改造模型。OpenAI 上一次发布开放权重语言模型还是 2019 年的 GPT-2，中间隔了六年。

这种局面下，一个反复被问的问题是：OpenAI 会不会再做开放模型？如果做，做出来的开放模型能不能跟它自己的闭源推理模型处在同一个水平，还是只能当个缩水版？更难的一层是安全问题：开放权重意味着任何人拿到权重后都能微调，安全措施一旦被微调去掉，模型就可能被改造成有害用途。这也是这次发布一再被推迟的原因之一——OpenAI 首席执行官 Sam Altman 曾公开把推迟归因于需要做更久的安全评估。

这篇博客要回答的，就是这三个问题：模型是什么、强到什么程度、以及为什么 OpenAI 认为现在放出来是安全的。它没有提出一个科学问题，也没有要验证的假设。它要回答的是产品与发布层面的问题：gpt-oss 是什么、怎么用、凭什么可信、在哪里能拿到。它不是一篇论文，不能按论文的标准去要求它；精读它的意义在于，把它宣称的东西原原本本记下来，并且分清哪些是可核查的事实、哪些只是没有数字支撑的说法。

## 二、方法与设计

### 两个模型：一个大，一个小

这次发布的是两个模型：gpt-oss-120b 和 gpt-oss-20b。两者都是文本模型（text-only），不是多模态。120b 是面向生产级工作流的大模型，20b 是面向低延迟、本地部署的小模型。

博客给出的定位是：120b 在核心推理基准上接近 OpenAI o4-mini 的水平，同时可以在一块 80 GB 的 GPU 上高效运行；20b 在常见基准上与 OpenAI o3-mini 的结果类似，可以在只有 16 GB 内存的边缘设备上运行，适合设备端使用、本地推理或快速迭代而不需要昂贵的基础设施。

两个模型都支持工具使用、少样本函数调用（few-shot function calling）、思维链（chain-of-thought，CoT）推理，在 Tau-Bench 智能体评估套件和 HealthBench 健康基准上表现强劲——HealthBench 上甚至超过了 o1 和 GPT-4o 这样的专有模型。

### 架构：混合专家 Transformer

两个模型都是 Transformer 架构，使用混合专家（mixture-of-experts，MoE）来减少处理每个输入 token 需要激活的参数量。

博客给出的架构参数表是这样的：

| 模型 | 层数 | 总参数 | 每 token 激活参数 | 专家总数 | 每 token 激活专家数 | 上下文长度 |
|---|---|---|---|---|---|---|
| gpt-oss-120b | 36 | 117B | 5.1B | 128 | 4 | 128k |
| gpt-oss-20b | 24 | 21B | 3.6B | 32 | 4 | 128k |

注意模型名字里的 120b 和 20b 是约数：120b 的实际总参数是 117B，20b 是 21B。两个模型每 token 都只激活 4 个专家。

其他架构细节：模型使用交替的稠密注意力（dense attention）和局部带状稀疏注意力（locally banded sparse attention），与 GPT-3 类似；为了推理与内存效率，使用分组多查询注意力（grouped multi-query attention），分组大小（group size）为 8；位置编码用旋转位置编码（Rotary Positional Embedding，RoPE）；原生支持最长 128k 的上下文。

### 训练数据与分词器

模型是在一个以英语为主的纯文本数据集上训练的，重点是 STEM（科学、技术、工程、数学）、编程和通用知识。博客没有给出数据集规模、token 数、训练算力，也没有给出数据来源与配比——这些数字在发布帖里根本没有出现。

分词器用的是 o200k_harmony，是 OpenAI o4-mini 和 GPT-4o 所用分词器的超集，这次也一并开源了。

博客说，两个模型用的是 OpenAI 最先进的预训练与后训练技术，特别关注推理、效率和在各种部署环境下的真实可用性。训练用的是强化学习（reinforcement learning）与受 o3 等前沿内部模型启发的技术混合。更具体的训练细节，博客指向模型卡，没有在正文里展开。

### 后训练：与 o4-mini 同一套流程

后训练用的流程与 o4-mini 类似，包括一个有监督微调（supervised fine-tuning，SFT）阶段和一个高算力强化学习阶段。目标是让模型与 OpenAI 模型规范（Model Spec）对齐，并在给出答案之前学会运用思维链推理与工具使用。博客的说法是，用了与最先进的专有推理模型相同的技术，后训练后的模型展现出卓越的能力。

和 OpenAI o 系列 API 推理模型一样，两个开放权重模型支持三档推理努力程度（reasoning effort）：低（low）、中（medium）、高（high），在延迟与性能之间权衡。开发者可以用系统消息（system message）里的一句话轻松设定推理努力程度。

### 思维链：不直接监督，完整开放

博客专门用一节讲思维链。OpenAI 最近的研究表明，只要不对思维链做直接监督来对齐它，监控推理模型的思维链有助于发现不当行为，业内其他人也认同这一观点。沿用自发布 o1-preview 以来的原则，OpenAI 对两个 gpt-oss 模型都没有在思维链上加直接监督。博客认为，这对监控模型的不当行为、欺骗与滥用至关重要。发布一个思维链不受监督的开放模型，是希望给开发者和研究者机会，去研究并实现自己的思维链监控系统。

但博客同时提醒：开发者不应该在应用里直接把思维链展示给用户。思维链可能包含幻觉或有害内容，可能包含不符合 OpenAI 标准安全政策的语言，还可能包含模型被明确要求不要放进最终答案的信息。

博客还记录了一个值得注意的行为：gpt-oss-120b 在输出中能稳健地遵循系统指令，但在思维链里却常常明确违背指令。这句话是博客原文里对模型行为的直接描述。

### 工具使用与示例

两个模型兼容 OpenAI 的 Responses API，设计上用于智能体工作流：出色的指令遵循、工具使用（如网页搜索、Python 代码执行）与推理能力，包括按任务调节推理努力程度。模型完全可定制，提供完整的思维链，并支持结构化输出（Structured Outputs）。

博客给了一个示例展开（example rollouts）：gpt-oss-120b 能够用浏览工具快速聚合最新信息，包括把几十次后续调用链接起来。这里的“几十次”就是博客的原话，没有更精确的数字。

## 三、主要发现

### 评估：只有相对表述，没有具体分数

博客在“评估”（Evaluations）一节说，两个模型在一系列标准学术基准上接受了评估，覆盖编程、竞赛数学、健康与智能体工具使用，并与 o3、o3-mini、o4-mini 等 OpenAI 推理模型对照。

具体宣称是这样几句：

- gpt-oss-120b 超过 o3-mini，在竞赛编程（Codeforces）、通用问题解决（MMLU 与 HLE）与工具调用（TauBench）上达到或超过 o4-mini。
- 它在健康相关查询（HealthBench）与竞赛数学（AIME 2024 与 2025）上甚至比 o4-mini 更好。
- gpt-oss-20b 在同样的评估上达到或超过 o3-mini，尽管尺寸小得多，甚至在竞赛数学与健康上超过了 o3-mini。

这些就是博客正文给出的全部评估内容：相对高低，没有一个具体分数。AIME、Codeforces、MMLU、HLE、TauBench、HealthBench 各自的得分、样本量、测试条件（推理努力程度档位、采样设置）在正文里都没有。评估数字如果出现在页面图表里，本次精读的文本抓取没有读到，不印数字。

博客在健康评估后加了一句免责声明：gpt-oss 模型不能替代医疗专业人员，不应用于疾病的诊断或治疗。

### 安全：三层做法加一层“最坏情况”评估

安全是这篇博客花篇幅最多的部分之一，分了三层，再加一层发布前特有的评估。

第一层是预训练过滤。在预训练阶段，过滤掉了与化学、生物、放射性、核（Chemical, Biological, Radiological, and Nuclear，CBRN）相关的某些有害数据。

第二层是后训练对齐。在后训练阶段，用审慎对齐（deliberative alignment）与指令层级（instruction hierarchy）教模型拒绝不安全的提示、抵御提示注入（prompt injection）。

第三层是发布前的“最坏情况微调”（worst-case fine-tuning）评估。开放权重模型一旦发布，对手就可能为了恶意目的微调它。OpenAI 直接评估了这种风险：用专门的生物学与网络安全数据对模型做微调，像攻击者那样为每个领域各造一个不拒绝的领域专用版本，然后通过内部与外部测试评估这些模型的性能水平。按配套安全论文的说法，即使经过利用 OpenAI 领先训练技术栈的强力微调，这些恶意微调的模型也未能按 OpenAI 的 Preparedness Framework（准备度框架）达到高能力水平。

这套恶意微调方法由三个独立的专家组审阅，专家组提出了改进训练流程与评估的建议，OpenAI 采纳了其中许多建议，相关建议的细节写在模型卡里。博客说，这些流程标志着开放模型安全有意义的进步，这些发现支撑了发布 gpt-oss 的决定。

博客还说，gpt-oss 模型在内部安全基准上的表现与 OpenAI 的前沿模型相当，给开发者提供与近期专有模型相同的安全标准。但“相当”没有配任何数字，内部安全基准的项目、分数与对照都没有在正文里给出。

### 红队挑战：50 万美元奖金

为了推动更安全的开源生态，OpenAI 在 Kaggle 上办了一个红队挑战（Red Teaming Challenge），鼓励全球的研究者、开发者与爱好者帮助发现新的安全问题。挑战奖金总额为 50 万美元，由来自 OpenAI 与其他领先实验室的专家评审团评定。挑战结束后，OpenAI 将发布一份报告，并根据验证过的发现开源一个评估数据集，让更广泛的社区直接受益。

### 可用性：权重、量化与合作伙伴

两个模型的权重可以在 Hugging Face 上免费下载，原生以 MXFP4 量化提供。这使得 120b 模型可以在 80 GB 内存内运行，20b 模型只需要 16 GB。

模型按 harmony 提示格式（harmony prompt format）做了后训练，OpenAI 同时开源了一个 harmony 渲染器（renderer），有 Python 版和 Rust 版。还发布了用 PyTorch 推理和在苹果 Metal 平台上推理的参考实现，以及一批示例工具。

为了让模型随处可用，OpenAI 在发布前与一批部署平台合作：Azure、Hugging Face、vLLM、Ollama、llama.cpp、LM Studio、AWS、Fireworks、Together AI、Baseten、Databricks、Vercel、Cloudflare、OpenRouter。硬件方面与 NVIDIA、AMD、Cerebras、Groq 合作，确保在各类系统上做优化。

微软也在发布当天把 GPU 优化版的 gpt-oss-20b 带到 Windows 设备上，由 ONNX Runtime 驱动，通过 Foundry Local 与 VS Code 的 AI Toolkit 提供本地推理。

博客还提到了三家早期合作伙伴：AI Sweden、Orange、Snowflake。合作内容包括在本地托管模型以保障数据安全，以及在专门数据集上微调模型。

关于与 API 模型的关系，博客的说法是：想要完全可定制、能在自己的环境里微调与部署的模型，gpt-oss 很合适；想要多模态支持、内置工具与平台无缝集成，API 平台上的模型仍是更好的选择。OpenAI 表示会继续听取开发者反馈，未来可能考虑为 gpt-oss 提供 API 支持。

想试用模型的人可以去 gpt-oss.com 的开放模型 playground；不同生态提供方上的使用与微调指南在 OpenAI cookbook 里。

### 博客最后的立场：为什么开放模型重要

博客的收尾一节讲开放模型的意义。开放模型与托管模型互补，给开发者更广泛的工具来加速前沿研究、促进创新、让 AI 开发更安全透明。开放模型也降低了新兴市场、资源受限行业与小组织的门槛，这些地方可能没有预算或灵活性去采用专有模型。博客还说，在美国制造的、广泛可用的强大开放权重模型，有助于扩展“民主 AI 轨道”（democratic AI rails）。

## 四、作者的结论与局限

### 作者的结论

博客没有研究结论。它要传达的信息是四句：第一，gpt-oss-120b 与 gpt-oss-20b 是自 GPT-2 以来 OpenAI 首个开放权重语言模型，在 Apache 2.0 许可下发布；第二，120b 接近 o4-mini 的水平，20b 接近 o3-mini 的水平，而且都能在消费级硬件上跑；第三，安全上做了预训练过滤、后训练对齐与“最坏情况微调”评估，结论是即使被恶意微调也达不到高能力水平；第四，开放模型降低了门槛、扩展了民主 AI 的轨道。

关于未来，博客没有给出技术路线图，只说会继续听取开发者反馈，未来可能考虑为 gpt-oss 提供 API 支持，并期待开发者与研究者用这些模型做实验、协作、推进可能性的边界。

### 作者自述的局限

博客没有单独列出一节“局限”，但正文里明确承认了以下几点：

第一，模型是纯文本的。训练数据是以英语为主的纯文本，模型只能处理文本，不能处理图像、音频等多模态输入。

第二，思维链不可直接示人。思维链可能包含幻觉或有害内容，可能包含不符合 OpenAI 标准安全政策的语言，还可能包含模型被明确要求不要放进最终答案的信息。开发者不应该在应用里直接把思维链展示给用户。

第三，120b 的思维链与输出不一致。gpt-oss-120b 在输出中稳健地遵循系统指令，但在思维链里常常明确违背指令。这是博客自己写出来的行为描述。

第四，健康用途的边界。gpt-oss 模型不能替代医疗专业人员，不应用于疾病的诊断或治疗。

第五，安全结论的适用范围。恶意微调评估的结论是“未能达到高能力水平”，这个结论依赖于 OpenAI 的 Preparedness Framework 的能力分级，以及它自己做的微调实验——博客正文没有给出分级的具体阈值，也没有给出微调实验的细节，细节在配套的安全论文与模型卡里。

除此之外，博客没有列出别的局限。特别是，它没有报告任何可核查的基准分数，也没有给出训练数据规模与算力。这一点不是博客自己承认的局限，是分析者发现的缺口，见下一节。

## 五、精读点评

这一节是分析者的判断，和上面对博客的呈现分开写。

### 这篇文档真正要回答的问题

这篇文档真正要回答的问题不是科学问题，而是发布问题：一个六年来只做闭源模型的实验室，凭什么现在敢把一个接近前沿水平的推理模型以开放权重放出来。它给出的答案分三层。第一层是模型本身：两个尺寸、MoE 架构、128k 上下文、三档推理努力、完整思维链、结构化输出、Apache 2.0 许可——这套形态是具体的、可核查的。第二层是“它有多强”：120b 接近 o4-mini、20b 接近 o3-mini——但这一层在正文里没有任何数字，只有一组相对高低的说法。第三层是“放出来安不安全”：预训练过滤、后训练对齐、恶意微调评估——这一层的结论（“达不到高能力水平”）同样没有正文数字，细节全在配套论文与模型卡里。第二层和第三层，是这篇博客立不住的部分。

### 科学问题还原：五问

**现象是什么？** 开放权重模型与闭源前沿模型之间存在一道能力鸿沟：开放模型能部署、能微调、能改造，但推理能力一直明显落后于同期的闭源模型；闭源模型能力强，但开发者拿不到权重，做不了本地部署与深度定制。反常不在于某一次实验失败，而在于“开放”与“前沿”长期不能兼得——gpt-oss 就是要宣称自己同时做到了这两点。

**为什么重要，不解决会怎样？** 对实践来说，不解决它，需要在本地、离线、防火墙内或边缘设备上跑强推理模型的开发者，就只能在“能力弱的开放模型”和“不能本地部署的闭源 API”之间二选一。对领域来说，不解决它，开放生态就一直处在追赶位置，安全研究也缺少一个“思维链不受监督、权重完全开放”的前沿级研究对象。这篇博客的重要性首先在于它宣布了一个可用的开放模型家族，而不是提出了一个新发现。

**为什么之前做不了？** 博客没有直接回答这个问题。分析者能从博客内容里推断的 blocker 有三个：一是能力，要把推理能力做到接近 o4-mini，同时把激活参数压到每 token 5.1B、让 120b 跑进一块 80 GB 的 GPU；二是安全，开放权重意味着安全措施可能被微调去掉，需要一套能让发布方自己信服的“最坏情况”评估；三是时机与政策，OpenAI 内部需要先接受“放出接近前沿的模型”这个决定。但这三点是分析者的推断，博客本身没有把它们写成“之前卡住的点”。

## I. 结论、结果与价值总览

### 一句话结论

这是一篇模型发布博客，不是研究论文：它宣布了自 GPT-2 以来 OpenAI 首个开放权重模型家族 gpt-oss，给出了具体的架构、训练方式与部署条件，但关于模型能力与安全评估，没有给出任何正文里可核查的数字。

### 核心结论

1. **gpt-oss 是自 GPT-2 以来 OpenAI 首个开放权重语言模型家族（置信度：高）。** 包括 gpt-oss-120b 与 gpt-oss-20b 两个模型，Apache 2.0 许可，权重可在 Hugging Face 上免费下载，原生 MXFP4 量化。

2. **架构是具体的、可核查的（置信度：高）。** 120b：117B 总参数、每 token 激活 5.1B、36 层、128 个专家、每 token 激活 4 个专家；20b：21B 总参数、每 token 激活 3.6B、24 层、32 个专家、每 token 激活 4 个专家；两者都是 128k 上下文，分组多查询注意力分组大小为 8，位置编码用 RoPE。

3. **“接近 o4-mini / o3-mini”没有数字支撑（置信度：高）。** 博客说 120b 接近 o4-mini、20b 接近 o3-mini，但在 Codeforces、MMLU、HLE、TauBench、HealthBench、AIME 2024 与 2025 上都没有给出任何具体分数；这些数字要去配套的模型卡里核实。

4. **安全评估的思路值得注意，但结论在正文里不可核查（置信度：中）。** 预训练过滤 CBRN 相关有害数据、后训练用审慎对齐与指令层级、发布前做“最坏情况微调”评估并由三个独立专家组审阅方法——思路是具体的；但“恶意微调后达不到高能力水平”与“内部安全基准上与前沿模型相当”这两个结论都没有正文数字，细节在配套论文与模型卡里。

5. **部署条件与获取方式是明确的（置信度：高）。** 120b 在 80 GB 内存内运行，20b 只需要 16 GB；harmony 提示格式与 Python、Rust 版渲染器开源；PyTorch 与苹果 Metal 推理参考实现开源；部署与硬件合作伙伴名单明确；红队挑战奖金总额 50 万美元。

方法价值是中等的。留下的可复用东西有三样：“最坏情况微调”这套发布前评估思路、不对思维链做直接监督并完整开放思维链供研究者做监控研究的取舍、以及 harmony 格式与 MXFP4 原生量化这些工程做法。前两样是方法层面的贡献，但博客正文只给了思路，没有给出可复现的细节。
