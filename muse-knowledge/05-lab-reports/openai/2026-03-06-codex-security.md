## 一、背景与问题

### 发布之前是什么局面

博客开篇给出的局面是两难：上下文（context）对判断真正的安全风险至关重要，但大多数 AI 安全工具只会标记低影响的发现与误报，迫使安全团队花大量时间做分流（triage）。与此同时，智能体（agent）正在加速软件开发，安全审查越来越成为瓶颈。Codex Security 要同时解决这两个问题：用前沿模型的智能体推理加上自动验证，给出高置信度的发现与可操作的修复，让团队把精力放在真正重要的漏洞上，更快地交付安全的代码。

### 这篇博客要宣布什么

博客宣布推出 Codex Security，一个应用安全智能体（application security agent）。它原名 Aardvark（LR-237 已精读，2025 年 10 月宣布进入私人测试），去年以私人测试的形式在一小批客户中使用。从今天起，它以研究预览（research preview）的形式向 ChatGPT Pro、Enterprise、Business 和 Edu 客户推出，通过 Codex 网页版（Codex web）使用，接下来一个月免费。

### 这是一篇什么样的文档

这是一篇产品发布博客，没有署名作者，不是研究论文。它没有研究问题、没有实验设计、没有评估方法，只有一组定性主张、几条规模与改进数字、一段客户评价、一节开源工作说明与一个附录（附录列出了发现的高影响开源漏洞）。

正因为如此，这篇精读的老实写法是：它能回答的只是“OpenAI 发布了什么、怎么说的、产品长什么样、测试期间测出了什么规模的数字”，回答不了“Codex Security 到底有多准、多可靠”。把一篇发布博客读成一篇论文，是对它的误读；把它当作发布博客来读，它的信息是完整的。

## 二、方法与设计

### 文档结构

博客按这个顺序展开：宣布 Codex Security、它怎么工作、一段客户评价、支持开源社区的说明、开始使用的指引、附录（高影响开源漏洞示例）。没有方法、没有数据、没有评估细节。

### Codex Security 是怎么工作的

博客说，Codex Security 利用 OpenAI 的前沿模型与 Codex 智能体，把漏洞发现、验证与打补丁扎根在系统特有的上下文里，以此减少噪声、加速修复。工作分三步：

第一步是建立系统上下文、生成可编辑的威胁模型（threat model）。配置扫描之后，它分析代码仓库，理解系统与安全相关的结构，生成一份针对该项目的威胁模型，记录系统是做什么的、信任什么、在哪里最暴露。威胁模型可以编辑，让智能体与团队的理解保持一致。

第二步是排优先级并验证问题。用威胁模型作上下文，它搜索漏洞，按在该系统里的预期真实影响对发现分类。在可能的情况下，它在沙箱验证环境里对发现做压力测试（pressure-test），以区分信号与噪声，用户可以在已验证的发现里看到这份分析。如果 Codex Security 配置了针对该项目定制的环境，它可以直接在运行系统的上下文里验证潜在问题：更深的验证可以进一步降低误报，还能生成可用的概念验证（proof-of-concept），给安全团队更强的证据与更清晰的修复路径。

第三步是带着完整的系统上下文打补丁。它针对发现的问题提出修复方案，与系统意图和周围行为保持一致：这样的补丁既能提升安全性，又能尽量减少回归（regression），让审查与合并更安全。用户可以筛选发现，只关注对团队最重要、安全影响最大的部分。

博客还说，Codex Security 能随时间从用户的反馈中学习：当用户调整某个发现的严重级别时，它可以用这份反馈优化威胁模型，在后续运行中提高精度，因为它学会了什么在用户的架构与风险姿态里重要。

### 按检查表，什么是“未报告”

按 NeurIPS / Pineau 检查表的思路，这篇博客未报告的项目包括：所用的具体模型版本与配置、威胁模型生成的具体实现、沙箱验证的覆盖率（多少发现真正经过了验证）、三条改进率（噪声、严重级别高报、误报率）的分母与基线、与任何基线方法（包括传统工具与人类研究员）的对照、人类评估、失败案例、以及可复现路径。这不是疏漏——发布博客本来就不承担这些。精读的任务是把“没给”记下来，而不是替它补上。

## 三、主要发现

### 测试期间的改进：三条没有分母的比率

博客说，Codex Security 去年以私人测试开始。早期内部部署中，它发现了一个真实的 SSRF（服务器端请求伪造）、一个严重的跨租户认证漏洞（cross-tenant authentication vulnerability），以及许多其他问题，OpenAI 的安全团队在数小时内打了补丁。外部测试者的早期部署帮助改进了用户提供产品上下文的方式，以及从接入到开始保护代码的流程。

测试期间发现的质量“显著提高”：在同一批仓库上随时间重复扫描，精度不断上升——在一个案例里，自最初推出以来噪声（noise）减少了 84%；严重级别被高报（over-reported severity）的发现率下降了 90% 以上；所有仓库的检测误报率下降了 50% 以上。博客说，这些改进让 Codex Security 报告的严重级别更符合真实风险、减少了不必要的分流负担，并且预计信噪比会继续改善。

这三条比率的问题在于，博客没有给出任何一条的分母与基线：84% 的噪声减少只说“在一个案例里”，没有说那是哪个仓库、噪声的原始水平是多少、用什么量噪声；90% 以上与 50% 以上没有说基线是多少、测了多少仓库、覆盖了多长时间。它们是博客原话的方向性说法，不能按精确测量引用。

### 规模数字：过去 30 天的扫描量

博客给出的最扎实的一组数字是规模数字：在过去 30 天里，Codex Security 在测试队列（beta cohort）的外部仓库上扫描了超过 120 万次提交（commit），识别出 792 个严重（critical）发现与 10,561 个高严重级别（high-severity）发现。严重问题出现在不到 0.1% 的被扫描提交中。博客用这个数字论证：系统能在大量代码里找出有安全影响的问题，同时把给审查者的噪声控制在最小。

这组数字内部是一致的：792 除以 120 万约为 0.066%，确实不到 0.1%。但它仍然缺少关键条件：博客没有说测试队列有多少个仓库、这些仓库是什么类型与规模、792 个与 10,561 个发现里有多少经过了沙箱验证、有多少被人工确认、有多少已经修复。没有这些，它能支撑的只是“在测试队列的 30 天里扫出了这个量级的发现”，支撑不了“这些发现都是真的”或“误报率很低”。

### 一段客户评价

博客引用了 NETGEAR 产品安全负责人 Chandan Nandakumaraiah 的话：作为一家专注于产品安全的公司，NETGEAR 很高兴加入早期访问计划，结果超出预期；Codex Security 毫不费力地融入了他们强大的安全开发生命环境，加强了审查流程的速度与深度；它的发现非常清晰全面，常常让人感觉像一位经验丰富的产品安全研究员在并肩工作。

这段话是客户评价，不是证据。它说明了一家早期使用者的第一反应，但不能替代评估数据。引言人同时是 CVE 董事会（CVE Board）成员，博客在署名里写明了这一点。

### 开源社区：14 个 CVE 与一个附录

博客说，开源软件是现代系统的基础，包括 OpenAI 自己的系统。OpenAI 一直在用 Codex Security 扫描自己最依赖的开源仓库，把发现的高影响安全问题分享给维护者。在与维护者的对话里，一个反复出现的主题是：问题不是漏洞报告太少，而是低质量的报告太多。维护者说，他们需要更少的误报、一种更可持续的方式来发现真正的安全问题，而不增加分流负担。这些对话影响了 OpenAI 支持开源社区的方式：不是生成大量推测性发现，而是优先给出维护者能快速处理的高置信度问题。

作为这项工作的一部分，OpenAI 向一些广泛使用的开源项目报告了严重漏洞，包括 OpenSSH、GnuTLS、GOGS、Thorium、libssh、PHP 与 Chromium 等。博客说已有 14 个 CVE 被分配，其中两个是双重报告（dual reporting），并在附录里分享了一些例子。

附录列出的高影响开源漏洞示例包括：GnuTLS certtool 堆缓冲区溢出（差一错误）、GnuTLS SCT 扩展解析中的堆缓冲区越读、GnuTLS otherName SAN 导出中的双重释放、GOGS 的双因素认证绕过与未授权访问、路径遍历、LDAP 注入、未授权拒绝服务与邮件滥用、密码更改后会话未轮换、Elasticsearch 客户端禁用 TLS 验证、拒绝服务（除以零）、gpg-agent 的栈缓冲区溢出等，附 CVE 编号。

这里有一个需要如实记下的不一致：正文说“14 个 CVE 已被分配”，但附录里实际列出的 CVE 编号有 16 个。见文末未核实清单。

博客还说，最近开始让第一批开源维护者加入 Codex for OSS 计划——为生态提供免费的 ChatGPT Pro 与 Plus 账号、代码审查与 Codex Security。vLLM 等项目已经在正常工作流程里用 Codex Security 发现并修补了问题。计划在未来几周内扩大这个项目，让更多维护者直接获得更好的安全、更强的审查工作流与支持。如果是开源维护者且感兴趣，可以联系 OpenAI。

## 四、作者的结论与局限

### 作者的结论

博客没有设“结论”一节，它的结论就是发布本身：Codex Security 从 Aardvark 的私人测试走到了研究预览，向付费客户开放；它用前沿模型推理加自动验证，解决“AI 安全工具噪声太多”与“安全审查跟不上开发速度”这两个问题；它在开源社区的工作方式是优先高置信度发现，而不是大量推测性报告。

### 作者自述的局限

博客没有自述任何局限。它没有说 Codex Security 在哪些情况下不可靠、误报率到底是多少、哪些类型的漏洞它发现不了、也不说三条改进率的适用范围。唯一接近局限表述的话，是研究预览这个状态本身——它还不是正式发布（generally available），行为与可用范围可能还会变——以及“我们预计信噪比会继续改善”，这句话承认了当前信噪比还不完美，但没有展开。

## 五、精读点评

这一节是分析者的判断，和上面对博客的呈现分开写。

### 这篇博客真正要回答的问题

这篇博客真正要回答的问题不是一个科学问题，而是一个产品问题：原 Aardvark 现在叫什么、它怎么工作、谁能用上它、以及 OpenAI 打算怎样把它交到开发者、安全团队与开源维护者手里。

用工具里的科学问题五问来套它，大部分问题是答不上的——这本身就是答案。反常是什么？博客没有指出任何反常或失败：它没有说某个基准上工具翻了车、没有说某个假设被推翻，它只是在说“我们把 Aardvark 改名、放进了 Codex、向付费客户开放了”。为什么重要？博客给出的理由是规模与流程层面的：AI 安全工具噪声太多、安全审查跟不上开发速度、开源维护者被低质量报告淹没。但这是一个动机层面的主张，不是这篇博客证明了的东西——博客没有提供任何证据表明 Codex Security 改变了这个局面。为什么之前做不了？博客没有回答：它没有说从 Aardvark 到 Codex Security 的五个月里移走了哪块具体的石头（数据、算力、方法、概念），只说测试期间的反馈改进了上下文提供方式与接入流程。方法与问题是否匹配？这个问题在这里基本不适用：博客没有方法细节，也就没有“方法回答问题”这回事。答案改变了什么？认知上什么都没改变——博客没有确立任何新的科学事实；实践上它改变的是产品：一个安全工具从私人测试进入研究预览、向付费客户开放、附带一个开源支持计划。

把这五问答不上的状态如实记下来，比硬套一个“科学问题”更诚实。这篇博客的价值不在科学发现，而在公开定性：它第一次以 OpenAI 的名义把 Aardvark 的路线收进 Codex 品牌，并把“可编辑威胁模型、沙箱验证、带系统上下文的补丁”定为这条路线的产品形态。

### 与 LR-237（Aardvark 初版）的关系

这篇是 LR-237 的直接后续，读的时候必须对照着看，有三处变化值得记下。

第一，名字与形态变了。Aardvark 从一个独立的智能体安全研究员，变成了 Codex 里的一个功能 Codex Security，通过 Codex 网页版提供。Aardvark 博客里说的四阶段流水线（分析、提交扫描、验证、打补丁）基本原样保留，只是第一步的威胁模型现在明确写成“可编辑”，验证一步明确写成“沙箱压力测试”，打补丁一步明确写成“带完整系统上下文、尽量减少回归”。

第二，能力数字从一条变成了两组。Aardvark 博客只有一条 92% 的召回率，而且没有分母与精度；这篇博客没有再提 92%，而是给出了 30 天扫描量与发现数（超过 120 万次提交、792 个严重、10,561 个高严重级别），以及三条改进率（噪声降 84%、严重级别高报降 90% 以上、误报率降 50% 以上）。规模数字比 92% 更扎实——分母（提交数）是明确的；改进率则和 92% 一样没有分母与基线，同样不能按精确测量引用。

第三，开源成果从一个计数变成了带附录的清单。Aardvark 博客只说十个漏洞获得了 CVE 编号，没有列出它们；这篇博客说 14 个 CVE 已被分配，并在附录里列出了具体的漏洞与 CVE 编号。这是两篇博客之间最实在的进步：读者第一次可以逐项核对它声称的开源成果。附录里 CVE 编号的数量（16 个）与正文说的 14 个对不上，这个不一致也第一次变得可见——见文末未核实清单。

### 价值判断

认知价值是低的。博客没有推翻或确认任何信念：它没有给出任何可核查的测量，也就没有可被推翻的东西。“高置信度发现”是一个定性断言，不是一个测量；三条改进率没有分母与基线，撑不起“质量显著提高”之外的任何结论。如果这篇博客不存在，关于智能体安全研究的科学认知不会有任何不同——人们失去的只是一次产品发布的消息。

方法价值是低的，但不是零。博客没有留下任何别人能拿走复用的东西：没有新工具、新度量、新实验设计、新数据集。但它留下了一个比 Aardvark 博客更具体的产品思路：威胁模型可编辑、沙箱验证出概念验证、补丁带完整系统上下文、用户调严重级别可以反哺威胁模型。这个思路本身不难想到，但作为一条公开的路线陈述，它是这篇博客里最接近方法贡献的部分。

边界价值是高的，这正是这份精读记录最有用的部分。它明确不证明的东西包括：Codex Security 的精度与误报率到底是多少（没有数字）；三条改进率的基线与适用范围（没有分母）；792 个与 10,561 个发现里有多少经过验证、被确认、被修复（没有数字）；它与传统工具或人类安全研究员相比如何（没有对照）；14 个 CVE 的分量（附录列了 16 个编号，与正文的 14 个对不上）；以及研究预览之外的用户实际用上它会得到什么（发布时只是研究预览）。读者最容易误读的推论，是把“792 个严重发现”读成“792 个已被确认的真实严重漏洞”——博客没有说这些发现经过了什么程度的验证。

启示价值在于，最便宜的决定性下一步不是再读这篇博客，而是等 Codex Security 的后续披露：精度与误报率的数字、在真实仓库上的评估、与基线方法的对照、以及附录 CVE 数量不一致的解释。具体设计在下面“接下来看什么”里写。

### 最弱的一环

最弱的一环是三条改进率与任何可核查条件之间的断裂。整篇博客关于“质量显著提高”的说服力建立在这三条比率上，但读者不知道分母是多少、基线是多少、测了多少仓库、覆盖了多长时间。84% 只限定在“一个案例里”，连适用范围都没有给出。一个没有分母、没有基线的比率，无法支撑“质量显著提高”这个判断——它能支撑的只是“OpenAI 在自己的测试里测出了这些方向”。

第二弱的一环是 792 个与 10,561 个发现这两个数字与“高置信度”之间的断裂。博客用“不到 0.1% 的提交出现严重问题”论证系统能在大量代码里找问题、同时把噪声控制在最小，但它没有说这些发现里有多少经过了沙箱验证、有多少被人工确认、有多少已经修复。没有这个环节，读者无法区分“792 个真实严重漏洞”与“792 个被标为严重的发现”——而这两者之间的差距，正是误报率本身。

第三弱的一环是附录 CVE 数量与正文的不一致。正文说 14 个 CVE 已被分配，附录列出了 16 个 CVE 编号。这个不一致本身不大，但它说明博客的数字没有经过严格的逐项核对——而一篇以“高置信度”与“减少噪声”为卖点的博客，自己的数字对不上，是值得记下的一笔。

### 效度判断

下面是针对这篇博客作为证据的评分，满分 5 分，评的是证据，不是工具本身。对一篇产品发布博客打效度分，本身就有点勉强——它本来就不是证据文件。分数只表示：如果有人拿这篇博客当作关于 Codex Security 能力的证据，它能撑到什么程度。

内部效度 1 分。博客没有对照、没有随机化、没有统计，三条改进率与“质量显著提高”之间的因果链是完全开放的：我们不知道基线是多少，也不知道同样的评估换一批仓库会出什么结果。

外部效度 1 分。博客的说法只能推广到“OpenAI 在 2026 年 3 月 6 日宣布了这些”，不能推广到“用户实际用 Codex Security 会得到什么”。测试队列、未公开的仓库清单、未说明的验证覆盖率，这些条件本身就说明发布当时的体验与博客描述的体验之间还有距离。

构念效度 2 分。“高置信度发现”“显著提高”“真实世界影响”这些概念在这篇博客里没有操作化：没有定义什么算噪声、什么算误报、什么算验证通过。唯一相对扎实的概念是产品形态本身（三步工作流、可编辑威胁模型、沙箱验证、Codex 网页版），因为这些是具体的功能描述，不是能力断言。

统计结论效度 1 分。博客里带数字的说法里，没有一个配上了样本量（除了提交数这个分母）、误差或置信区间。把博客里的任何一句话读成一个统计结论，都是超出了它的证据。

可复现性 1 分。读者无法按博客的描述复现任何一个结果：没有模型、没有权重、没有代码、没有评估所用的仓库、没有改进率的测量方法。唯一能“复现”的是去申请使用研究预览、自己试——那是产品体验，不是复现。

## 七、证伪器、替代解释、接下来看什么

### 证伪器

“过去 30 天扫描超过 120 万次提交、发现 792 个严重问题”：公开测试队列的仓库清单与扫描日志，再由独立一方核对提交数与发现数。如果独立核对的提交数或发现数明显低于博客的数字，这个规模说法就要修正。

“噪声减少 84%、严重级别高报下降 90% 以上、误报率下降 50% 以上”：公开每条比率的基线、分母与测量方法。如果基线本身就很低、或测量只覆盖了少数仓库，这些比率就要按实际口径降级理解。这个主张无法从博客本身证伪——博客没有给出基线，记为不可证伪，只能看后续披露。

“792 个严重发现是高置信度的”：公布这些发现里有多少经过了沙箱验证、有多少被人工确认、有多少已经修复。如果其中多数未经验证或未被确认，“高置信度”这个说法就要修正。

“14 个 CVE 证明了它在开源项目上的实际价值”：解释附录里 16 个 CVE 编号与正文 14 个之间的不一致，并公布每个 CVE 的严重程度与修复状态。如果其中多数是低严重程度、或并非 Codex Security 独自发现，这个主张的分量就要打折。

### 替代解释

替代解释一：测试队列取巧解释。120 万次提交与 792 个严重发现可能来自一批对 Codex Security 友好的测试队列：仓库类型可能偏向它擅长的类型，而真实世界里更难、更隐蔽的漏洞类型可能不在其中。预测：换一批真实仓库，严重发现的比例与验证通过率会明显变化，误报率会成为更值得关注的数字。区分证据：独立评测，或 OpenAI 公开测试队列的仓库清单与完整数字。

替代解释二：产品先行解释。Codex Security 真正的新东西可能不是发现漏洞的能力跃升，而是产品形态的跃升：把威胁模型、沙箱验证、打补丁排成一条连续的流水线，并嵌进 Codex 网页版的工作流，让安全工作跟上代码演进的速度。预测：它在单个漏洞上的发现能力与现有工具或人类研究员的差距，比博客的修辞暗示的要小；而流水线与工作流集成，才是这篇博客里最经得起时间检验的部分。区分证据：与传统工具、人类研究员在同一批仓库上的对照评测。

替代解释三：改名先行解释。“Codex Security”可能主要是品牌整合：Aardvark 并入 Codex 品牌，研究预览向付费客户开放，能力本身在五个月里没有发生质变。预测：后续披露里的能力评估会与 Aardvark 时期基本一致，92% 那个数字的消失只是因为它不再适合新的叙事，而不是因为能力变了。区分证据：后续披露是否给出新的、可核查的能力评估，以及 92% 是否被重申或收回。

### 作者自述局限与分析者发现的局限

作者自述的局限：博客没有自述任何局限。最接近的话是研究预览这个状态本身，以及“我们预计信噪比会继续改善”——这两句承认了当前状态还不完美，但没有展开成任何具体的局限。

分析者发现的、作者没说的局限有四点。第一，三条改进率没有分母与基线，84% 只限定在“一个案例里”。第二，规模数字没有验证环节的数字：792 个与 10,561 个发现里有多少经过验证、被确认、被修复，博客没有说。第三，附录 CVE 数量与正文不一致：正文说 14 个，附录列出 16 个编号。第四，博客没有提 92% 召回率的去向、没有点名模型版本、没有说免费期之后的价格与正式发布的条件。

### 接下来看什么

最值得先做的，是等 Codex Security 的后续披露：精度与误报率的绝对数字、在真实仓库上的评估、与基线方法的对照、以及附录 CVE 数量不一致的解释。

具体设计：对照后续披露里对 Codex Security 的评估，看博客里的定性主张（高置信度、低误报、质量显著提高）在后续披露里有没有对应的测量、测量结果是支持还是收紧了博客的说法；再看后续披露是否给出了博客没提的东西（绝对误报率、验证通过率、修复率、与传统工具或人类研究员的对照）。

判据很简单：如果后续披露里的评估显示三条改进率只在特定仓库或特定条件下成立，这些比率就要按后续披露的口径降级理解；如果后续披露给出了绝对误报率，博客里“误报率下降 50% 以上”的说法才第一次有了可核查的含义。

## I. 结论、结果与价值总览

### 一句话结论

这是一篇产品发布博客，不是研究论文：它宣布原 Aardvark 更名为 Codex Security 并进入研究预览，给出了一组可核对的规模数字（30 天、120 多万次提交、792 个严重发现），以及三条没有分母的改进率——作为发布消息它是完整的，作为能力证据它是空的。

### 核心结论

1. **Codex Security 发布了，是原 Aardvark 的更名与整合（置信度：高）。** 博客于 2026 年 3 月 6 日宣布 Codex Security 进入研究预览，通过 Codex 网页版向 ChatGPT Pro、Enterprise、Business 与 Edu 客户提供，接下来一个月免费。置信度给高，因为这是博客的原话，发布事实本身已核实。

2. **规模数字是全篇最扎实的部分（置信度：高）。** 过去 30 天在测试队列的外部仓库上扫描超过 120 万次提交，识别出 792 个严重发现与 10,561 个高严重级别发现，严重问题出现在不到 0.1% 的提交中。792 / 1,200,000 ≈ 0.066%，与“不到 0.1%”自洽。但这些发现经验证、确认、修复的比例没有给出。

3. **三条改进率都没有分母与基线（置信度：高）。** 噪声在一个案例里减少 84%、严重级别高报下降 90% 以上、误报率下降 50% 以上——方向是博客原话，数字不能按精确测量引用。

4. **开源成果第一次有了可核对的附录，但数字对不上（置信度：中）。** 正文说 14 个 CVE 已被分配，附录实际列出 16 个 CVE 编号。不一致的原因未核实，分量无法判断。

5. **产品形态是这篇博客最实质的内容（置信度：高）。** 可编辑威胁模型、沙箱验证出概念验证、带完整系统上下文的补丁、用户反馈反哺威胁模型——这些都是具体的、可核查的产品事实。

### 科学价值总评

认知价值是低的。博客没有确立任何新的科学事实，“高置信度发现”是一个定性断言，不是测量。如果这篇博客不存在，关于智能体安全研究的科学认知不会有任何不同。

方法价值是低的，但不是零。博客没有留下任何可复用的方法、工具、度量或数据集，但留下了一个比 Aardvark 博客更具体的产品思路：可编辑威胁模型、沙箱验证、带系统上下文的补丁、用户反馈反哺威胁模型。

边界价值是高的。它明确不证明：三条改进率的基线与适用范围、792 个与 10,561 个发现的验证与确认情况、Codex Security 的绝对误报率、它与传统工具或人类研究员相比如何、14 个 CVE 的分量、研究预览之外的用户实际会得到什么。最容易误读的推论，是把“792 个严重发现”读成“792 个已被确认的真实严重漏洞”。

启示价值在于，最便宜的决定性下一步是等 Codex Security 的后续披露，看博客里的定性主张在后续披露里有没有对应的测量。

总体 verdict 是：这篇工作值得被记住为一次产品发布——原 Aardvark 更名为 Codex Security、进入研究预览、向付费客户开放，以及 OpenAI 把安全工作定位为“Codex 里的应用安全智能体”路线的公开表态。不值得被记住为任何关于 Codex Security 能力的证据——它只给了一组规模数字与三条没有分母的改进率，也不该用它的措辞去论证工具发现漏洞的能力有多强。
