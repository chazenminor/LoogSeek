## 一、背景与问题

### 低资源语言：代码少，责任重

有些编程语言的公开代码与文档比 Python、JavaScript 少得多，模型很难从它们身上学到东西。帖子把这类语言叫做低资源编程语言（low-resource programming languages），点名的三个是 COBOL、Fortran 与 Visual Basic。它们的共同点是：支撑着关键基础设施与基本服务，维护起来却越来越难。

COBOL 的例子最能说明这种反差。按帖子引用的第三方数据，COBOL 支撑着超过 40% 的网上银行系统、80% 的现场信用卡交易与 95% 的 ATM 交易；Fortran 用在天气预报与核反应堆安全分析里。这些系统不能停，但维护它们越来越难：文档可能不完整，最初的开发者可能已经离开公司，重要的业务规则可能只存在于代码里。无论是修 bug 还是迁移到另一种语言，团队都要保住这些系统依赖的行为。

### 主要主张

帖子的主张大致有三条。

第一，OpenAI 最新的模型在低资源语言上的能力有了大幅提升，准确率更高、成本更低。MultiLangBench 上，GPT-6 Astra 的平均测试通过率是 87.4%，GPT-5.6 Sol 只有 26.8%；COBOL 迁移评估上，GPT-6.1 Sol 在低推理力度下准确率 86.6%，GPT-5.6 Sol 只有 5.4%，在更高推理力度下达到 97.9%，接近测满。

第二，这两项评估测的是两种互补的能力：从头搭建新软件，与保住已有软件的行为。前者是 MultiLangBench，后者是 COBOL 迁移评估。

第三，OpenAI 正在把 MultiLangBench 的评估设置与测试套件发布到 GitHub 上，让开发者自己检查评估测了什么、看自己用的语言上的表现、找出对自己工作重要的差距。

## 二、方法与设计

### MultiLangBench：从头搭建一个 SQLite 兼容的数据库引擎

MultiLangBench 要求模型用指定的编程语言，从头搭建一个与 SQLite 兼容的数据库引擎。模型要组织代码库、管理状态、处理错误，还要在保留已有功能的前提下增加新功能。

为了能跨语言比较，评估用数据库文件作为统一接口：候选程序拿到一个初始数据库与一条 SQL 查询，产出一个修改后的数据库，再用参考的 SQLite 实现检查产出的数据库内容是否符合预期。这样不管用什么语言搭建引擎，都可以用同一套测试来衡量。

测试是从 SQLite 已有的测试套件改编过来的。评估衡量的是模型在一段较长的编码会话里能搭建出多少可用的功能，报告两个指标：测试通过率与 API 成本。

### COBOL 迁移评估：搬家，但行为一个字节都不能变

第二项评估要求模型把 COBOL 程序迁移到 C++、Java、Kotlin、Python 或 Rust，同时保留每个程序的行为。成功的迁移既要理解程序的业务逻辑，也要理解 COBOL 这门语言特有的行为。

帖子举了一个例子说明为什么这件事难：COBOL 的定点算术（fixed-point arithmetic）会丢弃多余的小数位，除非明确要求四舍五入。一个改写时把这些值四舍五入的重写版本可以正常运行、不报错，却会产出不同的财务结果。金融交易与业务记录的处理里，这类细节——四舍五入规则、缺失记录的处理方式——反映的都是业务要求，错一点都不行。

为了检验这些行为是否被保留，评估用隐藏测试（hidden tests），要求可观测输出的字节级一致（byte-for-byte parity）。只有全部测试通过，迁移才算成功。帖子同时提醒，把这种能力用到生产软件上仍然需要专家审查，并针对系统的业务规则与依赖关系做测试。

### 评估条件

MultiLangBench 的分数是在最大推理力度（maximum reasoning effort）下测的。COBOL 迁移评估的分数分两档：低推理力度（low reasoning effort）与更高推理力度（higher reasoning effort），后者没有点名具体是哪个档位。

对照组是 GPT-5.6 Sol，MultiLangBench 上是它的 26.8%，COBOL 迁移上是它在同样低推理力度下的 5.4%。GPT-6 Luna 只在 MultiLangBench 上出现，作为低成本选项。

### 按检查表，什么是“未报告”

没有报告的东西有几样。两项评估各自的样本量（多少个任务、多少个程序）没有给出；每个分数的运行次数、误差棒、置信区间都没有；MultiLangBench 的 20 种语言里，除了点名的四种（COBOL、OCaml、Fortran、Visual Basic），其余 16 种各自的分数没有在正文里给出——帖子说结果在 GitHub 上，但本篇没有去读 GitHub 仓库；COBOL 迁移评估里“更高推理力度”具体是哪个档位，帖子没有点名；“准确率 97.9%”的分母是多少（多少个程序），帖子没有说；成本数字是“估计的 API 成本”，估计方法没有定义；评估的隐藏测试集规模、任务来源（真实遗留代码还是合成程序），帖子没有说明。

同行评审状态不适用：这不是一篇论文，没有投稿、没有评审。它的可信度取决于 OpenAI 自己公布的数字，而这些数字没有以可下载的原始数据形式公开——不过 MultiLangBench 的测试套件据称已在 GitHub 上发布，第三方可以去复核，见未核实清单。

## 三、主要发现

### MultiLangBench：Astra 平均 87.4%，Sol 只有 26.8%

在最大推理力度下，GPT-6 Astra 在 20 种语言上的平均测试通过率是 87.4%，GPT-5.6 Sol 是 26.8%，差距是 60.6 个百分点。提升覆盖了测试的每一种语言。点名的四种语言里，COBOL 从 10.9% 升到 72.1%，OCaml 从 25.6% 升到 85.8%，Fortran 从 21.4% 升到 83.5%，Visual Basic 从 27.5% 升到 89.4%。

Astra 在 20 种语言里有 19 种得分超过 83%，COBOL 是最难的一种，72%——帖子在两个地方写了 COBOL 的分数，一处是 72.1%，一处是 72%，后者是前者的四舍五入，对得上。

GPT-6 Luna 作为低成本选项，在最大推理力度下平均测试通过率 40.3%，同样在每种语言上都超过了 GPT-5.6 Sol。点名的四种语言里，COBOL 从 10.9% 升到 17.1%，OCaml 从 25.6% 升到 34.1%，Fortran 从 21.4% 升到 31.4%，Visual Basic 从 27.5% 升到 41.6%。它的估计平均 API 成本是每个样本 0.77 美元，GPT-5.6 Sol 是 3.48 美元，大约低 78%。验算一下：0.77 除以 3.48 等于 0.221，确实低了约 78%。

### COBOL 迁移：6.1 Sol 低推理力度 86.6%，高推理力度 97.9%

COBOL 迁移评估上，GPT-6.1 Sol 在低推理力度下准确率 86.6%，GPT-5.6 Sol 在同样设置下只有 5.4%，差距是 81.2 个百分点；同时 6.1 Sol 的成本只有 Sol 的 61%，也就是低 39%。在更高推理力度下，准确率达到 97.9%，帖子说这让评估“接近饱和”（nearly saturating the evaluation）。

5.4% 这个对照分数值得留意。它说明 GPT-5.6 Sol 在这项评估上几乎完全做不对——不是“做得差一点”，而是“几乎全错”。这个对照分数本身就是一个发现：低推理力度下的 Sol 连 COBOL 迁移的门槛都没摸到。而 6.1 Sol 在同样的低推理力度下能做到 86.6%，说明提升不是靠多花算力堆出来的，至少在低推理力度这一档上是模型本身变强了。

但 97.9% 这个数字也要看清它的含义。它说的是“在更高推理力度下，97.9% 的迁移全部通过了隐藏测试”。帖子没有说分母是多少——是几十个程序，还是几百个——也没有说这些程序是真实的遗留代码还是合成的测试程序。97.9% 接近测满，意味着这项评估本身已经快测不出模型之间的差距了，下一代模型需要更难的评估。

### 成本：更强，而且更便宜

帖子反复强调的一点是，准确率提升的同时成本也在下降。MultiLangBench 上，Luna 的每个样本成本 0.77 美元对 Sol 的 3.48 美元，低约 78%；COBOL 迁移上，6.1 Sol 在低推理力度下的成本只有 Sol 的 61%。这两组成本数字都是“估计的 API 成本”，帖子没有定义估计方法——是按实际 token 用量算的，还是按定价表算的，没有说明。

### 帖子自己划的边界

帖子在 COBOL 迁移一节的末尾自己划了一条线：把这种能力用到生产软件上仍然需要专家审查，并针对系统的业务规则与依赖关系做测试。换句话说，97.9% 是“在隐藏测试上全部通过”的比例，不是“可以直接上线”的保证。真实遗留系统里的业务规则往往没有文档、只存在于代码与老员工的脑子里，评估里的隐藏测试覆盖不了这些。

## 四、作者的结论与局限

### 作者的结论

帖子的结论就是开篇那句话：最新的模型在两项评估上都有大幅提升，准确率更高、成本更低。具体说，MultiLangBench 上 Astra 平均 87.4% 对 Sol 的 26.8%，COBOL 迁移上 6.1 Sol 低推理力度 86.6%、高推理力度 97.9% 对 Sol 的 5.4%。帖子没有设结论节，这些结论散落在开篇与各段落里。

### 作者自述的局限

帖子没有设“局限”一节。以下边界是它在行文里自己承认的，散落在各处。

第一，把迁移能力用到生产软件上仍然需要专家审查，并针对系统的业务规则与依赖关系做测试——评估分数不等于可以直接上线。

第二，帖子没有明说但行文里能看出来的一点：两项评估测的都是“在评估里做得对不对”，不是“在真实遗留系统上做得对不对”。真实系统的文档不完整、原开发者已离开、业务规则只存在于代码里，这些困难在评估里是被抽象掉的。

帖子没有明说的局限，见下一节精读点评。

## 五、精读点评

### 这篇工作真正要回答的问题

先把问题还原成它本来的样子。这不是一篇研究论文，没有科学发现要报告；它要回答的是一个能力问题：模型能不能在公开代码与文档很少的语言里，既从头搭建软件，又把已有的软件原样搬走。反常不在于某个基准分数，而在于低资源语言的特殊处境：这些语言支撑着银行、天气预报、核安全这些不能停的系统，但因为公开代码少，模型在它们身上一直很弱——而维护这些系统的人最需要的，恰恰是模型在这些语言上变强。

为什么重要？对实践来说，这决定了银行、政府与企业能不能用 AI 来维护与现代化改造它们依赖的遗留系统：如果模型在 COBOL 上只有 10.9% 的通过率，这些系统就只能继续靠越来越少的人工维护；如果能到 72% 甚至更高，维护与迁移就有了新的工具。对行业来说，它把“低资源”这个概念从自然语言处理借到了软件工程：公开数据少，不等于不重要。

为什么之前做不了？帖子没有明说，但 blocker 是清楚的：低资源语言的公开代码与文档太少，模型在训练里见得少；而且“迁移时保住行为”这个要求比“写出能跑的代码”要严得多——四舍五入的规则、缺失记录的处理方式，错一点就会产出不同的财务结果，而这些规则往往只存在于代码里。这篇工作的办法是绕过这个 blocker：不依赖公开数据，而是自己出题——MultiLangBench 用数据库文件作统一接口，让同一套测试能跨语言比较；COBOL 迁移评估用隐藏测试要求字节级一致，把“保住行为”变成一个可判定的标准。

方法与问题是匹配的：两项评估恰好对应两种互补的技能——从头搭建，与原样搬走。MultiLangBench 测的是“能不能造”，COBOL 迁移测的是“能不能保住”。但匹配不等于证明：它证明的是“在这两项自研评估上，最新模型比 Sol 好得多”，没有证明“在真实遗留系统上，模型也能做到同样的事”。

答案改变了什么？认知上，它确认了低资源语言不是模型能力的死角：Astra 在 20 种语言上平均 87.4%，COBOL 从 10.9% 升到 72.1%，说明“公开数据少”这个限制是可以被克服的。实践上，它给出了一个清晰的选型信号：从头搭建用 Astra，COBOL 迁移用 6.1 Sol，低成本场景用 Luna。至于它没有改变的东西：它没有证明模型在真实遗留系统上同样可靠，帖子自己也提醒了这一点——用到生产软件上仍然需要专家审查。

### 证据链：数字全、条件清，但评估是自研的

先说这篇帖子的优点。它是这批里数字给得最全、条件写得最清楚的一篇：MultiLangBench 上 Astra 与 Luna 各自的平均分、点名的四种语言各自的分数、每个样本的成本，全都给了；COBOL 迁移上低推理力度与高推理力度的分数、对照分数、成本比，全都给了。能验算的部分都站得住：Luna 的 0.77 美元对 3.48 美元确实低约 78%；COBOL 的 72.1% 与后文的 72% 是四舍五入的关系，对得上；5.4% 到 86.6% 的差距是 81.2 个百分点，帖子没有夸大。

问题出在评估本身是自研的。MultiLangBench 与 COBOL 迁移评估都是 OpenAI 自己出的题、自己打的分，测试集没有公开过同行评审，任务来源（真实遗留代码还是合成程序）也没有说明。帖子说 MultiLangBench 的评估设置与测试套件已在 GitHub 上发布，这是一个可以复核的承诺，但本篇没有去读 GitHub 仓库——如果仓库里的测试与帖子说的对得上，评估的可信度就高一截；如果对不上，帖子的数字就要打折扣。这个复核是后续工作里最值得做的一件。

第二个问题是样本量与误差棒全都没有。两项评估各自有多少个任务、每个分数跑过几次、波动多大，帖子一概没有报告。MultiLangBench 的 20 种语言里，除了点名的四种，其余 16 种各自的分数没有在正文里给出——帖子说结果在 GitHub 上，但正文里只给了平均分。平均分 87.4% 背后，19 种语言超过 83%、COBOL 是 72%，这个分布是帖子自己说的；但没有逐语言分数，读者没法看到分布的全貌，也没法判断平均分是不是被少数几种语言拉起来的。

第三个问题是“更高推理力度”没有点名档位。COBOL 迁移的 97.9% 是在“更高推理力度”下取得的，但帖子没有说这是 high、xhigh 还是 max。没有档位，就没法判断 97.9% 的代价是多少——如果是在 max 档位下取得的，那么它的每任务成本可能比低推理力度下高得多，而帖子只给了低推理力度下的成本比（61%）。读者如果把 97.9% 与“成本只有 61%”拼在一起，就会误以为“又好又便宜”是在同一个设置下成立的，实际上这两个数字来自不同的推理力度。

还有一个值得留意的地方：GPT-5.6 Sol 在 COBOL 迁移上的 5.4% 是在“同样设置”下测的，也就是低推理力度。这个对照是干净的——同样的档位，86.6% 对 5.4%，提升是真实的。但 MultiLangBench 上的对照就没有这么干净：Astra 与 Luna 的分数都是在最大推理力度下测的，Sol 的 26.8% 是在什么推理力度下测的，帖子没有明说。如果 Sol 的 26.8% 是在默认档位下测的，而 Astra 的 87.4% 是在最大推理力度下测的，那么 60.6 个百分点的差距里，有多少是模型更强，有多少只是算力更多，帖子的数据区分不了。

### 价值判断

认知价值：它提供了一个具体的认知更新——低资源语言不是模型能力的死角，公开数据少这个限制是可以被克服的。Astra 在 20 种语言上平均 87.4%、COBOL 从 10.9% 升到 72.1%，这个幅度本身就是证据。反事实是：要推翻这个判断，需要证明这两项评估的分数在独立复测中不存在——而 MultiLangBench 的测试套件据称已在 GitHub 上发布，复测是可能的，所以这个判断是可检验的。

方法价值：它留下了两项可以复用的评估——MultiLangBench 与 COBOL 迁移评估。前者用数据库文件作统一接口、让同一套测试能跨语言比较，这个设计本身就是一个可复用的方法；后者用隐藏测试要求字节级一致，把“保住行为”变成可判定的标准，也是一个可复用的设计。如果 GitHub 上的发布与帖子说的相符，这两项评估的方法价值就是这批里最高的。

边界价值：它明确不证明模型在真实遗留系统上同样可靠，帖子自己就划了线——用到生产软件上仍然需要专家审查。读者最容易误读的推论是“COBOL 迁移已经解决了，97.9% 就是可以直接上线”——准确的说法是“在 OpenAI 自研的隐藏测试上，97.9% 的迁移全部通过”，真实遗留系统里的业务规则往往没有文档、只存在于代码与老员工的脑子里，评估覆盖不了这些。

启示价值：最便宜的决定性下一步，是去读 GitHub 上的 MultiLangBench 仓库，核对测试套件与帖子说的是否相符，再用它独立复测 Astra 与 Sol 的分数。如果复测的分数与帖子对得上，这两项评估就立住了；如果复测发现测试集有泄漏、或者分数对不上，帖子的数字就要打折扣。其次是看真实遗留系统上的验证：找一套真实的、带业务规则的 COBOL 代码库，让模型去迁移，看隐藏测试之外的业务规则是不是真的被保住了。

### 最弱的一环

全篇最薄弱的一环，是评估的自研性与不可复核性。两项评估都是 OpenAI 自己出的题、自己打的分，样本量、运行次数、误差棒全都没有，16 种语言的逐语言分数只在 GitHub 上、正文里没有，COBOL 迁移的“更高推理力度”没有点名档位。帖子给出的数字本身是完整的、可验算的，但数字背后的评估设计——任务从哪来、有多少、怎么打分——读者只能相信 OpenAI 的说法，没法独立核查。MultiLangBench 在 GitHub 上的发布是唯一的复核入口，而本篇没有去读它。

这不是说数字是假的，而是说数字的可信度取决于评估本身的质量，而评估本身的质量目前没有独立证据。按“能力评估帖”的标准去读，它是这批里最扎实的一篇；按“研究报告”的标准去读，它仍然缺少样本量、误差棒与独立复测。这篇精读把它当作前者来读，结论也只做到前者的程度。

### 效度判断

内部效度中等。COBOL 迁移上的对照是干净的——同样的低推理力度，86.6% 对 5.4%——但 MultiLangBench 上的对照没有明说推理力度是否相同，评估本身是自研的，样本量与运行次数没有报告。

外部效度窄。结论只针对这两项自研评估、这几个模型、发布时的版本。能不能推广到真实的遗留系统、别的低资源语言、别的任务，帖子没有提供证据，而且自己提醒了生产使用仍需专家审查。

构念效度方面，“测试通过率高”在这里被当作“能维护与迁移遗留软件”的证据，但评估里的任务与真实遗留系统之间有一道鸿沟：真实系统的业务规则往往没有文档、只存在于代码与老员工的脑子里，而评估里的隐藏测试只能覆盖可形式化的行为。帖子没有讨论这道鸿沟，只是提醒了生产使用仍需专家审查。

统计结论效度低。没有任何一个分数附带样本量、运行次数、误差棒或置信区间；16 种语言的逐语言分数没有在正文里给出；“估计的 API 成本”的估计方法没有定义。这些数字作为方向性证据是可用的，作为精确的效应量是不可用的。

可复现性中等。帖子称 MultiLangBench 的评估设置与测试套件已在 GitHub 上发布，如果发布属实，第三方可以复核 MultiLangBench 的分数；但 COBOL 迁移评估的隐藏测试集没有发布，第三方无法重跑那一项。好在复核不完全依赖复现：正文数字的算术只需要帖子本身就能验算，而且都站得住。

## 七、证伪器、替代解释、接下来看什么

### 证伪器

- 读 GitHub 上的 MultiLangBench 仓库，用它独立复测 Astra 与 Sol 的分数：如果复测的平均分与帖子的 87.4% 对 26.8% 对不上，或者发现测试集有泄漏，帖子的数字即被削弱。
- 在真实的、带业务规则的 COBOL 代码库上验证迁移：如果模型在真实遗留代码上的迁移通过率远低于 97.9%，或者隐藏测试之外的业务规则被改坏了，“COBOL 迁移已经接近解决”的说法即被削弱。
- 固定推理力度重新测 MultiLangBench：如果 Sol 在最大推理力度下的分数远高于 26.8%，60.6 个百分点的差距就要打折扣。
- 公布 COBOL 迁移“更高推理力度”的具体档位与成本：如果 97.9% 是在 max 档位下以数倍成本取得的，“又好又便宜”的说法即被削弱。

### 替代解释

替代解释一：MultiLangBench 上的差距主要来自推理力度，而不是模型本身更强。Astra 与 Luna 的分数都是在最大推理力度下测的，Sol 的 26.8% 是在什么推理力度下测的，帖子没有明说。如果 Sol 的分数是在默认档位下测的，而 Astra 是在最大推理力度下测的，那么 60.6 个百分点的差距里，有多少是模型更强，有多少只是算力更多，帖子的数据区分不了。区分的办法是固定推理力度重新测：把所有模型放在同一个档位下比较。帖子没有提供这样的数据。

替代解释二：COBOL 迁移的 97.9% 主要来自评估本身太容易，而不是模型真的学会了迁移。帖子说 97.9% 让评估“接近饱和”，但没有说分母是多少、程序是真实遗留代码还是合成的测试程序。如果测试程序是合成的、业务逻辑简单的，那么 97.9% 反映的是模型在简单程序上的表现，而不是在真实遗留系统上的表现。区分的办法是在真实的、带业务规则的 COBOL 代码库上测一次。帖子没有提供这样的数据。

### 作者自述局限与分析者发现的局限

作者自述的局限：把迁移能力用到生产软件上仍然需要专家审查，并针对系统的业务规则与依赖关系做测试；两项评估测的都是评估里的表现，不是真实遗留系统上的表现。

分析者发现的局限，作者没有明说的有三点。第一，MultiLangBench 上 Sol 的对照分数没有明说推理力度，比较口径可能不对等。第二，COBOL 迁移的 97.9% 没有点名推理力度档位、没有给出分母，成本未知。第三，样本量、运行次数、误差棒全都没有，16 种语言的逐语言分数只在 GitHub 上、正文里没有，评估本身的可复核性取决于一个本篇没有去读的仓库。

## I. 结论、结果与价值总览

### 一句话结论

低资源语言的编码能力确实大幅提升了：MultiLangBench 上 Astra 平均 87.4% 对 Sol 的 26.8%，COBOL 迁移上 6.1 Sol 低推理力度 86.6% 对 Sol 的 5.4%、高推理力度 97.9% 接近测满，而且成本更低；但两项评估都是 OpenAI 自研的，样本量与误差棒全都没有，所以它是一篇扎实的能力评估帖，不是一份有独立复测背书的研究报告。

### 核心结论

1. MultiLangBench 上，GPT-6 Astra 在 20 种语言上的平均测试通过率是 87.4%，GPT-5.6 Sol 是 26.8%，差距 60.6 个百分点；COBOL 从 10.9% 升到 72.1%，是 20 种语言里最难的一种。置信度中。证据：数字台账 E1、E2、E3。
2. COBOL 迁移评估上，GPT-6.1 Sol 在低推理力度下准确率 86.6%，GPT-5.6 Sol 在同样设置下只有 5.4%，差距 81.2 个百分点，成本只有 Sol 的 61%。置信度高。证据：数字台账 E6。
3. COBOL 迁移在更高推理力度下准确率达到 97.9%，接近测满；但具体档位没有点名，分母没有给出。置信度中。证据：数字台账 E7。
4. GPT-6 Luna 在 MultiLangBench 上平均 40.3%，每个样本成本 0.77 美元对 Sol 的 3.48 美元，低约 78%。置信度高。证据：数字台账 E4、E5。
5. 帖子自己划了边界：把迁移能力用到生产软件上仍然需要专家审查，评估分数不等于可以直接上线。置信度高。证据：正文第 2 节。

### 科学价值总评

认知价值：提供了一个具体的认知更新——低资源语言不是模型能力的死角，公开数据少这个限制是可以被克服的；Astra 在 20 种语言上平均 87.4%、COBOL 从 10.9% 升到 72.1%，这个幅度本身就是证据。方法价值：留下了两项可以复用的评估——MultiLangBench 用数据库文件作统一接口、让同一套测试能跨语言比较，COBOL 迁移评估用隐藏测试要求字节级一致；如果 GitHub 上的发布与帖子说的相符，这两项评估的方法价值就是这批里最高的。边界价值：它明确不证明模型在真实遗留系统上同样可靠，帖子自己就划了线——用到生产软件上仍然需要专家审查；读者最容易误读的推论恰恰是“COBOL 迁移已经解决了，97.9% 就是可以直接上线”。启示价值：下一步最值得看的是去读 GitHub 上的 MultiLangBench 仓库并独立复测，其次是真实遗留系统上的验证——前者裁决评估本身能不能信，后者裁决 97.9% 能不能当真。

总体 verdict：这是一篇扎实的能力评估帖，值得因为它给全了数字、写清了条件、算清了成本而被记住，不值得因为它正文里的 97.9% 而被当作“COBOL 迁移已经解决”的证据。读它的时候，以两项自研评估、样本量与误差棒全都没有、真实遗留系统尚未验证这三个限定为准，正文里的分数只作参考。

### 适用边界

它不证明模型在真实遗留系统上同样可靠，不证明 COBOL 迁移已经解决，不证明 MultiLangBench 上的 60.6 个百分点差距全都是模型本身的提升（Sol 的对照推理力度未明说），也不证明 97.9% 是在可负担的成本下取得的（档位未点名）。它不该被拿来为“遗留系统现代化已经解决”背书，也不该被拿来为“低资源语言问题已经解决”背书。分数只在发布当天、这两项自研评估上准确，引用时必须注明条件。
